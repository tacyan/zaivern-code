# 操作性ループ (UX Loop) — 進捗台帳

「世界一のエディタ」を目標に、操作性の穴を潰し続ける長期ループの台帳。
参照した先行実装: superset / VS Code / cmux / orca / Zed。

**この文書はコンテキスト消失を跨いで生き残る唯一の状態である。**
1 反復ごとに「発見 → 実装 → 検証 → コミット」を記録すること。

## ループの1反復

1. 穴の発見: 調査エージェントを並列で走らせ、機能ごとに 実装済み/部分的/無し を判定
2. 優先順位: インパクト × 実装容易性 で並べ替え、独立した実装単位へ分割
3. 並列実装: worktree 隔離した実装エージェントへ配布 (ファイル衝突を事前に分割)
4. 検証: 各エージェントが `cargo check` + 自分のテストを走らせ、出力を証拠として提出
5. 統合: このブランチへ取り込み、`cargo nextest run` で全体を確認
6. 記録: 下の「反復ログ」へ追記

## 不変条件 (毎反復で確認する)

- ハードコーディング無し (パス・OS 前提・エージェント固有値)
- `cargo check` の `never used` 警告ゼロ = 追加した機能に到達経路がある
- 追加した機能はパレット / メニュー / ボタン / キーバインドのいずれかから到達できる
- 機能を足す前に、重複した到達経路を減らせないか考える

### 運用上の学習

- **worktree 隔離エージェントの並列度は 4〜5 が上限。** 8 体で走らせたら
  ロードアベレージが 79 まで上がり、2 体がストリーム停滞で落ちた。
  各 worktree が独立した `target/` を持つため、ビルドが CPU を食い合う。
- **描画層 (`code_editor_ui`) は衝突の主戦場。** 複数キャレット・検索ヒット・
  括弧・波線がすべて同じ場所に挿さる。解決するときは**重ね順**を意識して
  両方を残すこと (下地 → 選択 → キャレット → 波線)。
- エージェントの「正直な申告」は受け入れる価値がある。例: IME 変換中に
  N 箇所へ文字を散らすと確定前に本文が壊れるため、変換中は主キャレットのみ
  — これは手抜きではなく設計判断。

## 反復2 (2026-08-09) — VS Code パリティ

### 運用上の重大な発見

**worktree 隔離エージェントは常に `main` から分岐する** (統合ブランチからではない)。
そのため統合を重ねるほど後発エージェントの衝突が増える。実測: 10 件統合した時点で
後発 1 体の衝突が **21 箇所**、うち 1 つは設計レベルの食い違い
(`TreeActions` が `Vec` か `Option` か) だった。

**対策**: 各エージェントへ「**コミット前に統合ブランチを自分の worktree へ取り込んで
衝突を解決する**」よう指示する。設計レベルの食い違いは、自分のコードの意図を
知っているエージェント本人に解決させるのが早い (指揮者が直すと意図を取り違える)。

### 指示を出す前に実態を確認する

反復2の実装指示のうち**複数が誤った前提**だった。並行して走らせた実コード監査が
以下を明らかにした:

| 指示に書いた前提 | 実際 |
|---|---|
| ツリーの D&D 移動は実装済み | **存在しない** (`dnd_drop_zone` がツリーに1つも無い) |
| コピペの自動採番は未実装 | **実装済み** (VS Code の `incrementalNaming` 準拠、テスト付き) |
| 末尾空白除去・最終改行・保存時整形は未実装 | **すべて実装済み** |
| Emmet / 複数ルート / include-exclude glob / 置換プレビュー / ターミナル分割 | **すべて実装済み** |

**教訓**: 調査エージェントの報告を実装指示へ写すときは、必ず「無い」と書かれた項目を
自分で grep して裏を取る。写し間違えると、エージェントは存在しないものを作り直す。

### egui 0.29 / winit 0.30 で原理的に不可能と確認したもの

- **アプリ発の OS ドラッグ** (ツリーから Finder へ書き出す) — winit に drag-source API が無い。
  受け取り側 (`raw.dropped_files`) は実装済みなので非対称のまま
- **タブを別ウィンドウへ切り離すジェスチャ** — ウィンドウ外のドラッグ座標が取れない

- **編集可能な Peek Definition** — ネストしたテキスト編集の入力ルーティングが素直でない。
  「行間に埋め込む読み取り専用ビュー」で妥協するのが現実的

- **事前に「コミット前へ統合ブランチを取り込め」と指示した回は衝突ゼロ**、

  「複数選択の D&D で最初の衝突を 1 回聞けば残り全部に効く」まで繋いできた。
  指揮者が機械的に直していたらこの価値は出ていない。
- **メッセージの誤配送に注意。** 訂正を隣のエージェントへ送ってしまったが、

### egui 0.29 の制約として確定したもの (再挑戦しないこと)

- **選択テキストのドラッグ移動は TextEdit のフォークなしには不可能。**
  `show_content` の内部が `Sense::click_and_drag()` の応答を自分で解釈し、
  ドラッグを常に「選択範囲の延長」として消費する。「既存の選択の内側で押した」を
  先に横取りする口が無く、`interactive(false)` は選択延長だけでなくキャレット配置と
  入力ごと殺す。既存の選択操作を壊すリスクの方が大きいので入れない。

### 全体テストが遅い件の決着 (誤診を 3 回してから分かったこと)

**結論: 製品の欠陥ではない。全 2926 件が通る** (`--no-fail-fast` で 1010 秒、
遅いのは race の 1 件のみ)。CI プロファイルの `terminate-after` が
その 1 件を落として実行を中断していただけだった。

**遅さの正体**: テストバイナリが **111MB** あり、1 プロセスの起動だけで 0.83 秒かかる。
nextest は**テスト 1 件につき 1 プロセス**を起こすので 2926 回起動し、16 並列で
読み込みが競合する。この作業ツリーは `target` 25GB + `.claude/worktrees` 配下 23GB を
抱えており、ページキャッシュが押し出されて読み込みがさらに遅い。
**各エージェントの worktree では同じ 2900 件が 104〜137 秒で通っている。**

**私が誤診した順序と、その原因**:
1. 「マシン飽和」— エージェントを止めても再現したので誤り
2. 「自分が入れた掃除処理」— 直しても再現したので誤り
   (ただし 1 プロセス 1 回の `read_dir` は実際に O(n²) だったので、
   スタンプで 1 時間に 1 回へ間引く修正自体は正しい)
3. 2 回の「計測」が `--slow-timeout` を CLI 引数として渡していて**そもそも走っていなかった**

**教訓**: 「遅い」を追うときは、**最初に全件を最後まで走らせて分布を取る**。
仮説から入ると、仮説に合う対策を打って、効かなかったことだけが分かる。
計測コマンドが本当に走ったかを、結果を読む前に確かめる。

**残した改善** (これらは独立して正しい):
- テスト用リポジトリを一段深く掘り、worktree が共有 `$TMPDIR` 直下に生まれないようにした
- `unique_temp_dir` の掃除をスタンプで 1 時間に 1 回へ間引いた
  (テストが後始末をせず 3441 個 / 251MB 溜まっていたのは事実)
