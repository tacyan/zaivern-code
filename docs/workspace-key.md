# ワークスペースキー — 台帳の置き場を決める 16 桁

`history::workspace_key(cwd) -> String` は「作業フォルダ → 16 桁 hex」の写像で、
**このアプリがディスクへ残すものの置き場をほぼ全部決めている**。

| 層 | 置き場 |
|---|---|
| 履歴 (`history.rs`) | `~/.zaivern/history/<agent>/<key>.jsonl` |
| リース台帳 (`lease.rs:2148`) | `~/.zaivern/lease/<key>.json` |
| 競合ゼロの予約 (`czero.rs:1334`) | `~/.zaivern/czero/<key>/` |
| ローカル履歴 (`local_history.rs:1717`) | `~/.zaivern/local_history/<key>/` |
| mesh のスコープ (`mesh.rs:677`) | 文字列としてそのまま |

つまり**キーが 1 ビットでも変われば、利用者から見て「台帳もセッションも
ログも全部消えた」**ことになる。しかも消えたことに気付く手段が無い
(新しいキーの場所は空なので、ただの初回起動に見える)。

したがってこのキーに求める性質は 1 つだけ:

> **同じフォルダなら、いつ・どの版のバイナリで計算しても同じ 16 桁になる。**

## なぜ `DefaultHasher` を捨てたか

v0.14.0 まではこうだった:

```rust
let resolved = cwd.canonicalize().unwrap_or_else(|_| cwd.to_path_buf());
let mut hasher = DefaultHasher::new();
resolved.to_string_lossy().hash(&mut hasher);
format!("{:016x}", hasher.finish())
```

`std::collections::hash_map::DefaultHasher` は標準ライブラリのドキュメントが
**「アルゴリズムと出力は Rust のリリース間で変わり得る」と明言している**。
インスタンス間で安定なだけで、*版*をまたぐ保証は無い。

これは「rustc を上げたらキーが変わるかもしれない」ではなく、
**「上がったときに全ワークスペースのデータが無言で行方不明になる」**という
リリースブロッカーである。`zai` は単一バイナリを配って自動更新する前提なので、
利用者は自分で rustc を選べない。

「どのリポジトリでも競合が起きない」という主張の土台がコンパイラの版に
依存していたことになる。

## 選んだハッシュ: FNV-1a 64bit

```rust
const FNV_OFFSET: u64 = 0xcbf2_9ce4_8422_2325;
const FNV_PRIME:  u64 = 0x0000_0100_0000_01b3;
```

理由は 3 つ:

1. **依存を増やさずに 5 行で書ける。** `Cargo.toml` を 1 行も触らない
   (`fnv` クレートは syntect の孫依存として入ってはいるが、直接依存として
   宣言していないものに台帳の場所を預けるのは筋が悪い)。
2. **公開テストベクタで外部から検証できる。** `fnv1a64(b"a") == 0xaf63dc4c8601ec8c`、
   `fnv1a64(b"foobar") == 0x85944171f73967e8` は FNV の作者が公開している値。
   「うちの実装同士で一致する」ではなく「世界の FNV と一致する」ことが確かめられる。
3. **同じ理由で既に `spec.rs:225` が採っている。** 新しい概念を持ち込まない。

暗号用途ではない。求めているのは秘匿性ではなく**再現性**である。
64bit なので、現実的なワークスペース数 (数十〜数百) では衝突は起こらない。

## 正規化の規則

キーを取る前にパスへ当てる規則は 5 つだけ。

1. **シンボリックリンクと `..` を解決する。** `canonicalize` が本命だが、
   **存在しないフォルダでも諦めない**: (a) そのまま → (b) 字面で `..` を
   畳んでもう一度 → (c) **実在する最も深い祖先まで戻って解決し、残りを継ぎ足す**。
   (c) が要るのは macOS の `$TMPDIR` (`/var/…` の実体は `/private/var/…`) で
   必ず踏むため。これが無いと「フォルダを作った瞬間にキーが変わる」。
   Windows の `\\?\` 接頭辞は `pathx::plain` で落とす — 付いたり付かなかったり
   する接頭辞をそのまま混ぜると、**フォルダが実在するかどうかでキーが変わる**。
2. **相対パスは現在の作業ディレクトリで絶対化する。** `zai .` と
   `zai /path/to/x` が別のキーになってはいけない。
3. **区切りを `/` に揃え、`.` / 空 / 末尾の区切りを畳む。**
   `\` を写すのは **Windows だけ**。unix では `\` は普通のファイル名文字なので、
   触ると別々のフォルダが同じキーになる。
4. **大小を畳む — ただし既定のファイルシステムが大小を区別しない OS でだけ**
   (`FOLD_CASE = cfg!(any(target_os = "windows", target_os = "macos"))`)。
   macOS / Windows で `MyRepo` と `myrepo` は同じフォルダなので、畳まないと
   **同じフォルダに 2 つの台帳ができて排他が効かない**。Linux の ext4 / xfs は
   区別するので畳んではいけない (別々のフォルダが 1 つの台帳を共有し、
   いもしない相手に断られる)。
   畳むのは **ASCII の範囲だけ**: `str::to_lowercase` は Unicode の写像表を引き、
   **その表は rustc に同梱される Unicode の版で変わる** — `DefaultHasher` を
   捨てた理由と同じ問題を連れ戻してしまう。`A-Z → a-z` は未来永劫変わらない。
5. **Unicode で表せないパス名は生バイトも混ぜる。** `to_string_lossy` は
   不正なバイトを U+FFFD へ潰すので、別々のフォルダが同じ文字列になり得る
   (Linux では latin-1 のファイル名が普通に存在する)。潰れたときだけ
   `<正規化文字列> ++ 0x00 ++ <生バイト>` を FNV へ流す。

### 固定したテストベクタ

`history::tests::正規化済みパスからキーへの写像を値ごと固定する` が番人。
値は Python の独立実装で突き合わせて起こした。

| 正規化済みの入力 | キー |
|---|---|
| `/home/u/proj` | `143becae573131b5` |
| `/` | `af63a24c860189fe` |
| `c:/users/u/proj` | `e1f5d8f194c658cf` |
| `"/tmp/ws/\u{FFFD}"` + 生バイト `b"/tmp/ws/\xff"` | `ba0cf83a33d8fe77` |

`canonicalize` はファイルシステムに触るので、値を固定する層 (`key_of_normalized`)
は純関数として切り出してある。**どの OS のどのマシンでも、実在するフォルダ無しで
同じ値になることを確かめられる。**

### 既知の限界 (正直に書く)

- **大小を区別する APFS ボリューム**を使っていると、`Foo` と `foo` が別の
  フォルダなのに 1 つの台帳を共有する。排他としては安全側 (混ぜるのであって
  緩めるのではない) に倒れるが、履歴は混ざる。
- **macOS の Unicode 正規化 (NFC / NFD)**。`canonicalize` が成功する限りは
  ディスク上の形へ寄るので揃うが、失敗した経路では NFC と NFD が別のキーに
  なり得る。直すには `unicode-normalization` の依存が要るので、今は入れない。

## 移行: 「旧キーも読む」ではなく「改名する」

旧キーで置かれたデータは `history::adopt_legacy_keys_in(zdir, cwd)` が
**新しい名前へ改名して引き取る**。読み側で両対応にはしない。

**なぜ改名か。** 読み側で両対応にするには、キーを使う 4 つの層
(`lease` / `czero` / `local_history` / `history`) がそれぞれ
「新の場所を見て、無ければ旧の場所を見る」を書く必要がある。置き場の形も
違う (`<key>.json` / `<key>/` / `<agent>/<key>.jsonl`) ので、**同じ分岐が
4 箇所に増え、1 つ書き忘れた場所だけが静かにデータを失う**。しかも旧キーは
`DefaultHasher` 由来なので、読み側の分岐を残す限り「rustc を上げたら読めなく
なる」性質を永久に抱え込む。改名なら 1 回で終わり、以後どの層も新しいキーだけを
見ればよい。

**層を知らない実装にしてある。** `~/.zaivern` を深さ 3 まで走査して、
名前 (拡張子を除いた語幹) が旧キーと一致するファイル / ディレクトリを
`rename` するだけ。置き場の形を知らないので、**将来キーで場所を決める層が
増えても自動的に面倒を見る**。

安全側の作り:

- **新しい名前が既にあれば何もしない。** 古い方も消さずに残す
  (利用者のデータを黙って捨てない。人が見て判断できる状態で置いておく)。
- **`rename` は原子的。** 複数インスタンスが同時に走っても、負けた側は
  「元が無い」/「先が在る」で失敗するだけで、壊れた中間状態にならない。
- **Windows の delete pending / `ACCESS_DENIED` (os error 5) は異常ではない。**
  誰かがそのファイルを開いている間は改名できないので、黙って諦めて次の起動で
  やり直す。ここで騒ぐと「いちばん使っているワークスペースだけ移行できない」
  形で表に出る。
- **別ワークスペースの入れ物 (16 桁 hex の名前) には降りない。**
  中身はすべてその持ち主のものなので旧キーの名前は構造上あり得ないし、
  `term_logs/<key>/` のように数千件になる置き場を読み切らずに済む。
- 走査するエントリ数に上限 (4096) を置く。

**呼ぶ場所。** `history::append` と `history::list_all` の入口で
`adopt_legacy_keys(cwd)` を呼ぶ (1 プロセス 1 ワークスペース 1 回)。
`workspace_key` 自身には入れない — あれは**キーを組み立てるたびに**
(リース台帳の 1 操作ごとに) 呼ばれる純関数で、そこにファイル操作を隠すと
テストが実 `~/.zaivern` を読むようにもなる。

**有効期限がある。** `legacy_workspace_key` が過去の値を再現できるのは
「データを書いた版と同じ `DefaultHasher` を持つ rustc でビルドされている間」
だけである。**移行を先送りするほど引き取れる保証が薄くなる**ので、今入れた。

## まだ揃っていないもの

`workspace_key` を通っていない、**別々に計算されている同種のキー**が残っている。
どれも同じフォルダに対して**違う値**になるので、寄せるまでは別々の置き場のままになる。

- `session.rs:228 workspace_hash` — `canonicalize` 後の **`Path` を** `DefaultHasher` に
  かける (こちらは文字列をかけていた)。`Path::hash` と `str::hash` は別の値を出すので、
  ドキュメントの「`history` と同じ流儀」は**事実ではない** (実測: 同じフォルダで
  `7d04257970e725eb` と `be6ef641440bbada`)。`term_logs/<hash>/` の置き場でもある。
- `session.rs:128 roots_hash` — ルート集合版。マルチルートは 1 本にできないので、
  「集合を `/` 区切りで繋いで `workspace_key` と同じ写像へ流す」形にするのが筋。
- `marks.rs:905 workspace_key` — `session.rs` と同じ流儀の私的な複製。
- `mesh.rs:446 short_hash` — 任意文字列版。コメントは「`history::workspace_key` と
  同じ流儀」と書いてあるが、こちらも `DefaultHasher`。

寄せるときは、**この文書の移行 (改名) をそれぞれの旧キーに対しても走らせること**。
`adopt_legacy_keys_in` は旧キーと新キーを引数で受ける形へ一般化すれば再利用できる。
