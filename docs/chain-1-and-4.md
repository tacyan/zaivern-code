# 鎖① と鎖④ — 未測定だった 2 本を実測する

[docs/conflict-zero.md](conflict-zero.md) §2 は、衝突を起こさせない 4 本の鎖のうち
**① (配る前の分割)** を「未測定」、**④ (共有面の自動解決)** を
「実装されたが、この合成リポジトリでは 1 件も吸収しなかった」と書いていた。
この文書はその 2 つを埋める。**測っていないものは書かない。減らなかったものは
減らなかったと書く。**

再現はコマンド 2 行:

```sh
cargo test --bin zai --no-run                 # ① のハーネスはテストバイナリを使う
tools/coordinator-bench.sh --seeds "20260812 20260813 20260814"
cargo build --bin zai                         # ④ のハーネスは出荷物の zai を使う
tools/shared-surface-bench.sh --writers "2 4 8"
```

計測環境: macOS 26.5.2 / git 2.47.1 / rustc 1.97.1 / `zai` 0.16.0 (debug) /
HEAD `85a350e`。日付 2026-08-12。

---

## 0. 先に結論

| | 結論 | 数字 |
|---|---|---|
| ① | **効く。ただし「同じファイルの中で編集が当たる」ときだけ。** | 22 → 0 ハンク (種 6 通りで 17〜22 → 0) |
| ① | **ゼロは作業量で買っている。** | 書けた担当 36 → 13〜17 パターン (36〜47%) |
| ① | 編集が当たらないなら**素の git がもとから 0 件** | `--edit spread` は 6 種すべて naive も 0 |
| ④ | **マーカを囲めば実物の共有面でも消える。** | `config.rs` 14 → **0** ハンク (8 人) |
| ④ | **`--auto` (マーカ無し) は 1 件も吸収しない。** | 14 → 14。ドライバは呼ばれている |
| ④ | **`src/features/` の「新規ファイルだけ」は 0 のまま。** | 全条件で 0 (ドライバは 1 度も起きない) |
| ④ | **衝突 0 でも正しいとは限らない。** | `keybinds.rs` は全条件で `NG(長さ)` (→ §2.5.1 で解消) |

**いちばん大事なのは最後の行**である。`[BindAction; N]` の `N` は
どの枝も「今の値 + 1」を書くので git は綺麗に通すが、実際の要素数とは合わない。
**「衝突ゼロ」と「正しい」は別の主張**で、混ぜたら嘘になる。

> **2026-08-12 追記**: この `NG(長さ)` は**構造を変えて潰した**。
> `keybinds::all_actions!` が長さを要素から数えるので、
> **人が数を書く場所そのものが無くなった**。同じハーネスで全条件 `OK`
> になったところまで §2.5.1 に実測を載せてある。
> 一方、**衝突数は 1 件も減っていない** (baseline / union-auto は今でも
> 3 / 7 件で衝突する) — 直したのは「衝突 0 なのに間違っている」であって、
> 「衝突が出る」ではない。この 2 つも混ぜないこと。

## 1. 鎖① — 配る前の分割 (`tools/coordinator-bench.sh`)

### 1.1 何を比べたか

| 段 | 中身 |
|---|---|
| `naive` | 分割を通さない。担当表をそのまま N 人へ round-robin で配る |
| `coord` | `Coordinator::try_assign` → 断られたら `overlap_reason_for` / `overlap_split_for` を通し、**重ならない部分だけ**配る |

どちらの段も同じ担当表・同じ種・同じ編集規則で、**実際にブランチを作って
`git merge`** する。担当表は種から決まる (MINSTD。awk の倍精度で誤差が出ない
乗数を選んである)。

`coordinator` は GUI からしか到達せず `zai` に CLI 入口が無いので、
ハーネスは `union::tests::merge_driver_helper` と同じ形で**テストバイナリ
自身**を呼ぶ (`coordinator::tests::assign_helper`)。名前がずれるとハーネスは
「0 件のテストが走った」で静かに緑になるので、
`coordinator::tests::assign_helper_name_matches_harness` が番人。

### 1.2 編集規則を 2 つ用意した理由

[conflict-zero.md](conflict-zero.md) §3.8.1 は「離した行域なら素の git が
もとから 0 件でマージする」を実測している。つまり**鎖① が衝突を減らすかどうかは
「同じファイルの中で編集が当たるか」に丸ごと依存する**。片方だけ載せると必ず
どちらかの嘘になるので、両方出す。

* `--edit same` … どの枝も同じ行 (要約行のような 1 点) を書き換える
* `--edit spread` … 各枝が自分の id から決まる別の行を書き換える

合成リポジトリの各行の中身は**すべて一意**にしてある。§3.16 の教訓
(周期的な内容だと diff がハンクを別の位置へ合わせるので行距離でハンク境界が
決まらない) の交絡を、最初から入れないため。

| 20260813 | naive | 9 | 17 | 17 | 55 | **6** | 12 | 0 | 0 | 36 |
| 20260813 | coord | **0** | **0** | **0** | **0** | **0** | 2 | 9 | 1 | 17 |
| 20260814 | naive | 9 | 18 | 18 | 58 | **7** | 12 | 0 | 0 | 36 |
| 20260814 | coord | **0** | **0** | **0** | **0** | **0** | 2 | 7 | 3 | 16 |

**6 種すべてで 17〜22 ハンク → 0 ハンク。**同時に、
**書けた担当は 36 パターン → 13〜17 パターン (36〜47%)** へ落ちている。
ゼロは「配り方を賢くした」だけで得られたのではなく、
**5 人ぶん前後の作業を後回しにして買っている**。

### 1.4 実測 — `--edit spread`

同じ担当表・同じ種で、編集する行だけを枝ごとにずらしたもの。

| 種 | 段 | ハンク | 二重 | 書込P |
|---|---|---:|---:|---:|
| 20260812 | naive | **0** | 8 | 36 |
| 20260812 | coord | 0 | 0 | 13 |
| 20260813 | naive | **0** | 6 | 36 |
| 20260813 | coord | 0 | 0 | 17 |
| 20260814 | naive | **0** | 7 | 36 |
| 20260814 | coord | 0 | 0 | 16 |
| 20260815 | naive | **0** | 9 | 36 |
| 20260815 | coord | 0 | 0 | 17 |
| 20260816 | naive | **0** | 8 | 36 |
| 20260816 | coord | 0 | 0 | 16 |
| 20260817 | naive | **0** | 10 | 36 |
| 20260817 | coord | 0 | 0 | 15 |

**6 種すべてで naive も 0 ハンク。**鎖① は 1 件も減らしていない。
それでいて **naive の「二重」は 6〜10 件**ある — 2 人が同じファイルを書いており、
たまたま行が当たっていないだけである。

これは [conflict-zero.md](conflict-zero.md) §3.8.1 の
「離した行域なら素の git がもとから 0 件でマージする」を、
**ファイル単位でも同じことが起きる**という形で裏付けている。
そして §6-3 の「互いに素な行域 ⇒ 綺麗にマージできる」が反証されたとおり、
**逆は言えない** — 内容が変われば同じ担当表が衝突しうる。

### 1.5 重なりを振る

`--overlap` は「ホットプール (先頭 1/4 のファイル) から引く確率」で、
重なりの量そのものではない。**12 タスク × 3 個 = 36 回の抽選を 24 ファイルへ
入れる以上、0.0 でも鳩の巣原理で必ず重なる**。本当に薄い条件を見たいなら
`--files` を広げる。`--edit same`・種 3 通り・各段の代表値:

| 条件 | naive ハンク | naive 二重 | coord ハンク | coord 書込P (36 中) |
|---|---:|---:|---:|---:|
| `--files 120 --overlap 0.0` (薄い) | 2〜4 | 2〜3 | **0** | **32〜34** |
| `--files 24 --overlap 0.0` | 13〜15 | 10 | **0** | 18〜20 |
| `--files 24 --overlap 0.5` | 17〜22 | 6〜10 | **0** | 13〜17 |
| `--files 24 --overlap 1.0` (全員が同じ 6 個) | **27** | 6 | **0** | **6** |

**混むほど、買う衝突ゼロの値段が上がる。** 全員が同じ 6 ファイルを取り合う
条件では、36 パターンのうち 6 しか配れない (拒否 8〜9 / 12 タスク)。
逆に薄い条件では 34/36 が配れて、それでも 0 になる。

[conflict-zero.md](conflict-zero.md) §1「意味しないこと」の 3 番
(「重なりが無い作業で 0 なのは当たり前」) と同じ構造が、
鎖① でもそのまま成り立つ。

### 1.6 ハーネスの費用

`naive` 段は「**同じプロセス起動・同じ担当表の解析・同じ出力で、
`Coordinator` を 1 度も作らない**」空回しである。時間は `--reps 9` の**最小値**
(平均や 1 点だと、同時に走る他の仕事で 1.3〜2.8 倍に散る — §3.14 で実測済み)。

| 段 | 判定 ms (6 種の幅) |
|---|---|
| `naive` (ハーネスの床) | 63〜80 |
| `coord` (床 + 判定) | 84〜102 |
| **判定の正味 (coord − naive)** | **+7 〜 +33** |
| **ハーネス率 (naive ÷ coord)** | **68〜92%** |

**測っている時間の 7 割前後はハーネス** (libtest バイナリのプロセス起動 +
担当表の解析) で、12 タスクぶんの `admit` / `overlap_reason` /
`overlap_split` の正味は **10〜30ms 台**である。

**この数字を「速い」の根拠には使わないこと。** 床が正味の 3〜9 倍あるので、
差の相対誤差が大きい。**言えるのは「判定は統合時間に対して無視できる」まで**で、
実際に 12 タスクの統合 (ブランチ作成 + マージ) はこの 20〜100 倍かかる。

差し引かずに `coord` の 84〜102ms をそのまま「配る前の分割の費用」と書くと、
**最大で 9 割が嘘**になる。CLAUDE.md が言う「ハーネスの費用を測って差し引く」の
実例がここでも出た。

### 1.7 判定関数が主張そのものを見ているか

§3.11.5 の事故 (`verdict_of()` が `conflict_files` だけを見て `dup_lines` を
見ていなかった) を踏まえ、このハーネスは**衝突数とは別に「配ったもの」を
そのまま保存して検査する**。

* `二重` = 2 つ以上の枝へ同じファイルを配った件数
* `coord` 段でこれが 0 でなければ、**衝突が 0 でもその段は失格** (rc=22)

この列があるおかげで `--edit spread` の naive 段が読める:
**衝突 0 なのに二重が 6〜10 件ある**。衝突だけを見ていたら「保護は要らない」と
読めてしまうが、実際には 2 人が同じファイルを書いており、
**編集の当たり方が変わった瞬間に壊れる**。

### 1.8 正直に書くこと

* **`coord` の 0 は「書かせない」ことで買っている。** 書けた担当は
  36 パターンから 13〜17 パターンへ落ちる。断られた担当を別のエージェントへ
  回したときに何回目で通るのかは、ここでも測っていない
  ([conflict-zero.md](conflict-zero.md) §5-5 のまま)。
* **`--agents` を減らすと様子が変わる。** 同じセッションへ渡す 2 タスクは
  重なってよい (`admit` の仕様) ので、セッション数を絞ると分割が減る。
  この表はセッション数 = タスク数 (最悪ケース) の数字である。
* **ファイル単位の粒度しか見ていない。** 行域 (鎖②') は
  [conflict-zero.md](conflict-zero.md) §3.8 の担当で、ここでは扱わない。

## 2. 鎖④ — 共有面の自動解決 (`tools/shared-surface-bench.sh`)

### 2.1 なぜ実物で測り直す必要があったか

* `tools/conflict-zero-bench.sh` の合成リポジトリは `let value = N;` の
  **書き換え**しかしないので union の守備範囲の外 (§3.7 の「効果ゼロ」)
* `tools/union-bench.sh` は共有面を**模した**フィクスチャで測る。形は似せて
  あるが、**本物の `src/config.rs` は 6900 行、`src/keybinds.rs` の配列は
  89 要素**という条件が落ちている

このハーネスは**このリポジトリ自身を複製して**、CLAUDE.md が名指ししている
共有面そのものへ N 本の枝が独立に追記する。

| 共有面 | 触る箇所 |
|---|---|
| `config` | `struct Config` へ 1 フィールド + `impl Default for Config` へ 1 行 (**2 箇所**) |
| `keybinds` | `enum BindAction` へ 1 variant + `ALL_ACTIONS` へ 1 行 (**2 箇所**)。一覧が手書き長の綴りなら **`[BindAction; N]` の N の書き換え**も足して **3 箇所** — 古いチェックアウトでも同じ穴を再現する (§2.5.1) |
| `features` | `src/features/bench_feat_<i>.rs` を**新規作成するだけ** |

**対象リポジトリは 1 バイトも汚さない** (`git clone --no-hardlinks` した複製の
側でしか作業しない)。差し込む行は**その場所の改行 (CRLF/LF) に合わせる**。

`tools/shared-surface-bench.sh --writers "2 4 8"`。
**2 回走らせて、件数の列は 1 つ残らず同じだった** (乱数を使わないので決定的。
違ったのは ms の列だけ)。

### ハーネスの費用 (差し引ける組と、差し引けない組)

**差し引ける**のは `baseline` と `union-auto` だけである。この 2 つは
**同じ 7 件の衝突を同じ規則で解決する**ので、差はドライバのプロセスぶんに
なる:

| 共有面 | 人数 | baseline (床) | union-auto | 差 | 駆動 1 回あたり |
|---|---:|---:|---:|---:|---:|
| config | 4 | 1163 | 2279 | 1116 | **372 ms** |
| config | 8 | 2715 | 4873 | 2158 | **308 ms** |
| keybinds | 4 | 880 | 1937 | 1057 | **352 ms** |
| keybinds | 8 | 2169 | 4156 | 1987 | **284 ms** |

**1 回あたり 284〜372ms を払って、ハンクは 1 つも減らない。**
(debug ビルドの `zai` を毎回プロセス起動している数字である。
release では別の値になるはずだが、**測っていないので書かない**。)

**差し引けない**のは `union-marked` である。衝突が 0 なので
「衝突を解決して commit し直す」段をそもそも通らず、**baseline と同じ仕事を
していない**。`union-marked` が baseline より速い (1935 対 2715) のは
ドライバが速いからではなく、**やる仕事が減ったから**である。
ここを引き算すると嘘になるので、引かない。

### 2.3 なぜ `--auto` は効かないのか

「ドライバが呼ばれていない (配管の失敗)」と「ドライバが自分で降りた (方針)」は
まったく別の話なので、ハーネスはドライバを小さな包み越しに起こして
**呼ばれた回数を数える**。実測では `union-auto` の駆動回数は衝突マージ回数と
同じ (8 人なら 7 回) なので、**配管は繋がっていて、ドライバが降りている**。

理由は `union::tests::実物の共有面で自動判定がどこまで届くか` に固定してある:

| 追記先 | 一覧に見えるか | 追記行が塊の内側か | `--auto` で解けるか |
|---|---|---|---|
| `struct Config` の末尾 (559 行目) | Bracket・79 塊 | **外側** | 解けない |
| `impl Default` の末尾 (1044 行目) | 同上 | 内側 | **解けない** |
| `enum BindAction` の末尾 (205 行目) | Bracket・15 塊 | **外側** | 解けない |
| `ALL_ACTIONS` の末尾 (298 行目) | 同上 | 内側 | **解ける** |

* `detect_flat` / `detect_bracket` の塊は**連続した宣言行**しか拾わない。
  実物の `struct Config` は末尾フィールドの直前に doc コメントと
  `#[serde(...)]` が挟まるので、**閉じ括弧の手前は塊の外**になる
* `impl Default` は塊の内側なのに解けない。
  **塊の内側であることは必要条件であって十分条件ではない**
* そして `cli_main` は**1 つでも衝突が残るとファイルごと git へ降りる**
  (`auto_only && res.has_conflict()`)。4 箇所のうち 1 箇所が解けても、
  **ベンチのハンク数は 1 つも減らない**

**これは失敗ではなく、安全側に倒した設計どおりの「解決しない」**である。
一覧に見えないファイルを勝手に両側マージすると、順序に意味があるコードを
黙って壊す。`--auto` が触らなければ結果は素の git と 1 バイトも変わらない。

### 2.4 マーカを囲めば実物でも消える

`union-marked` (`zaivern:union-begin` / `union-end` で囲んでから
`zai merge-driver`) は、**`config.rs` も `keybinds.rs` も 2/4/8 人すべてで
0 ハンク**になる。§3.7 の「効果ゼロ」は合成リポジトリの中身の問題であって、
**ドライバの限界ではなかった**。

### 2.5 それでも `keybinds.rs` は直らなかった (ここが肝)

> この節は **0.16.0 で `all_actions!` を入れる前**の観測である。
> 現在の形と実測は §2.5.1。ここは「union では原理的に直せない種類がある」
> という根拠として残す。

`keybinds` は**どの条件でも `NG(長さ)`** だった。

| 人数 | 宣言長 (`[BindAction; N]`) | あるべき要素数 | 衝突 (union-marked) |
|---:|---:|---:|---:|
| 2 | 90 | 91 | 0 |
| 4 | 90 | 93 | 0 |
| 8 | 90 | 97 | 0 |

* 各枝は `[BindAction; 89]` を `[BindAction; 90]` へ書き換える
* **両側が同じ 90 を書く**ので git は綺麗にマージする (衝突 0)
* しかし実際の要素数は 89 + N なので、**宣言長とずれる**

union は**追記を両方残す**ためのものであって、
**「一覧の長さを表す数」を足し算し直すことはできない**。
`ALL_ACTIONS` の追記そのものは (マーカがあれば) 全部残るのに、
ファイルはコンパイルできない。

**「衝突ゼロ」と「正しい」を混ぜてはいけない**という主張の、
このリポジトリ自身での実物の反例である。

### 2.5.1 直し方は「union を強くする」ではなく「数を書かせない」だった

union 側でどう頑張っても直らない。**両側が同じ `90` を書いた時点で、
残せる正解がどこにも無い**からである (union は「両側の追記を両方残す」
装置であって、数を足し算する装置ではない)。

そこで**書き手が数を書く場所そのものを消した** (`src/keybinds.rs`):

```rust
// 前: 一覧へ 1 行足す人が、必ずこの 89 を 90 へ書き換える
pub const ALL_ACTIONS: [BindAction; 89] = [ … ];

// 後: 長さは要素から数える。**人が書く数は 1 つも無い**
macro_rules! all_actions {
    ($($p:path),* $(,)?) => {
        pub const ALL_ACTIONS: [BindAction; [$(stringify!($p)),*].len()] = [$($p),*];
    };
}
all_actions![ … ];
```

**同じハーネス・同じ条件での前後**
(`tools/shared-surface-bench.sh --surfaces keybinds --writers "4 8"`):

| 人数 | 条件 | 衝突F | 前: 宣言長 / あるべき | 前 | 後: 数えた数 / あるべき | 後 |
|---:|---|---:|---:|---|---:|---|
| 4 | baseline | 3 | 90 / 93 | **NG(長さ)** | 93 / 93 | **OK** |
| 4 | union-auto | 3 | 90 / 93 | **NG(長さ)** | 93 / 93 | **OK** |
| 4 | union-marked | **0** | 90 / 93 | **NG(長さ)** | 93 / 93 | **OK** |
| 8 | baseline | 7 | 90 / 97 | **NG(長さ)** | 97 / 97 | **OK** |
| 8 | union-auto | 7 | 90 / 97 | **NG(長さ)** | 97 / 97 | **OK** |
| 8 | union-marked | **0** | 90 / 97 | **NG(長さ)** | 97 / 97 | **OK** |

**衝突数は 1 件も変わっていない。** 直したのは「衝突 0 なのに間違っている」
という一群だけで、`baseline` / `union-auto` が衝突すること自体は前のままである。
`union-marked` の行が「衝突 0 かつ検算 OK」になったのが、この変更の中身。

#### 判定を緩めて OK にしたのではない

「直したから見ない」にしないため、ハーネスは**同じ性質を見続ける**:

* `counted` の綴りでは `kb_len` が `all_actions![ … ];` の中の要素を
  **実際に数え**、`元の数 + 残った追記` と突き合わせる。
  要素が落ちても二重に入っても今までどおり `NG(長さ)` になる
  (むしろ `BenchAct*` だけを数えていた前より広く見ている —
  **元からある 89 件のどれかが落ちても捕まる**)
* 手書き長が復活したら `NG(手書き長が復活)`。
  この検査は**実際に 1 度発火した** — 上のコード例を説明する散文が
  `[BindAction; 89]` と書いていたのを拾ったためで、
  行コメントを落としてから見るよう直した (§4 の作法どおり)
* 古いチェックアウトや他リポジトリでは `handwritten` として認識し、
  **N の書き換えごと再現して `NG(長さ)` を出す**。穴の再現能力は残してある

#### なぜ `&[BindAction]` にしなかったか

長さは同じく消えるが、`for a in ALL_ACTIONS` の要素型が
`BindAction` から `&BindAction` へ変わり、`app.rs` / `jump.rs` /
`whichkey.rs` / `tutorial.rs` / `marks.rs` の **20 箇所超**を書き換えることになる。
それらは今まさに別の枝が触っているファイルなので、
**長さのずれを、他の枝とのマージ衝突へ交換するだけ**になる。
`[BindAction; N]` のまま長さだけを const 評価で数えれば、
**呼び出し側は 1 行も変わらない** (実測: `cargo test --bin zai` の追従 0 件)。

`enum BindAction` ごとマクロへ畳んで追記点を 2 → 1 にする案も採らなかった。
**追記点が 2 つあること自体は問題ではない** — 同じハーネスで `config` 面
(struct + `Default` の 2 箇所) は全条件 `OK` である。壊れていたのは
手で数えた長さだけなので、そこだけ直す。

#### 同じ種を二度と生やさせない

`src/union.rs` の `handcounted_len` に番人を 4 件置いた
(union が原理的に直せない種類なので、union の隣に置くのが正しい):

1. 検出器そのものを表で固定する (拾うもの / 拾わないものの**両方**)
2. `keybinds.rs` のコード中に `[BindAction; N]` が戻っていない
3. 共有追記面 (`keybinds.rs` / `config.rs` / `feature.rs` / `features/`) に
   手書き長が 1 つも無い
4. `src/` 全体の **module 直下**の手書き長は既知の 14 件だけ。
   増えたら落ちるし、**既知が消えても落ちる** (番人が空回りしない)

誤検出を出さないため、対象は
**「module 直下 (字下げ無し) の `const` / `static` で、複数行リテラルで、
長さが 10 進リテラル」**に絞ってある。
1 行で書いた配列 (`const UNITS: [&str; 5] = ["B", …];`) は、要素を足すと
**その行の書き換え**になるので git が必ず衝突を出す = 静かには壊れない。
関数の中の `let` / `const` も、1 つの関数に閉じているので独立追記の面にならない。

導入前に**番人が実際に落ちること**を確認してある
(4 件中 3 件が赤・検出器の自己検査だけ緑 = 検出器が壊れているのではなく
対象が本当に居る、と区別できる状態)。

### 2.6 いちばん強かったのは構造だった

`features` は**全条件・全人数で衝突 0 / 検算 OK / ドライバの駆動 0 回**。
`build.rs` が `src/features/*.rs` を走査して `mod` 宣言を `OUT_DIR` へ
生成するので、機能を足しても**共有ファイルを 1 バイトも触らない**。

マージドライバは共有面の傷を縫うが、**傷を作らない構造には勝てない**。
CLAUDE.md の「新しい機能は `src/features/<名前>.rs` を新規作成するだけで足す」は、
ここで数字として裏が取れた。

### 2.7 正直に書くこと

* **`config.rs` と `keybinds.rs` にマーカは入っていない。** `union-marked` の
  0 ハンクは「入れたらこうなる」という数字であって、いまの HEAD の性質ではない
* **`--whole` は測っていない。** 6900 行のファイル全体を union 対象にする
  条件は、壊し方が読めないので今回は試していない
* **コンパイルは通していない。** 検算は行の数え上げまでで、
  `cargo check` までは回していない (N 本ぶんのビルドが要るため)
* **`src/features/` の登録は「新規ファイルだけ」の理想形で測った。**
  実際には打鍵が要る機能が `keybinds.rs` へ、設定を持つ機能が `config.rs` へ
  追記する。CLAUDE.md が「ゼロにできていない共有面が 2 つ残る」と書いている
  とおりで、この表はその 2 つの費用がいくらかを示したものである

## 3. 残っている穴

1. **断られた担当の再投入は測っていない。** ①のゼロは書き込みを断って買って
   いる (書けた担当 36 → 13〜17)。回した先で何回目に通るのかは 1 つも数字が無い。
2. **`--auto` を実物へ届かせる案は試していない。** 塊の判定を
   「閉じ括弧の直前まで伸ばす」等は、誤自動解決の危険と引き換えなので
   別途測ってからでないと入れられない。
3. ~~**固定長配列の長さを足し算する仕組みが無い。**~~ → **塞いだ** (§2.5.1)。
   union を強くするのではなく `keybinds::all_actions!` で
   **人が数を書く場所を消した**。ただし**同じ種はまだ 14 箇所ある** —
   `src/union.rs` の `handcounted_len::module直下の手書き長は既知の分だけ`
   に一覧と理由が載っている。中でも `terminal.rs` の
   `MENU_KEYS` / `MENU_DESC_ALLOW` / `MENU_DESC_SKIP` / `MENU_DESC_RATING` は
   **添字で対応する 4 本の並行配列**なので、長さが揃っていても
   *対応がずれる*ぶんはコンパイラが何も言わない。
   こちらは「衝突 0 で、しかも**実行時まで静かな**」より悪い形になりうる。
4. **Linux / Windows で測り直していない。** どちらのハーネスも
   macOS でしか回していない。

## 4. ハーネスの作法 (`docs/bench-honesty.md` に従っている点)

* `# @zai-honesty-begin` 〜 `# @zai-honesty-end` の共通ブロックを
  **1 バイトも変えずに**貼ってある (両ハーネスとも)
* `zai` / テストバイナリは**版とソース mtime**の両方で照合し、
  古ければ理由と直し方を出して降りる (`exit 20`)
* **測る前に能力検査**を通す。①は「同じファイルを 2 タスクが要求したら
  naive は両方配り coord は割る」、④は「`merge-driver --auto` が
  両側の追記を残す」。落ちたら「測った」と言わずに `exit 21`
* `HOME` と `ZAIVERN_HOME` を一時ディレクトリへ向けるので、
  **本物の `~/.zaivern` と `~/.gitconfig` に 1 バイトも触らない**
* `| head` / `| tail` の後ろで `$?` を見ている箇所は 1 つも無い

### 作業中に踏んだ罠 (対策に含めた)

**`target/debug/deps/zai-<hash>` には素の `zai` 実行ファイルも入っている。**
cargo は bin ターゲットもここへ置き、`target/debug/zai` はそこへのハードリンク
である。`zai` は**知らない語をワークスペース指定として扱う**ので、
候補を新しい順に見て `zai --list` を撃った瞬間に **GUI の窓が開いて永久に
返ってこなくなった** (実際にこのハーネスが固まった。
`cargo build --bin zai` を走らせた直後だけ、素の実行ファイルのほうが
テストバイナリより新しくなるので先に当たる)。

対策は `cmp -s` で `target/{debug,release}/zai` と中身が同じ候補を先に外すこと。
`cmp` は POSIX にあり、ハードリンクでもコピーでも同じ判定になる。
**飛ばした候補には理由を書き残す** (`docs/bench-honesty.md` の
「選ばれなかった候補にも記録を残す」と同じ理由)。

なお §1 の数字はこの罠の**前**に取ったもので、出力の先頭に載っている
テストバイナリのパス (`zai-9bca2fcdf4883164`) がそれを示している。
素の実行ファイルを掴んだ実行は 1 度も表に入っていない。
