# どのリポジトリでも競合が起きない — を、**利用者自身のリポジトリ**で証明する

`tools/anyrepo-prove.sh`

## なぜ要るのか

`tools/conflict-zero-bench.sh` と `tools/coedit-bench.sh` は、その場で作った
**合成リポジトリ**でしか測っていない。48 個の同じ形をした `src/mod_%04d.rs` は、
行数も言語構成も履歴も現実には存在しない。だから出てくる数字は
「**この合成物では**効く」までしか言えず、「**どの**リポジトリでも」という
主張の裏付けにはならない。

このハーネスは逆から入る。**利用者が自分のリポジトリのパスを渡す**と、
その実在のファイル・実在のサイズ・実在の言語構成・`git log` から出した
実在のホットスポットを使って、同じ担当表を 2 回流す。

```
tools/anyrepo-prove.sh                                  カレントのリポジトリ
tools/anyrepo-prove.sh --repo ~/dev/foo --writers 8,16,32,64
tools/anyrepo-prove.sh --repo ~/dev/foo --json           JSON は stdout、表は stderr
tools/anyrepo-prove.sh --shapes                          形ごとの可否を実測
tools/anyrepo-prove.sh --help
```

終了コードは **0 = 証明できた / 1 = 証明できなかった (理由を出す) / 2 = 使い方の誤り**。

## 何と何を比べているのか

| 段 | 中身 |
|---|---|
| ベースライン | 何もしない。N 体が worktree に分かれて同時に書き、作成順に直列マージ |
| zaivern あり | **1 バイト同じ担当表**を、`zai lease claim --shift` の予約と `zai hook` のゲートを通してから書く |

違うのは「書く前に予約とゲートを通すか」の 1 点だけ。ここに差を混ぜると A/B が
意味を失うので、編集の適用コードは両段で共有している。

編集は「選んだ行の**末尾に目印を足す**」だけ。言語に依らず、意味も持たない
(ビルドはしない)。大事なのは「同じ行を 2 人が触れば git が必ず衝突させる」ことだけ。

### 重なりは「行」まで作る

`--overlap` はファイルの重なりだけでなく、**行域の重なり**も作る
(`--hot-blocks`、既定 3)。ファイル単位で重ねても行が離れれば git は衝突させないので、
ここを重ねないとベースラインが不自然にゼロになり、A/B が意味を失う。

そして「重なった」の一次データは**行単位**で数える。行域 (ブロック) 単位で数えると
`--shift` が同じブロック内の別の行へずらしただけで「重なった」と出る
(実測: ブロック単位 5 件 → 行単位 0 件)。守っている性質は「同じ行を 2 人が書かない」
なので、そのまま行で数える。

## 「証明」と名乗る前に必ず通す能力検査

検査を省くと「全員書けて衝突 0」という**静かな嘘**が出る。実際に
`docs/conflict-zero.md` の計測では、能力検査を入れたことで (1) CLI が retry 版の
ロックを使っておらず 64 体中 18 体しか通らない (2) EOF を超える予約が縮んで
2 つの担当が重なる (3) `--shift` が CLI へ届いていない、の 3 件が見つかっている。

| | 検査 | なぜ要るか |
|---|---|---|
| V1 | `zai --version` と `Cargo.toml` の照合 | **古い `zai` は知らないサブコマンドをワークスペース指定として扱い、GUI を起こして落ちる**。`cargo test --bin zai` は bin を作らないので `target/*/zai` は前の実行の残骸かもしれない |
| V2 | `zai help` に `zai lease` / `zai hook` があるか | help に載っていない語を投げない = 上の事故を構造的に避ける |
| V3 | 重なる 2 本の行域予約が**断られる**か / 離れた 2 本は通るか | 0.13.0 は `a.rs#L1-10` を**ただの文字列**として飲んでいた。保護が 1 つも無いのに rc=0 で返る |
| V4a | `--shift` が最後の行に `granted <仕様>` を出し、既存と重ならない所へずらすか | 0.13.0 は**知らないフラグを黙って確保パターンとして飲む**。rc=0 なのにずらしていない |
| V5 | ゲートが「自分の域は通す / 他人の域は止める / 空き域は通す」か | 名前が近いだけの別経路を当てると**止めていないのに緑に見える** |
| V6 | 対象リポジトリの指紋が前後で変わっていないか | 下記 |
| V7 | 実行ファイルの素性 (`touch` 耐性) | **V1 の版照合も mtime の鮮度判定も `touch` 1 回で破れる**。下記 |

必須は **V1 / V2 / V3 / V5 / V7**。V4a (交渉) は「あれば強い」であって、無くても
「要求どおりか拒否か」で測定は成立する。**1 つでも落ちたら結論を「証明できず」に
落として理由を出す** (数字自体は出す — 隠すと次に何を直せばいいか判らなくなる)。

## 「証明できた」と言える条件 — **出力の先頭に必ず出す**

結論だけを持ち帰られても誤解されないよう、条件そのものを毎回先頭へ出す。
文章で書くと実装とずれるので、**判定に使う値そのもの**を並べてある
(表の `[OK]/[NG]` 行と JSON の `criteria` / `checks` は同じ一次データ)。

| | 条件 |
|---|---|
| C1 | ベースラインで実際に衝突が出た (出なければ A/B に意味がない) |
| C2 | zaivern あり: **2 体以上が同じ行を書いた数が 0** |
| C3 | zaivern あり: git のマージで衝突したファイルが 0 |
| C4 | zaivern あり: zai 呼び出しのタイムアウトが 0 |
| C5 | ハーネスの編集が目印 1 つの追加だけ (改行・エンコードを壊していない) |
| C6 | 能力検査 (V1/V2/V3/V5/V7) が全部 OK |
| C7 | 対象リポジトリの指紋が前後で同一 |

**C2 と C3 は別物である。** 「git が衝突と呼ばなかった」ことは
「2 体が同じ行を書かなかった」ことを意味しない (同じ行への 2 つの編集が
偶然同じ文字列になれば git は黙る)。所有の保証はこの製品の中核の主張なので、
**C2 が破れた時点で、衝突が 0 でも証明は失敗**とする。

**測っていないもの**も同じ場所へ出す: 編集後にビルドが通るか / 編集の意味的な
正しさ / マージ順序の全通り / 実在のエージェント (書き手はハーネスのスレッド) /
改行以外のファイル属性 (mode・symlink・submodule・LFS の中身) /
`--scan-cap` で間引いた標本の外。

## 改行コードとエンコードを 1 バイトも変えない

編集はすべて**バイト列**で読み書きする。CRLF の行は末尾の `\r` の**手前**へ
目印を入れるので、その行の改行も CRLF のまま残る。BOM・混在改行・非 UTF-8
(Shift_JIS 等) も同じ理由で通る。標本を選ぶ判定も UTF-8 を要求しない
(git 自身の判定と同じく「NUL があるか」で見る)。

**これは机上の配慮ではなく、実際に証明を偽にしていた欠陥である。**
以前は Python の `open()` を汎用改行のまま使っていたので、CRLF のファイルを
読んだ時点で LF へ畳み、書き戻すと**そのファイルが 1 行残らず書き換わって**
どの段でも必ず衝突した。ある実在リポジトリの失敗 5 件は**すべてその 4 つの
CRLF ファイル**が原因で、LF へ正規化した複製では 8 通りの設定すべてが衝突 0 だった。
**Windows 由来のリポジトリは、守られているのに「証明できず」と言われていた。**

再現と検証 (CRLF 20 / LF 20・BOM 1 件・Shift_JIS 1 件の複製、8 体・`--overlap 1.0`):

| | 重なった行 | 衝突ファイル | 結論 |
|---|---|---|---|
| 直す前 | 0 | **26** | 証明できず |
| 直した後 | 0 | **0** | **証明できた** |

口約束にしないため、**1 件の編集ごとに「目印 1 つの追加だけか」を突き合わせる**
(C5)。ここが 1 件でも破れたら、測定器の側が壊れているとして結果を捨てる。

## V7 — `touch` 1 回で破れる関所を塞ぐ

`zai` の選定は「版が一致し、ソースより新しい」で篩っている。この 2 つは
**中身の違うバイナリを 1 件も捕まえられない**ことがある:

* 版は `Cargo.toml` を上げない限り同じ文字列のまま
* mtime は `touch target/debug/zai` で更新できる

実演では、`Stale` として弾かれた実行ファイルが `touch` 1 回で受け入れられ、
ハーネスは **「証明できた」と出した**。

V7 は、実行ファイルの隣へ
`(実行ファイルの同一性, ソースの内容ハッシュ, 判定)` を書き残して塞ぐ。
同一性は `touch` で動かないもの (unix: dev+inode+サイズ / Windows: 作成時刻+サイズ)。

* 同じ実行ファイル・同じソース内容 → **前回の判定を繰り返す** (`touch` が効かない)
* 同じ実行ファイルなのにソースの内容が変わった → 無条件に古い
* **選ばれなかった候補にも記録を残す**。弾かれた実行ファイルにこそ
  「stale だった」と書かないと、`touch` された次の回に素通りする

費用は**ソース 130 ファイル / 12.5MB の sha256 で中央値 63.4 ms**
(51.9〜67.6 ms。ビルドと同時に走らせると 188〜1106 ms まで伸びる)、
1 回の実行につき 1 回。
**弱点も出力に書く**: 記録が 1 つも無い初回だけは mtime しか手掛かりが無い。
ここを閉じるには `build.rs` でソースのハッシュをバイナリへ焼き込むしかない
(担当ファイルの外)。詳細は `docs/bench-honesty.md`。

## 対象リポジトリを絶対に汚さない

* 実験は必ず `git clone --local --no-hardlinks` した**複製**の上。
  `--no-hardlinks` は速さより安全を選んだ結果 (ハードリンクでも git は
  オブジェクトを書き換えないが、証明の道具が元と何も共有していないことを自明にしたい)
* `HOME` を一時ディレクトリへ差し替えるので、本物の `~/.zaivern` と `~/.gitconfig`
  にも触らない
* 指紋 = HEAD / 全 ref / 作業ツリーの状態 / オブジェクト数 / worktree 一覧 / ローカル設定。
  読むだけの `git status` が索引を書き戻して**偽陽性**を出さないよう、指紋を取る git は
  すべて `--no-optional-locks` を通す
* **指紋はハッシュだけでなく「数」も持つ** (ref 何本 / status 何行 / worktree 何個 /
  loose object 何個)。ハッシュだけだと「変わった」としか言えず、
  利用者が「何がどれだけ動いたか」を追えない。V6 が赤いときは
  `worktrees 3 個 abcd → 4 個 ef01` のように前後を並べて出す
* **cargo を 1 度も呼ばない。** 既にある `zai` を使うだけで、ホストの `target/` は
  1 バイトも触らない
* 統合が済んだ worktree は**その場で消す** (1 つあたり独立した checkout を持つので、
  64 体 × 2 段 × 4 サイズを放置するとページキャッシュが押し出される)

**既知の偽陽性**: 対象リポジトリを**別のプロセスが同時に編集している**と、
指紋の `status` が動いて V6 が赤くなる。ハーネスは書いていないので、
この場合は「誰が触ったか」を先に確かめること。

## リポジトリの形ごとの可否 (`--shapes` の実測結果)

説明ではなく**その場で実物を作って通した**結果 (git 2.47.1 / macOS)。
`tools/anyrepo-prove.sh --shapes --writers 4 --overlap 1.0` で再現できる。

| 形 | 可否 | 注記 |
|---|---|---|
| 普通のリポジトリ | ○ | |
| bare | ○ | 作業ツリーは複製側で作られる |
| 連結 worktree の中 | ○ | 複製は共有リポジトリ側の既定ブランチから |
| shallow clone | ○ | 履歴が浅いので churn の情報が乏しい (ホットスポットは大きさ順へ寄る) |
| 履歴が 1 コミットだけ | ○ | 同上 |
| detached HEAD | ○ | 複製されるのは**既定ブランチ**。今の detached な位置ではない |
| 未コミットの変更あり | ○ | **未コミットの変更は複製に入らない** (git clone はコミット済みだけを運ぶ) |
| sparse-checkout | ○ | 複製は全ファイルを持つ (sparse は作業ツリー側の設定) |
| submodule あり | ○ | **サブモジュールは初期化しない**。親のファイルだけで測る |
| LFS | ○ | ポインタのまま扱う (`GIT_LFS_SKIP_SMUDGE=1`)。実体は引きに行かない |
| 巨大 (追跡 4200 件 > `--scan-cap` 4000) | ○ | **全件は調べない**。種で決まる等間隔の間引きで 4000 件だけ標本に取る |
| コミットが 0 件 | **skip** | 複製しても比べる基点がない |
| 非 git ディレクトリ | **skip** | 複製と直列マージで衝突を数えるので git が要る |

skip は 2 つだけで、どちらも**理由を明記して続行**する (黙って飛ばさない)。

**「巨大」の閾値は外から持ってこない。** 「10 万件なら巨大」のような数字は
`--scan-cap` を変えた瞬間に嘘になるので、閾値は「調べ切れる件数」そのもの
(`--scan-cap`) にしてある。

## 実測 (macOS 26 / git 2.47.1 / zai 0.14.0 / 既定の種)

同じ担当表を両段へ流した結果。`--overlap` は既定の 0.5。

| リポジトリ | 性質 | 書き手 | ベースライン 衝突ファイル/ハンク | zaivern あり | 予約 |
|---|---|---|---|---|---|
| `zaivern-code` | Rust 主体・追跡 259 件・594 コミット | 8 | **9 / 11** | **0 / 0** | 48/48 成立 (12 件ずらした・拒否 0) |
| | | 16 | **26 / 28** | **0 / 0** | 96/96 成立 (30 件ずらした・拒否 0) |
| `hyperframes` | TypeScript/HTML 主体・追跡 1194 件・575 コミット | 8 | **9 / 11** | 0 / 0 (**8 回中 3 回は 1 / 1**) | 48/48 成立 (7〜14 件ずらした・拒否 0) |
| | | 16 | **26 / 28** | **0 / 0** | 96/96 成立 (32 件ずらした・拒否 0) |
| 合成 (24 ファイル × 121 行) | `--overlap 1.0` | 32 | **118 / 147** | **0 / 0** | 192/192 成立 (171 件ずらした・拒否 0) |

**`予定 = 適用` がすべての行で成り立っている**ことに注意。誰も断られていない
(`--shift` が「断らずにずらす」ので、混んでいても諦めない)。
「半分が断られて衝突 0」ではない。

能力検査は 5 件すべて OK (V1 版一致 0.14.0 / V2 導線あり / V3 重なる予約を断る /
V4a `--shift` が `granted` を返しずらす / V5 ゲートが他人の域だけ止める)。
**V7 はこの計測より後に足した**ので、上の表には含まれていない。

### V6 が赤くなった実例と、その切り分け

`zaivern-code` の**連結 worktree**を対象にした 2 回の実行で V6 が赤くなり、
`objects` / `refs` / `worktrees` が変わったと出た。これは**別のエージェントが
同じリポジトリへ同時にコミットしていた**ためで (実測: 実行中の 05:44 と 05:45 に
別ブランチのコミットが 2 本増えた)、ハーネスの書き込みではない。

裏取りとして、**同じリポジトリを静かな複製へ取ってから**同じ測定をした:

* 衝突数は 1 件も変わらない (8 体 9/11 → 0/0、16 体 26/28 → 0/0)
* **V6 は緑**、終了コード 0

つまりハーネスは複製しか書いていない。V6 が赤いときは、まず
「対象リポジトリを同時に触っているプロセス」を疑うこと (ツールもその旨を出す)。

## 読み方の注意

* **`予定` と `適用` の差を必ず見る。** `--shift` が無い (または `--no-shift`) と、
  混んだ行域を頼んだ書き手は断られて `適用` が落ちる。衝突 0 は同じでも
  「全員書けて 0」と「半分が断られて 0」はまったく違う結果である
* **`台帳の整合`**: 別々の持ち主へ重なる行域が配られていないかを、段の終わりに
  `zai lease list --json` から検算する。衝突が残ったときに
  (a) zaivern が二重に配った のか (b) 予約の外へ書かれた のかを分ける。
  ここを分けないと、赤が出たときに製品とハーネスのどちらを直すか永久に決まらない
* **`--trace <パス>`**: 予約・許可・書き込みを 1 行 1 件の JSONL で書き出す。
  「証明できず」と出たときに原因へ辿れる唯一の記録
* 時間 (`p50` / `p95`) は**判定に使っていない**。絶対時間で線を引くと必ず嘘の赤が出る。
  判定は件数と比率だけで行う

## 未解決 (正直に残す)

実在リポジトリ (`hyperframes`: TypeScript 主体 / 追跡 1194 件 / 575 コミット) の
8 体・既定種で、**予約を取ったはずの 2 体が同じ行を書いた**ケースを観測した。

**この形はいま C2 が無条件に落とす。** かつての `verdict_of()` は
`conflict_files` しか見ておらず、同じ行に 2 体が載っても git がたまたま
衝突と呼ばなければ `proved` と出していた (再現: `dup=2, conf=0` で
直す前は `proved`、直した後は `unproved` + `C2=NG`)。
`--trace` の記録では `packages/producer/package.json` の L9 が w3 (76.303s) と
w5 (76.889s) の**両方へ granted されて**いる (0.59 秒差なので単なる同時実行の
競り合いではない)。

**頻度は珍しくない**: 同じ条件を 8 回繰り返して **3 回**再現した (種を変えた
3 通り — 既定 / 7 / 99 — では 1 度も出ず、同じ種でも出たり出なかったりする)。
落ちるのはいつも同じ 1 行 (`packages/producer/package.json:9`) で、
衝突ファイルは 1 件・ハンク 1 件。16 体では出ていない。

**最後の台帳には重なりが無い。** 落ちた実行でも
「別々の持ち主へ重なって配られたもの 0 件」と出る。つまり w3 の L9 は
**途中で台帳から消えている** (消えたから重ならない) 疑いが濃い。

同じ条件を切り出した最小再現は**すべて緑**だった:

* 逐次 6 体の `--shift` 連打 — 重複なし
* 並列 8 体 × 6 巡の `--shift` + 書き込み — 重複なし
* 上にゲート (`zai hook`) を足したもの — 重複なし
* 持ち主が自分の域を書いた後に他人が同じ行を要求 — 断られる
* 持ち主が自分の域を書いた**後にもう 1 件 claim** してから他人が要求 — 断られる
* 行の中身が重複するファイル (`  },` が 6 回出る実在の package.json) / 一意な行の
  ファイル — どちらも重複なし

その後の 3 種の種 (既定 / 7 / 99) と繰り返しでは再現しなかったため、
**間欠的で、複数ファイルにまたがる実負荷でしか出ない**とみられる。
このハーネスが無ければ観測できなかった種類の欠陥で、
`台帳の整合` の行が「どちら側の問題か」を次に切り分ける手掛かりになる。

なお `zai lease list --json` の `anchors` は CLI 経由の予約では
`{"head":"","tail":"","len":0}` (= 空) だった。行番号だけで持っている状態なので、
他人が上の行に行を**挿入**すると担当がずれる。この経路で錨を打たない理由が
設計上のものか漏れかは、このハーネスの守備範囲外。
