# リポジトリ形態ごとに、競合ゼロは何を保証するのか

`zai czero doctor` が検出するリポジトリ形態と、**その形で何が保証され、何が
保証されないか**の一覧。実装は `src/czero_init.rs` の `Shape` / `read_shape` /
`check_shape`、機械の読み手向けは `czero doctor --json` の `shape` 欄。

## なぜこの文書が要るのか

「どのリポジトリでも競合が起きない」は、**普通の作業ツリーなら**という前提が
隠れた主張だった。台帳・git フック・merge driver・`.gitattributes` の 4 段が
全部緑でも、sparse-checkout で作業ツリーに無いパス、LFS のポインタ、
submodule の中、bare リポジトリは、**4 段の外側にあって緑のまま素通りする**。

`czero` の判定は「判らないものを緑にしない」を守っている。この文書は
その裏返しで、**「未検証」を「安全」と書かない**ための対応表である。

## 守りの 4 段が、それぞれ何に依存しているか

| 段 | 実体 | 効く範囲 |
| --- | --- | --- |
| 行域の台帳 | `~/.zaivern/leases/<キー>.json` | キーは**本体リポジトリの実パス** (`lease::roots_of`)。git が要らない |
| git フック | `pre-commit` / `pre-applypatch` / `pre-merge-commit` | `git rev-parse --git-path hooks` が指す場所。**その git ディレクトリを共有するツリー全部** |
| merge driver | `.git/config` の `merge.zaivern-union*.driver` | `--local` なので**共有 git ディレクトリ単位** |
| `.gitattributes` | 作業ツリーの頂点 1 枚 | git の属性解決 (`git check-attr`) に従う |

**フックと driver は「共有 git ディレクトリ」単位、`.gitattributes` は
「作業ツリー」単位**という差が、下の表のほとんどの理由になっている。

## 形態ごとの対応表

### 素の作業ツリー — ✅

保証される: このツリーのコミットは全部フックを通る。一覧への両側追記は
union driver が解決する。同じファイルでも離れた行なら 2 人が同時に持てる。

保証されない: 何もない (`czero verify` が実際に起こして確かめられる唯一の形)。

### 非 git ディレクトリ — ❌ (`doctor` はエラーにせず説明する)

**片方だけが動くので、いちばん誤解される形。**

- `zai lease claim` は**成功する**。`lease::roots_of` は `.git` を持つ祖先が
  見つからないとカレントを台帳のキーにするため (`src/lease.rs` の `roots_raw`)。
- `zai czero init` は**失敗する**。`git rev-parse --show-toplevel` を要求するため。

つまり **台帳に自分から参加したエージェントだけは互いの行域を避けるが、
強制は 1 つも無い**。人間の `git commit` も、台帳を知らないエージェントも、
1 つも止まらない。`czero doctor` はこの非対称をそのまま出す。

直し方: `git init` するか、`--repo` で git リポジトリを指す。強制が要らない
（同意ベースで足りる）なら `zai lease list` で台帳だけを見る。

### bare リポジトリ — ❌

保証される: `clone` した作業ツリー側で `czero init` を打てば、そちらは守られる。

保証されない: bare には作業ツリーが無いので `.gitattributes` を置けず、
`pre-commit` も発火しない (誰もそこでコミットしない)。**bare 自体を守る意味が
無い**ので `init` は入らない。

### linked worktree (`git worktree add`) — ✅

保証される: フックと driver は共有 git ディレクトリに入るので、**本体と
他の worktree にも同時に効く**。台帳のキーも `.git` ポインタを辿って本体へ
寄るので、worktree をまたいだ行域の取り合いを検出できる。

保証されない: `.gitattributes` は**そのツリーの頂点 1 枚**なので、
別ブランチをチェックアウトしている worktree では中身が違うことがある
(git の通常の挙動どおり)。

### submodule — ⚠

保証される: 実行した側のリポジトリ (親なら親、submodule 内なら submodule)。

保証されない: **反対側**。submodule は別リポジトリで、独自の
`.git/config`・独自のフック置き場 (`.git/modules/<名>/hooks`) を持つ。
親で `czero init` しても submodule 内のコミットは素通りする。逆も同じ。

直し方: `zai czero init --repo <submodule のパス>` を submodule ごとに。

### sparse-checkout — ⚠

保証される: 台帳とフックは**stage されたパス**を見るので、cone の中は
普通どおりに守られる。cone の外のファイルはそもそも stage されない。

保証されない: `.gitattributes` の側。cone の外にある `.gitattributes` は
作業ツリーに無く、`czero init` が書くのも頂点の 1 枚だけ。**cone を後から
広げると、そこだけ union が当たらない**ことがある。広げたら `doctor` を
打ち直すこと。

### shallow clone — ⚠

保証される: フックと台帳 (履歴を見ないので影響なし)。

保証されない: `git merge-tree --write-tree` は共通祖先が要るので、
切り落とされた履歴に共通祖先がある組では失敗し、`coedit` の一撃統合が
縮退する。`git fetch --unshallow` で戻る。

### git-lfs — ✅ / ❌ (書き方による)

`git lfs track` が置く行は `filter=lfs diff=lfs merge=lfs -text` で、
**`merge` が埋まっている**。`czero` は既存の `merge` 指定があるパターンを
必ず避けるので、通常は安全側に倒れる (✅)。

危ないのは `filter=lfs` だけを手で書いた `.gitattributes` (❌)。`merge` が
空きに見えるので union が当たり、**union はポインタ行を連結する**ので、
その組で衝突が起きた瞬間に LFS オブジェクトが壊れる。`doctor` はこの組
(`filter` が `lfs` かつ `merge` が空き) を名指しで ❌ にする。

### `core.hooksPath` が既に別の場所を指している — ⚠

保証される: `czero` は `git rev-parse --git-path hooks` で**git 自身に
訊く**ので、husky の `.husky` のような置き場へ正しく入る。既に居るフックは
`<名前>.zaivern-prev` へ退避して**連鎖**する (上書きしない)。

保証されない: その置き場を管理しているツールが自分でフックを書き直したとき。
こちらの関所は黙って消える。

### 既存の pre-commit フレームワーク (husky / pre-commit / lefthook / overcommit) — ⚠

保証される: **共存できる**。導入時に既存フックを退避して連鎖するので、
向こうのチェックも走り続ける。

保証されない: 向こうの再インストール。`pre-commit install` も
`husky install` もフック本体を書き直すので、**こちらの関所が黙って消える**。
入れ直したら必ず `zai czero doctor`。

### シンボリックリンク越しのチェックアウト — ✅

保証される: 台帳のキーは `canonicalize` して実体へ寄せるので、
リンク経由と実体経由で台帳が 2 つに割れることはない
(macOS の `/var` → `/private/var` で実際に踏んだ罠)。

保証されない: **リポジトリの中から外を指すシンボリックリンク**。その先への
書き込みはリポジトリの外なので、行域の管轄外になる。

### 読み取り専用チェックアウト — ❌

保証される: 診断 (`doctor`) は動く。

保証されない: `init`。書けないので入らない。

検出の限界: git ディレクトリは**実際に一時ファイルを作って消す**ので確実。
作業ツリー側は `permissions().readonly()` しか見ない (作業ツリーへ 1 バイトも
書かないため)。したがって「誰も書けない」形 (`chmod 555` / 読み取り専用
マウント / Windows の読み取り専用属性) は拾えるが、**他人の所有物 (0755) は
拾えない** — その場合は `init` の失敗として出る。

### 巨大リポジトリ — ⚠ (注記のみ)

守りの強さは変わらない。`.git/index` が 32MiB (概ね 30 万件) を超えると、
診断が叩く `git ls-files` がパターンごとに全件を舐めるので待たされる。

### ネットワーク FS — **検出しない (試して撤回した)**

「形態の下見に 2 秒以上かかったら遅い置き場」という注記を入れて実測したら、
**ローカルの tmpfs に作った空リポジトリでも毎回 1.7〜2.3 秒**出た。内訳は
形態の下見ではなく、`shellenv::resolve_path` がプロセスで最初の 1 回だけ
**ログイン + 対話シェルを起こして PATH を解決する**コストだった
(git 呼び出し自体は 1 回 30〜64ms)。

つまりその数字はリポジトリの置き場を 1 ミリも測っていない。
**絶対時間で線を引くと必ず嘘をつく** (CLAUDE.md) の実例なので、判定ごと
撤回した。巨大さは時間ではなく index の大きさという構造で見る。
UNC パス (`\\server\share`) のような**構造で判る**信号が要るなら、
そちらを足すこと。

## 実証 (`czero verify`) が扱えていないもの

`verify` の試行は全部 `std::env::temp_dir()` 配下の使い捨てリポジトリで
起こす (対象リポジトリを 1 バイトも汚さないため)。したがって
**対象リポジトリ固有の形態は 1 つも通っていない**。

`verify` は対象の形態を見て、扱えていないものを見出しの直後に列挙する
(`--json` なら `untested_shapes`)。これを黙ると「守られています」が
リポジトリ全体の保証に読めてしまう。

## 判定の 3 段 (`verify` の `verdict`)

| 段 | 意味 | 既定の終了コード |
| --- | --- | --- |
| `verified` | 全ての試行を実際に起こして、全部通った。**かつ**対象リポジトリに実証が触れていない形態が無い | 0 |
| `partial` | 落ちた試行は無いが、**試せなかった試行**か**実証が触れていない形態**がある | 0 (`--strict` なら 1) |
| `broken` | 守られていない試行がある | 1 |

`partial` が要る理由: 実コミットが本当に止まるかを試す試行
(`trial_live_commit`) は、**本物の `zai` と実環境の台帳が揃っているとき
にしか走らない**。以前はこれが黙って飛んだうえで全体が「守られています」に
なり得た。いま飛んだ試行は理由付きで見出しの直後に出て、判定は `partial` で
止まる。
