# 「競合ゼロ」とは何か — 主張の線引きと実測

Zaivern Code は「並列でエージェントを走らせても、同じファイルを 2 人が触らない」
と言っている。次の版はこれを
「**同じファイルでも、違う行なら 2 人が同時に書ける**」へ広げようとしている。
**この文書はその主張が何を指し、何を指さないかを固定し、
支える数字を全部載せる。**測っていないものは書かない。

**先に結論**: 行域オーナーシップは**衝突を減らさない**。離れた行域なら
素の git がもとから 0 件でマージする (§3.8.1)。減るのは**拒否**で、
1 ファイルへ 64 体をぶつけたとき **63 件拒否 → 0 件**、
**完了 1 件 → 64 件**になる。そして**出荷物 (0.13.0) はまだ行域を
理解しない**ので、この段は参照実装でしか測れていない (§3.8.3)。

再現はコマンド 1 行:

```sh
tools/conflict-zero-bench.sh --writers 8            # ベースラインとガードの比較
tools/conflict-bench.sh --agents 64 --files 1000    # CHANGELOG 0.12.0 の数字 (約 6 分)
tools/coedit-bench.sh --agents 64 --lines 2000      # 行域オーナーシップ (§3.8。約 6 分)
```

## 1. 「競合ゼロ」が意味すること / しないこと

### 意味すること

**同じ担当表を流したとき、統合時に git のマージ衝突マーカ (`<<<<<<<`) が
1 つも出ない。**一次データは「2 人以上が同じファイルを書いた件数」で、
それが 0 なら衝突は**起こり得ない**。

### 意味しないこと (ここを混ぜたら嘘になる)

1. **意味的な衝突は防げない。** 片方が関数の引数を変え、もう片方が古い
   呼び方のまま別ファイルへ書いたら、リースは両方を通し、git も黙って
   マージする。壊れるのはビルド時かテスト時。
   (`src/semconf.rs` がこれを別立てで検出しようとしているが、
   **その検出率はこの文書では測っていない**。)
2. **「全員が全部書けたうえで衝突が 0」ではない。**
   ゼロは**書き込みを断る**ことで買っている。実測で、8 人 / 重なり 0.5 なら
   48 件中 27 件しか書けず、64 体 1536 件では 565 件 (37%) しか書けていない。
   断られた担当は消えるのではなく別のエージェントへ回る想定だが、
   **そこはまだ測っていない。**
3. **「重なりが無い作業」で 0 なのは当たり前。**
   下の実測表の `--overlap 0.0` の行がそれで、ガードが有っても無くても 0 件。
   **ガードの価値は重なりがある時にしか出ない。**
4. **同時実行数が上がると、ゲート自体が臨界路になる。**
   4〜8 体で p50 40〜50 ms、**64 体で p50 298.7 ms**。
5. **1 台の macOS でしか測っていない。** 数字はファイルシステムの速度に直結する。

### 新方針「行域オーナーシップ」が意味すること / しないこと

0.13.0 までの「ゼロ」は**ファイル単位の所有**で買っていた。次の方針は
「**同じファイルでも、違う行なら 2 人が同時に書ける**」(`src/region.rs` の
`Region` / `SAFE_BAND`)。実測は §3.8。**主張を先に狭めておく。**

#### 意味すること

**ファイル単位の所有が拒否していた書き込みが通るようになる。**
1 ファイルへ 8 体をぶつけると、ファイル単位では 8 件中 **1 件**しか書けない
(残り 7 件は拒否)。行域なら **8 件全部**が書けて、統合後も 8 体ぶんの変更が
残る。**これがこの機能の価値の全部**であり、下の「意味しないこと」1 と
必ずセットで読むこと。

#### 意味しないこと (ここを混ぜたら嘘になる)

1. **「行域にしたから衝突が減った」ではない。**
   互いに離れた行域なら、**素の git がもとから 0 件でマージする**
   (§3.8 の `disjoint` / 段 A が 0 ハンク)。行域オーナーシップは
   git にできないことをしているのではなく、**ファイル単位の所有が
   壊した並列度を戻しているだけ**。比較の相手は git ではなく
   「ファイル単位の所有」である。
2. **域が近ければ結局書けない。** わざと重ねた `crowded` では、
   行域でも 8 件中 **2 件**しか通らない。総作業量は素の git と同じで、
   変わるのは**人が衝突を解く回数が 6 回から 0 回になる**ことだけ。
   衝突を消したのではなく、**発見の時期を統合後から書き込み前へ動かした**。
3. **安全帯は保守的で、git なら通った組まで断る。**
   `crowded` で「安全帯的に近すぎる組」は 22 組あるのに、
   素の git が実際に衝突したのは 6 ブランチ。**差は取りこぼしではなく
   意図した過剰防衛**だが、拒否のコストとして数える必要がある。
4. **拒否された担当が別のエージェントへ回ることは、まだ測っていない。**
   これは 0.12.0 からの積み残し (§5-2) で、行域にしても解けていない。
5. **意味的な衝突は相変わらず 1 つも防げない。** 行が離れていても、
   片方が関数の引数を変えれば壊れる。

## 2. 4 つの鎖 — どこまで守れているか

衝突を起こさせないための鎖は 4 本ある。**1 本でも切れていたら「ゼロ」は言えない。**

| # | 鎖 | いつ効くか | 実装 | 実測 |
|---|---|---|---|---|
| ① | **配る前の分割** | タスクをエージェントへ割り当てる瞬間 | `coordinator::overlap_reason` / `overlap_split` (GUI から到達) | **未測定** |
| ② | **実行中の強制** | エージェントがファイルを書く直前 | `crate::lease::gate` (`zai hook` / エディタ自身の保存 / シェル経由の書き込み) | **測定済み (下記)** |
| ②' | **実行中の強制 (行域)** | 同上。粒度がファイル → 行域になる | `src/region.rs` (`Region` / `SAFE_BAND`) | **出荷物では未接続。参照ゲートで上限のみ測定 (§3.8)** |
| ③ | **統合** | ブランチをマージする時 | `zai train plan` / `run --dry-run` (`src/train.rs`) | **測定済み (下記)** |
| ④ | **共有面の自動解決** | 全員が触らざるを得ないファイル (設定一覧・`mod` 宣言など) | `zai merge-driver` (`src/union.rs`) | **測定済み — この合成リポジトリでは効果ゼロ** |

### 正直に言うと

- **① は動いているが、この文書には数字が無い。**`coordinator` のテストは
  「重なったら配らない」を単体で固定しているが、**エンドツーエンドで
  「配り方を変えたら衝突が何件減ったか」は測っていない。**
- **③ は実装されたが、衝突の総量は 1 つも減らない。**測ると
  **ハンク数は素朴な順序と完全に同じ**で、減るのは「衝突で止まる回数」だけ。
  さらに **書き手が worktree を持っている間は 1 本も計画に載らない**
  (`train::candidates` が他の worktree の握っている枝を外す仕様)。
  つまり**走っている最中には使えない**。
- **②' は `src/region.rs` があるだけで、呼び出し元が 1 つも無い。**
  `grep -rn 'region::' src/` は `src/region.rs` 自身の外で **0 件**。
  出荷物 (0.13.0) の `zai lease claim 'a.rs#L1-40'` は `#L1-40` を
  **ただのパス文字列**として扱うので、重なった 2 つの行域が両方通る。
  CLAUDE.md の「UI から到達できない実装は未完成」がそのまま当てはまる。
  §3.8 の段 C はこの検査に落ちて **skip (未測定)** になる。
- **④ は実装されたが、この合成リポジトリでは 1 件も吸収しなかった。**
  `zai merge-driver` を挿しても衝突数はベースラインと 1 桁も変わらない
  (下記 3.7)。**配管の問題ではない** — 同じ場所へ参照ドライバ
  (`git merge-file --union`) を挿すと 18 ハンクが 0 になるので、
  差はドライバの方針 (共有面の構文だけを吸収し、それ以外は通常の 3-way
  へ譲る) にある。CLAUDE.md が言う `config.rs` / `keybinds.rs` のような
  **実際の共有面での効果は、この合成ベンチでは測れていない。**

## 3. 実測

計測環境: macOS 26.5.2 (Darwin 25.5.0) / Intel Core i9-9980HK 8C16T / 64GB /
git 2.47.1 / Python 3.12.7 / `zai` 0.12.0 release (`5b2c66f`) / 2026-08-10。
全て `--seed 20260810` (既定)。合成リポジトリは 1 ファイル 6 ブロックで、
**同じファイルでも別ブロックなら git は自動マージする** (重なり = 衝突ではない)。

### 3.1 ベースライン — 「使わなかったら何件衝突するのか」

`tools/conflict-zero-bench.sh --writers 8 --files 48 --overlap <r>`

| 重なり | 2 人以上が書いたファイル | 衝突したマージ | 衝突ファイル | 衝突ハンク | 衝突行 |
|---:|---:|---:|---:|---:|---:|
| 0.00 | 0 | 0 / 8 | 0 | 0 | 0 |
| 0.25 | 3 | 3 / 8 | 3 | 3 | 6 |
| 0.50 | 5 | 4 / 8 | 4 | 7 | 16 |
| 0.75 | 6 | 7 / 8 | 6 | 15 | 33 |
| 1.00 | 6 | 7 / 8 | 6 | 18 | 42 |

**これがガードを 1 つも通さない素の git worktree の姿。**
重なりが 0 なら衝突も 0 で、重なりが増えると 8 回のマージのうち 7 回まで衝突する。

### 3.2 同じ担当表にガード (②) を掛けた場合

同じ表を `zai hook` (= `crate::lease::gate`) 越しに流した結果。

| 重なり | 書けた / 計画 | ゲートが止めた | 2 人以上が書いた | 衝突ハンク |
|---:|---:|---:|---:|---:|
| 0.00 | 48 / 48 | 0 | 0 | **0** |
| 0.25 | 40 / 48 | 8 | 0 | **0** |
| 0.50 | 27 / 48 | 21 | 0 | **0** |
| 0.75 | 24 / 48 | 24 | 0 | **0** |
| 1.00 | 10 / 48 | 38 | 0 | **0** |

- **衝突ハンクは全ての重なりで 0。**
- **重なり 0.00 ではゲートが 1 件も止めていない** — 使っていない人は払わない。
- **代償は書けた件数**。重なり 1.00 では 48 件中 10 件しか書けていない。

### 3.3 同時実行数を上げた場合 (重なり 0.5 固定・ファイル数 = 書き手 × 6)

| 書き手 | ベースライン: 衝突マージ / ハンク | ガード: 書けた / 計画 | fail-open | busy-deny | ゲート p50 / p95 |
|---:|---:|---:|---:|---:|---|
| 4 | 2 / 4 · 2 ハンク | 14 / 24 | 0 | 0 | 40 / 57 ms |
| 8 | 4 / 8 · 7 ハンク | 27 / 48 | 0 | 0 | 49 / 84 ms |
| 16 | 11 / 16 · 19 ハンク | 55 / 96 | 0 | 0 | 64 / 104 ms |
| 32 | 27 / 32 · 56 ハンク | 106 / 192 | 0 | **4** | 113 / 236 ms |
| 64 | 57 / 64 · 132 ハンク | 202 / 384 | 0 | **14** | 160 / 320 ms |

ガード側の衝突ハンクは**全ての行で 0**。

- **`fail-open` (判定せずに通した回数) は全ての規模で 0。**
  `docs/conflict-bench.md` がかつて「16 体で毎回漏れる」と書いていた問題は
  `ec9a479` の 2 つの修正で解消しており、再測で再現しない。
- **代わりに 32 体以上で `busy-deny` が出る。**混雑して判定できないときに
  **止める**方へ倒した結果で (fail-closed)、再試行すれば通る。
  安全側だが、ユーザーからは「たまに拒否される」として見える。
  **32 体以上を常用するならここが次の課題。**

### 3.4 CHANGELOG 0.12.0 の「64 体・1500 書込」

`tools/conflict-bench.sh --agents 64 --files 1000` で**再現した**。

| | A: ガード無し | B: ガード有り |
|---|---:|---:|
| 計画した編集 | 1536 件 | 1536 件 |
| 実際に書けた編集 | 1536 件 | **565 件** |
| 2 人以上が書いたファイル | 464 件 | **0 件** |
| 衝突したマージ | 54 / 64 回 | **0 / 64 回** |
| 衝突ハンク | **167 個** | **0 個** |
| 壁時計: 編集フェーズ | 993 ms | 9.8 秒 |

「1500 書込」の正体は **1536 件**、「167 箇所」の正体は **167 ハンク**。
**ただし B が書けたのは 37% (565/1536)。**この代償は CHANGELOG には
書かれていなかったので、ここに書く。

### 3.5 マージドライバの配管 — 参照ドライバでの上限

段④ が「どこまでなら吸収できるか」の上限を先に見る。git のマージドライバ
契約に沿った**参照ドライバ** (`git merge-file --union %A %O %B`) は
両側を機械的に残すので、**テキスト衝突を全部飲む**。
`--writers 8 --files 48 --overlap 1.0`:

| 段 | 2 人以上が書いたファイル | 衝突マージ | 衝突ハンク |
|---|---:|---:|---:|
| baseline | 6 | 7 / 8 | 18 |
| guard (②) | 0 | 0 / 8 | 0 |
| union (④, 参照ドライバ) | **6 のまま** | 0 / 8 | **0** |

**union は「起こった衝突をマージ時に吸収する」ので、`dup_files` は減らない。**
テキストとして綺麗にマージできたことと、結果がコンパイルできることは別 —
両側を残した `let value` が 2 行並んだコードはコンパイルが通らない。
**この行が示すのは「ドライバを挿す配管が動く」ことと、吸収の理論上限だけ。**
出荷される `zai merge-driver` の実測は 3.7。

### 3.6 統合の順序付け (③) — 総量は減らない。減るのは「止まる回数」

`tools/conflict-zero-bench.sh` は同じ N 本のブランチを **`zai train plan` が
出した順序**と**作成順 (素朴)** の両方でマージし、並べて出す。
片方だけ出しても「順序付けが効いた」とは言えないため。

| 書き手 | train 順: 衝突マージ / ハンク | 素朴順: 衝突マージ / ハンク | 最初の衝突までに自動で入った本数 (train / 素朴) |
|---:|---:|---:|---:|
| 4 | 2 / 4 回 · **2** | 2 / 4 回 · **2** | 2 / 2 |
| 8 | 4 / 8 回 · **7** | 4 / 8 回 · **7** | **4** / 2 |
| 16 | **9** / 16 回 · **19** | 11 / 16 回 · **19** | **7** / 2 |
| 24 | **16** / 24 回 · **40** | 19 / 24 回 · **40** | 1 / **2** |
| 32 | **23** / 32 回 · **56** | 27 / 32 回 · **56** | 1 / **2** |

- **衝突ハンクの総量は全ての規模で完全に一致した (2 / 7 / 19 / 40 / 56)。**
  順序付けは衝突を消す仕組みではない。同じ行域が重なった組は
  どう並べても人手が要る (`train` 自身が `line_pairs` として申告する)。
- **減るのは「衝突で止まったマージの回数」** — 16 人で 11 → 9、
  24 人で 19 → 16、32 人で 27 → 23。**人が割り込まれる回数**がここ。
- **「最初の衝突までに自動で入る本数」は規模によって逆転する。**
  8〜16 人では 2 → 4 / 2 → 7 と伸びるが、**24 人以上では 2 → 1 と縮む**。
  貪欲な並べ方が高並列で裏目に出ている。**良くなる方だけ書かない。**

#### 乾式検査 (`plan --json` の `dry` / `run --dry-run`) はよく当たる

| 書き手 | 予想が触れた段 / 当たり | 最初に衝突する枝 | 衝突ファイルまで |
|---:|---:|---|---|
| 4 | 3 / 3 | 一致 | 一致 |
| 8 | 5 / 5 | 一致 | 一致 |
| 16 | 8 / 8 | 一致 | 一致 |
| 24 | 2 / 2 | 一致 | 一致 |
| 32 | 2 / 2 | 一致 | 一致 |

`train run --dry-run` の終了コードは全ての規模で 1 (= 衝突で停止する見込み)
で、実際の結果と一致した。**予想は「最初に衝突した段で打ち切る」仕様**なので、
分母は予想が触れた段だけ。そこは 5 規模すべてで 100% 当たっている。

#### 使えない条件が 2 つある (どちらも仕様だが、数字として残す)

1. **書き手が worktree を持っている間は 1 本も計画に載らない。**
   実測で計画 0 本 / 他の worktree が握って外された枝が書き手と同数
   (8 人なら 8 本、32 人なら 32 本)。統合順を出せるのは
   **エージェントが worktree を手放した後**。
2. **24 本を超えると、超えたぶんが黙って計画から消える。**
   32 本を投げると計画は 24 本になるが、`plan.dropped` は **0** と報告する
   (`train::touches_from_repo` が `take(MAX_BRANCHES)` で数える前に切るため)。
   ハーネスは申告値を信じず**自分で引き算して**警告し、比較の公平のため
   落ちた枝を末尾へ足している。

### 3.7 共有面の自動解決 (④) — この合成リポジトリでは効果ゼロ

| 書き手 | baseline: 衝突マージ / ハンク | `zai merge-driver`: 衝突マージ / ハンク |
|---:|---:|---:|
| 8 | 4 / 8 · 7 | 4 / 8 · **7** |
| 16 | 11 / 16 · 19 | 11 / 16 · **19** |
| 32 | 27 / 32 · 56 | 27 / 32 · **56** |

**1 件も吸収していない。**ただしこれは配管の失敗ではない —
同じ場所へ参照ドライバ `git merge-file --union %A %O %B` を挿すと
`--overlap 1.0` で 18 ハンクが 0 になる (3.5)。差はドライバの方針で、
`zai merge-driver` は共有面の構文 (一覧・宣言ブロック) だけを吸収し、
それ以外は通常の 3-way へ譲る。**この合成リポジトリの中身は
`let value = N;` の書き換えだけなので、そもそも守備範囲の外。**
実際の `config.rs` / `keybinds.rs` のような共有面での効果は
**このベンチでは測れていない。**

### 3.8 行域オーナーシップ (②') — 拒否は消える。衝突は**もともと 0 だった**

`tools/coedit-bench.sh --agents 1,4,8,16,32,64 --lines 2000`。
計測環境は §3 と同じ機械 (macOS 26.5.2 / git 2.47.1 / `zai` 0.13.0) で
2026-08-10、種は既定の `20260810`。

**土俵が §3.1〜3.7 と逆であることに注意。**ここでは合成リポジトリに
**ファイルを 1 個しか置かない**。ファイル単位の所有だと並列度が構造的に
1 に潰れる状況を作って、行域が何を取り戻すのかだけを見る。

段は 4 つ: **A** 素の git (保護なし) / **B** ファイル単位の所有
(`zai lease claim 'src/wide.rs'`) / **C** 出荷物の行域所有
(`zai lease claim 'src/wide.rs#L10-40'`) / **Cref** 行域所有の**参照ゲート**
(`region::spans_too_close` をハーネス内に写したもの)。
**C は 12 段すべて skip した** — 理由は 3.8.3。

#### 3.8.1 離した行域 (`--layout disjoint`) — 衝突は 3 段とも 0。差は拒否だけ

安全帯以上に離れた行域を配った場合。担当表の「近すぎる組」は全規模で 0。

| 体数 | A 完了 | A 拒否 | A ハンク | B 完了 | B 拒否 | Cref 完了 | Cref 拒否 | Cref ハンク |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 0 | **0** | 1 | 0 | 1 | 0 | **0** |
| 4 | 4 | 0 | **0** | 1 | 3 | 4 | 0 | **0** |
| 8 | 8 | 0 | **0** | 1 | 7 | 8 | 0 | **0** |
| 16 | 16 | 0 | **0** | 1 | 15 | 16 | 0 | **0** |
| 32 | 32 | 0 | **0** | 1 | 31 | 32 | 0 | **0** |
| 64 | 64 | 0 | **0** | 1 | **63** | 64 | **0** | **0** |

統合後に残った担当の数は、A と Cref では**完了数と完全に一致**した
(64 体なら 64 体ぶんの変更が最終ツリーに残る)。B は全規模で **1**。

- **一番大事な数字は「A のハンクが全規模で 0」。**
  離れた行域なら、**保護を 1 つも通さない素の git がもとから衝突しない**。
  行域オーナーシップは git にできないことをしているのではない。
- **効いているのは B との比較だけ。** 1 ファイルに 64 体をぶつけると、
  ファイル単位の所有は **63 件を拒否して 1 件しか通さない**。
  行域なら **拒否 0 件・64 件全部が通る**。
  **拒否 63 → 0、完了 1 → 64。これがこの機能の価値の全部である。**
- **B が規模によらず「完了 1」なのは偶然ではない。**
  対象ファイルが 1 個しか無いのだから、ファイル単位の所有では
  並列度は定義上 1 になる。§3.2 の表 (48 ファイル) で
  「重なり 1.00 でも 10 件書けた」ように見えたのは、
  **ファイルが 48 個あったから**にすぎない。

#### 3.8.2 近づけた行域 (`--layout crowded`) — 保護は効く。ただし総作業量は増えない

わざと重ねて配った場合 (幅 6 行の域を 2 行間隔で並べる)。
**保護が本当に効くかの裏取り**がここ。

| 体数 | 近すぎる組 | A 衝突枝 | A ハンク | A 衝突行 | A 人手 | A 生存 | B 完了=生存 | B 拒否 | Cref 完了=生存 | Cref 拒否 | Cref 人手 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0 | 0 | 0 | 0 | 0 | 1 | 1 | 0 | 1 | 0 | 0 |
| 4 | 6 | 3 | 3 | 60 | 3 | 1 | 1 | 3 | 1 | 3 | **0** |
| 8 | 22 | 6 | 6 | 120 | 6 | 2 | 1 | 7 | 2 | 6 | **0** |
| 16 | 54 | 12 | 12 | 240 | 12 | 4 | 1 | 15 | 4 | 12 | **0** |
| 32 | 118 | 24 | 24 | 480 | 24 | 8 | 1 | 31 | 6 | 26 | **0** |
| 64 | 246 | **48** | **48** | **960** | **48** | 16 | 1 | 63 | **9** | 55 | **0** |

- **保護は効いている。** Cref のハンクは全規模で 0、人手も 0。
  同じ担当表で素の git は 64 体で **48 ブランチが衝突し、960 行を人に読ませ、
  48 回の手作業を要求する**。
- **しかし「行域にすれば得」ではない。**64 体の `crowded` で最終ツリーに
  残った担当は **A が 16、Cref は 9** で、**素の git の方が多い**。
  A はそれを **48 回の衝突解決**と引き換えに得ている。
  Cref は 9 体ぶんを**人手 0 回**で得る。
  **総作業量が増えるのではなく、コストが「統合後の人手」から
  「書き込み前の拒否」へ移動しているだけ**である。§1 の「意味しないこと」2 の実体。
- **安全帯は明確に過剰防衛である。**64 体で「近すぎる」と判定される組は
  **246 組**あるが、素の git が実際に衝突したのは **48 ブランチ**。
  fail-closed として正しいが、**断りすぎている分は数えておく必要がある**
  (§5-11)。
- B は `crowded` でも完了 1 のまま。**近さに関係なく 1**。

#### 3.8.3 出荷物 (0.13.0) は行域を理解しない — 段 C は 12 段すべて未測定

ハーネスは段 C を走らせる前に能力検査をする。重なった 2 つの行域
(`a.rs#L1-10` と `a.rs#L5-15`) を投げて、**2 本目が断られること**を確かめる。
0.13.0 は**両方通した**ので、12 段すべてが skip になった。

**これを検査せずに走らせると、静かな嘘になる。**0.13.0 の `lease claim` は
`#L1-10` を**ただのパス文字列**として扱う (台帳には小文字化された
`a.rs#l1-10` が並ぶ) ので、保護が 1 つも無いまま
「全員書けて衝突 0」という**綺麗な数字が出てしまう**。

さらに悪いことに、これは単なる未実装ではなく**後退**である:

| 台帳の状態 | 投げた指定 | 0.13.0 の結果 |
|---|---|---|
| 誰も持っていない | `a.rs` | 確保 |
| `ag1` が `a.rs` を持っている | `a.rs` | **拒否** (正しい) |
| `ag1` が `a.rs` を持っている | `a.rs#L1-10` | **確保** (素通り) |
| `ag1` が `a.rs#L1-10` を持っている | `a.rs#L5-15` | **確保** (重なっているのに) |

**いま `#L` 付きで claim すると、現に効いているファイル単位の保護をすり抜ける。**
`src/region.rs` は存在するが、`grep -rn 'region::' src/` は自分自身の外で
**0 件** — 呼び出し元が 1 つも無い。CLAUDE.md の
「UI から到達できない実装は未完成」がそのまま当てはまる (§5-9 / §5-10)。

#### 3.8.4 効かなかったもの・悪化したものも書く

- **参照ゲートのゲート待ちは、規模とともに露骨に伸びる**
  (64 体で p50 **1002ms** / max **1852ms**)。
  **ただしこれは行域判定の費用ではない。**参照ゲートは awk のプロセス起動と
  `mkdir` のスピンロックで書いてあり、測っているのは**ハーネスの費用**である。
  同じ規模で出荷物のファイル所有 (B) は p50 **153ms**。
  **行域判定そのものの費用は 1 度も測っていない** (§5-12)。
- **`disjoint` の統合時間は、行域にしても 1 ミリも減らない。**
  64 体で A が 11.3 秒、Cref が 12.7 秒。マージする枝の数が同じなので当然で、
  **B の 1.3 秒が速いのは 63 本を捨てているからにすぎない**。
  「行域にしたら統合が速くなる」とは言えない。
- **`git merge-tree --write-tree` の予測は 36 段すべてで 100% 一致した**
  (64 体なら 64/64)。予測と実際が食い違った段は 1 つも無い。
  git 2.38 未満では検算そのものを skip する。
- **1 体のときは 3 段とも完全に同じ数字になる** (完了 1 / 拒否 0 / 衝突 0)。
  **並列度 1 では、どの所有方式にも価値は無い。**

なお、掃引の **ms 列は別のベンチが一度重なって走った状態**で取っている。
件数の列は種を固定すれば決定的で、`--agents 8` の清浄な再実行で
`crowded` の 6 枝 / 6 ハンク / 120 衝突行 / 生存 2、Cref の完了 2 / 拒否 6 が
**完全に一致することを確認した**。ms 列は目安として読むこと。

### 3.9 出荷バイナリでの再測定 (v0.14.0) — 参照実装と 1 件も違わない

§3.8 の時点では段 C（行域）は**参照実装（シェルで模した台帳）でしか測れていなかった**。
0.13.0 の `zai lease claim` は `a.rs#L1-10` を**ただの文字列**として扱うため、
ハーネスの能力検査が段 C を skip していたからである。v0.14.0 で出荷物が行域を
理解するようになったので、**同じハーネスで出荷バイナリを測り直した**。

`sh tools/coedit-bench.sh --agents 64 --lines 2000 --mode all`（1 ファイル 2000 行に 64 体）:

| layout | 段 | 完了 | 拒否 | 衝突枝 | 衝突行 | 人手 | 生存 |
|---|---|---:|---:|---:|---:|---:|---:|
| 離した域 | A 素の git | 64 | 0 | 0 | 0 | 0 | 64 |
| 離した域 | B ファイル所有 | **1** | **63** | 0 | 0 | 0 | 1 |
| 離した域 | **C 行域（出荷物）** | **64** | **0** | **0** | **0** | **0** | 64 |
| 離した域 | C 行域（参照） | 64 | 0 | 0 | 0 | 0 | 64 |
| 詰めた域 | A 素の git | 64 | 0 | **48** | **960** | **48** | 16 |
| 詰めた域 | B ファイル所有 | 1 | 63 | 0 | 0 | 0 | 1 |
| 詰めた域 | **C 行域（出荷物）** | 11 | 53 | **0** | **0** | **0** | 11 |
| 詰めた域 | C 行域（参照） | 11 | 53 | 0 | 0 | 0 | 11 |

**出荷物と参照実装が全ての列で一致した。** 主張は §3.8 から変わらない —
**衝突は元から 0 で、行域が買うのは並列度（完了 1 → 64）** である。
詰めた条件で完了が 11 に留まるのも参照と同じで、これは要求総量がファイルに

#### 途中で見つかった回帰 — 単体テストでは捕まらなかった

最初の再測定で、ハーネスの能力検査が **「重なった 2 つの行域が両方通った」** を検出して
段 C を skip した。単体テストは 4178 件すべて緑だったので、**実バイナリを回さなければ
気付けなかった**。

再現は 1 行: 1 行しかないファイルへ `a.rs#L1-10` を確保した直後に `a.rs#L5-15` が通る。
原因は錨の解決で、(1) 記録した行数を現在のファイルの行数で頭打ちにしていたこと、
(2) 末尾の錨が空（= 確保時に EOF を超えていた）のとき域を先頭 1 行へ畳んでいたこと。
**EOF を超える確保は「これから書く場所の予約」で正しい状態**なので、縮めると予約が消えて
別人が同じ場所を取れる。`region::tests::eofを超える予約は縮まない` が番人。

**この 1 件は、ハーネスが「行域を理解しているか」を毎回検査してから測る作りだったから
見つかった。** 検査を省いていれば「全員書けて衝突 0」という綺麗な数字がそのまま出ていた。

### 3.10 安全帯の下限 — 実測で 3 → 1（`coedit` のみ）

`SAFE_BAND = 3` の根拠は「git の diff の既定文脈が 3 行だからハンクが畳まれる」と
説明されていたが、**これは誤りだった**。実 git で経路別に測った下限:

| 経路 | 相手=置換 | 相手=削除 | 相手=挿入 | 下限 |
|---|---|---|---|---|
| `git merge-file -p` | 1 | 1 | 1 | **1** |
| `git merge-tree --write-tree` / `git merge` | 1 | 1 | 1 | **1** |
| `git apply`（文脈 3 行） | 3 | 3 | 3 | **3** |

3 行は*表示*の話で、xdl_merge が衝突を出すのは変更ハンクが重なるか隣接するときだけ。
myers / minimal / patience / histogram の 4 アルゴリズムすべてで同じ。
**`SAFE_BAND = 3` は正しいが、由来はパッチ適用（`git apply`）だった。**

`coedit`（一撃マージの証明）は `git merge` しか使わないので、`MERGE_ONLY_BAND = 1` を使う:

| | 帯 1（新既定） | 帯 3（旧既定・同一ケース列） |
|---|---:|---:|
| 回したケース | **240** | 240 |
| 証明が立った | **122** | 72 |
| 実 git で綺麗だった | **122（全部）** | 72（全部） |
| **見逃し** | **0** | **0** |
| 過剰報告 | 18 = **15.3%** | 68 = **40.5%** |

帯 3 では止まっていた **50 件**が新たに証明でき、全件が実 git で綺麗だった。
Docker Linux（別 git 版）でも数字が 1 件違わず一致。
残る 15.3% は帯のせいではなく、(a) 挿入点を直前 1 行として持つぶんの厚み 16 件、
(b) 2 本が同じ行を同じように削って git が同一変更として畳んだ 2 件。

**`git apply` / `git am` / `format-patch` / `rebase --apply` を通す経路が 1 つでも
生えたら `SAFE_BAND` へ戻す必要がある。** この条件は `coedit` のモジュール doc に書いてある。

```sh
# 重なりを振る (0.0 = 完全独立 / 1.0 = 全員が同じファイル)
for r in 0.0 0.25 0.5 0.75 1.0; do

done

# 同時実行数を上げる
tools/conflict-zero-bench.sh --writers 32 --files 192 --overlap 0.5

# 共有面の自動解決 (④) の配管を参照ドライバで確かめる
tools/conflict-zero-bench.sh --writers 8 --files 48 --overlap 1.0 \
  --union-driver 'git merge-file --union %A %O %B'

# 機械可読
tools/conflict-zero-bench.sh --writers 8 --json | jq '.stages[] | {stage,status,hunks,dup_files}'

# CHANGELOG 0.12.0 の数字 (約 6 分)
tools/conflict-bench.sh --agents 64 --files 1000

# ── 行域オーナーシップ (§3.8) ───────────────────────────────────
# **ファイルは 1 個だけ**置いて、N 体が別々の行域を書く。
# zai が 1 つも無くても段 A (素の git) と Cref (参照ゲート) は必ず出る
tools/coedit-bench.sh --agents 8 --lines 500 --mode all

# 掃引 (§3.8 の表そのもの。約 6 分)
tools/coedit-bench.sh --agents 1,4,8,16,32,64 --lines 2000

# わざと域を近づけて、保護が本当に効くかの裏取りだけ
tools/coedit-bench.sh --agents 8 --lines 500 --layout crowded

# 機械可読
tools/coedit-bench.sh --agents 8 --lines 500 --json |
  jq '.region_aware, (.stages[] | {layout,mode,completed,denied,hunks})'
```

`coedit-bench.sh` は **python を呼ばない** (POSIX sh + awk だけ)。
終了コードは 0 = 保護のある段 (B / C / Cref) に衝突ハンクが無い (または skip)、
1 = 保護のある段に衝突が残った、2 = 引数か行数の誤り、3 = git / awk が無い。

一時リポジトリは `mktemp -d` (= `$TMPDIR` 由来)、`HOME` も一時ディレクトリへ
差し替えるので、**本物の `~/.zaivern` と `~/.gitconfig` には触らない**。
**cargo を呼ばないので、ホストの `target/` も汚さない** (既にある `zai` を
使うだけで、無ければその段を skip する)。

終了コードは 0 = ガード段が 0 件 (またはガード段が skip)、
1 = ガード段に衝突が残った、2 = 引数の指定ミス。

## 5. これから埋めるべき穴 (測っていないもの)

1. **鎖 ① の効果を端から端まで測る。** 「配る前に分けたら衝突が何件減ったか」。
   いまは単体テストしか無い。
2. **断られた担当がどうなるかを測る。** 「衝突ゼロ」は書き込みを断って
   買っているので、**総作業量が本当に保存されているか**を数字にしないと
   主張として片手落ち。
   → **半分だけ埋まった。**§3.8 で「完了した書き込み」と
   「統合後に生き残った担当の数」を測るようにしたので、
   *その 1 回の中で* 作業量が保存されているかは分かる
   (`disjoint` の行域なら 8/8 が書けて 8/8 が残る)。
   **まだ埋まっていないのは再投入**: 断られた担当を別のエージェントへ
   回したときに、何回目で通るのか・総壁時計が何倍になるのかは
   **1 つも測っていない**。
3. **鎖 ④ を、実際の共有面で測る。**この合成リポジトリは
   `let value = N;` しか書き換えないので `zai merge-driver` の守備範囲外で、
   効果ゼロという数字にしかならない。`config.rs` / `keybinds.rs` を模した
   一覧・宣言ブロックを持つ合成ファイルを足さないと、④ の主張は支えられない。
4. **32 体以上の `busy-deny` を減らす。** fail-open は消えたが、
   高並列で「再試行してください」が出る頻度は測ったとおり増えている。
5. **`train` の並べ方を高並列で見直す。**「最初の衝突までに自動で入る本数」が
   24 人以上で素朴順より短くなる (2 → 1)。貪欲な選び方が裏目に出ている。
6. **`train::MAX_BRANCHES` の切り捨てを申告どおりにする。**
   24 本超は `dropped` に数えられないまま計画から消える。
7. **`train` を作業中にも使えるようにする。**いまは書き手が worktree を
   持っている間、計画に 1 本も載らない。
8. **Linux / Windows で取り直す。** すべてファイルシステムの速度に直結する。
   `coedit-bench.sh` は POSIX sh + awk だけで書いてあるので Linux / Windows の
   git 同梱 sh でもそのまま走るはずだが、**実際に走らせてはいない**。
9. **行域オーナーシップを出荷物へ繋ぐ。** `src/region.rs` は呼び出し元が
   **0 件**で、`zai lease claim 'a.rs#L1-40'` は行域として解釈されない。
   §3.8 の段 C はこの理由で全部 skip している。
   **繋ぐまでは「同じファイルの違う行を 2 人が書ける」と製品として言えない。**
10. **`#L` 付きの指定が現行のファイル所有を素通りする。**
   実測: `a.rs` を誰かが持っている状態で `a.rs#L1-10` を投げると**通る**
   (台帳には小文字化された別パス `a.rs#l1-10` として並ぶ)。
   行域を実装するまでの間、この書き方は**保護を弱める方向の後退**であって、
   単なる未実装ではない。
11. **安全帯 (`SAFE_BAND = 3`) の過剰防衛を数える。**
   §3.8 の `crowded` では「近すぎる」と判定される組が 22 組あるのに、
   素の git が実際に衝突したのは 6 ブランチ。安全側なのは正しいが、
   **どれだけ余分に断っているか**を規模ごとに出さないと帯の幅を決められない。
12. **参照ゲートの遅延はハーネスの遅延であって実装の遅延ではない。**
   §3.8 の Cref のゲート待ちは awk のプロセス起動 + `mkdir` ロックの費用で、
   **行域判定そのものの費用は 1 度も測っていない**。
   出荷物へ繋いだら取り直すこと。
