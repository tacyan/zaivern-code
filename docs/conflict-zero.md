# 「競合ゼロ」とは何か — 主張の線引きと実測

Zaivern Code は「並列でエージェントを走らせても、同じファイルを 2 人が触らない」
と言っていた。0.14.0 でこれを
「**同じファイルでも、違う行なら 2 人が同時に書ける**」へ広げ、出荷物へ配線した。
**この文書はその主張が何を指し、何を指さないかを固定し、
支える数字を全部載せる。**測っていないものは書かない。
埋まった穴は本文へ畳み込む — **現在形で読める文章に古い数字を残さない。**
ただし**反証された主張は消さずに §6 の履歴へ移す** (消すだけだと、同じ測定を
した人が同じ誤った結論へ戻るため)。残っている穴は §5 に全部並べてある。

**先に結論**: 行域オーナーシップは**衝突を減らさない**。離れた行域なら
素の git がもとから 0 件でマージする (§3.8.1)。減るのは**拒否**で、
1 ファイルへ 64 体をぶつけたとき **63 件拒否 → 0 件**、
**完了 1 件 → 64 件**になる。0.14.0 で行域も `--shift` も出荷物へ配線され、
参照実装なしで測れるようになった (§3.9 / §3.11.4)。
**実在のリポジトリでも証明した** (§3.12)。64 体規模で出ていた取りこぼしは
0.15.0 で塞いだ (`lease::shift_ceiling`。経緯は §6-1)。**macOS でしか
測り直していないので、Linux での 64 体再測定は要再測定である** (§5-1)。

再現はコマンド 1 行:

```sh
tools/conflict-zero-bench.sh --writers 8            # ベースラインとガードの比較
tools/conflict-bench.sh --agents 64 --files 1000    # CHANGELOG 0.12.0 の数字 (約 6 分)
tools/coedit-bench.sh --agents 64 --lines 2000      # 行域オーナーシップ (§3.8。約 6 分)
tools/anyrepo-prove.sh --repo . --writers 8         # **自分のリポジトリで**証明する (§3.12)
tools/xplat-bench.sh                                # macOS と Linux を並べる (§3.13)
tools/region-cost.sh                                # 行域判定そのものの費用 (§3.14)
```

## 1. 「競合ゼロ」が意味すること / しないこと

### 意味すること

**同じ担当表を流したとき、統合時に git のマージ衝突マーカ (`<<<<<<<`) が
1 つも出ない。**一次データは「2 人以上が同じファイルを書いた件数」で、
それが 0 なら衝突は**起こり得ない**。

### 意味しないこと (ここを混ぜたら嘘になる)

1. **意味的な衝突は防げない。** 片方が関数の引数を変え、もう片方が古い
   呼び方のまま別ファイルへ書いたら、リースは両方を通し、git も黙って
   マージする。壊れるのはビルド時かテスト時。
   (`src/semconf.rs` がこれを別立てで検出しようとしているが、
   **その検出率はこの文書では測っていない**。)
2. **「全員が全部書けたうえで衝突が 0」ではない。**
   ゼロは**書き込みを断る**ことで買っている。実測で、8 人 / 重なり 0.5 なら
   48 件中 27 件しか書けず、64 体 1536 件では 565 件 (37%) しか書けていない。
   断られた担当は消えるのではなく別のエージェントへ回る想定だが、
   **そこはまだ測っていない。**
3. **「重なりが無い作業」で 0 なのは当たり前。**
   下の実測表の `--overlap 0.0` の行がそれで、ガードが有っても無くても 0 件。
   **ガードの価値は重なりがある時にしか出ない。**
4. **同時実行数が上がると、ゲート自体が臨界路になる。**
   4〜8 体で p50 40〜50 ms、**64 体で p50 298.7 ms**。
5. **落とす指標は Linux でも一致するが、壁時計は移せない。**
   `tools/xplat-bench.sh` で macOS と Linux を並べたところ、conflict-zero 20 段・
   coedit 64 行の**すべてで「落とす指標」(衝突ハンク数・二重書き込み・完了件数) が
   完全に一致**した。一方で壁時計は macOS が 6〜10 倍遅く、原因はファイル
   システムではなく**プロセス起動の値段**である (書き込みだけの編集フェーズは
   逆に macOS のほうが速い)。**時間の数字は OS をまたいで持ち込めない** (§3.13)。

### 新方針「行域オーナーシップ」が意味すること / しないこと

0.13.0 までの「ゼロ」は**ファイル単位の所有**で買っていた。次の方針は
「**同じファイルでも、違う行なら 2 人が同時に書ける**」(`src/region.rs` の
`Region` / `SAFE_BAND`)。実測は §3.8。**主張を先に狭めておく。**

#### 意味すること

**ファイル単位の所有が拒否していた書き込みが通るようになる。**
1 ファイルへ 8 体をぶつけると、ファイル単位では 8 件中 **1 件**しか書けない
(残り 7 件は拒否)。行域なら **8 件全部**が書けて、統合後も 8 体ぶんの変更が
残る。**これがこの機能の価値の全部**であり、下の「意味しないこと」1 と
必ずセットで読むこと。

#### 意味しないこと (ここを混ぜたら嘘になる)

1. **「行域にしたから衝突が減った」ではない。**
   互いに離れた行域なら、**素の git がもとから 0 件でマージする**
   (§3.8 の `disjoint` / 段 A が 0 ハンク)。行域オーナーシップは
   git にできないことをしているのではなく、**ファイル単位の所有が
   壊した並列度を戻しているだけ**。比較の相手は git ではなく
   「ファイル単位の所有」である。
2. **域が近ければ結局書けない。** わざと重ねた `crowded` では、
   行域でも 8 件中 **2 件**しか通らない。総作業量は素の git と同じで、
   変わるのは**人が衝突を解く回数が 6 回から 0 回になる**ことだけ。
   衝突を消したのではなく、**発見の時期を統合後から書き込み前へ動かした**。
3. **安全帯は保守的で、git なら通った組まで断る。**
   `crowded` で「安全帯的に近すぎる組」は 22 組あるのに、
   素の git が実際に衝突したのは 6 ブランチ。**差は取りこぼしではなく
   意図した過剰防衛**だが、拒否のコストとして数える必要がある。
4. **拒否された担当が別のエージェントへ回ることは、まだ測っていない。**
   これは 0.12.0 からの積み残し (§5-5) で、行域にしても解けていない。
5. **意味的な衝突は相変わらず 1 つも防げない。** 行が離れていても、
   片方が関数の引数を変えれば壊れる。
6. **「同じ行を 2 人に配らない」と「マージが綺麗に通る」は別の保証である。**
   前者 (`dup_lines = 0`) は台帳の性質なので**内容に一切依存せず、常に成り立つ**
   (121 回の証明実行で 121/121)。後者 (`conflict_files = 0`) は**git の diff の
   気持ち次第**で、反復的な内容では帯を満たしていても崩れる。§3.16 に実測。
   **この 2 つを 1 つの「衝突ゼロ」という言葉でまとめない。**

## 2. 4 つの鎖 — どこまで守れているか

衝突を起こさせないための鎖は 4 本ある。**1 本でも切れていたら「ゼロ」は言えない。**

| # | 鎖 | いつ効くか | 実装 | 実測 |
|---|---|---|---|---|
| ① | **配る前の分割** | タスクをエージェントへ割り当てる瞬間 | `coordinator::overlap_reason` / `overlap_split` (GUI から到達) | **未測定** |
| ② | **実行中の強制** | エージェントがファイルを書く直前 | `crate::lease::gate` (`zai hook` / エディタ自身の保存 / シェル経由の書き込み) | **測定済み (下記)** |
| ②' | **実行中の強制 (行域)** | 同上。粒度がファイル → 行域になる | `src/region.rs` → `lease.rs` / `czero.rs` / `coedit.rs` / `zai lease claim [--shift]` (`src/cli.rs`) | **測定済み — 出荷物 0.14.0 で §3.9 / §3.11.4 / §3.12** |
| ③ | **統合** | ブランチをマージする時 | `zai train plan` / `run --dry-run` (`src/train.rs`) | **測定済み (下記)** |
| ④ | **共有面の自動解決** | 全員が触らざるを得ないファイル (設定一覧・`mod` 宣言など) | `zai merge-driver` (`src/union.rs`) | **測定済み — この合成リポジトリでは効果ゼロ** |

### 正直に言うと

- **① は動いているが、この文書には数字が無い。**`coordinator` のテストは
  「重なったら配らない」を単体で固定しているが、**エンドツーエンドで
  「配り方を変えたら衝突が何件減ったか」は測っていない。**
- **③ は実装されたが、衝突の総量は 1 つも減らない。**測ると
  **ハンク数は素朴な順序と完全に同じ**で、減るのは「衝突で止まる回数」だけ。
  さらに **書き手が worktree を持っている間は 1 本も計画に載らない**
  (`train::candidates` が他の worktree の握っている枝を外す仕様)。
  つまり**走っている最中には使えない**。
- **②' は 0.14.0 で配線された。**`src/region.rs` は `lease.rs` /
  `czero.rs` / `coedit.rs` から呼ばれ、`zai lease claim 'a.rs#L1-40'` は
  行域として解釈される (`src/cli.rs`)。`--shift` / `--max-shift` も
  同じ経路に居る。§3.8 で skip だった段 C / 段 ins は §3.9 / §3.11.4 で
  出荷物のまま測れている。**0.15.0 で 64 体でも拒否 0 になった**
  (ずらし上限を混雑ぶんだけ広げる `lease::shift_ceiling`。§3.11.2 / §6-1)。
- **②' の保護は行番号ではなく錨で守っている。** 確保の瞬間に
  先頭行・末尾行の中身を覚え (`region::capture_anchor`)、判定のたびに
  取り直す (`region::resolve`)。**この錨が誤マッチして二重配布を起こしていた**
  ので、いまは「動いたと読めたら、その読みを採らない」(§3.12.2)。
- **④ は実装されたが、この合成リポジトリでは 1 件も吸収しなかった。**
  `zai merge-driver` を挿しても衝突数はベースラインと 1 桁も変わらない
  (下記 3.7)。**配管の問題ではない** — 同じ場所へ参照ドライバ
  (`git merge-file --union`) を挿すと 18 ハンクが 0 になるので、
  差はドライバの方針 (共有面の構文だけを吸収し、それ以外は通常の 3-way
  へ譲る) にある。CLAUDE.md が言う `config.rs` / `keybinds.rs` のような
  **実際の共有面での効果は、この合成ベンチでは測れていない。**

## 3. 実測

計測環境: macOS 26.5.2 (Darwin 25.5.0) / Intel Core i9-9980HK 8C16T / 64GB /
git 2.47.1 / Python 3.12.7 / `zai` 0.12.0 release (`5b2c66f`) / 2026-08-10。
全て `--seed 20260810` (既定)。合成リポジトリは 1 ファイル 6 ブロックで、
**同じファイルでも別ブロックなら git は自動マージする** (重なり = 衝突ではない)。

### 3.1 ベースライン — 「使わなかったら何件衝突するのか」

`tools/conflict-zero-bench.sh --writers 8 --files 48 --overlap <r>`

| 重なり | 2 人以上が書いたファイル | 衝突したマージ | 衝突ファイル | 衝突ハンク | 衝突行 |
|---:|---:|---:|---:|---:|---:|
| 0.00 | 0 | 0 / 8 | 0 | 0 | 0 |
| 0.25 | 3 | 3 / 8 | 3 | 3 | 6 |
| 0.50 | 5 | 4 / 8 | 4 | 7 | 16 |
| 0.75 | 6 | 7 / 8 | 6 | 15 | 33 |
| 1.00 | 6 | 7 / 8 | 6 | 18 | 42 |

**これがガードを 1 つも通さない素の git worktree の姿。**
重なりが 0 なら衝突も 0 で、重なりが増えると 8 回のマージのうち 7 回まで衝突する。

### 3.2 同じ担当表にガード (②) を掛けた場合

同じ表を `zai hook` (= `crate::lease::gate`) 越しに流した結果。

| 重なり | 書けた / 計画 | ゲートが止めた | 2 人以上が書いた | 衝突ハンク |
|---:|---:|---:|---:|---:|
| 0.00 | 48 / 48 | 0 | 0 | **0** |
| 0.25 | 40 / 48 | 8 | 0 | **0** |
| 0.50 | 27 / 48 | 21 | 0 | **0** |
| 0.75 | 24 / 48 | 24 | 0 | **0** |
| 1.00 | 10 / 48 | 38 | 0 | **0** |

- **衝突ハンクは全ての重なりで 0。**
- **重なり 0.00 ではゲートが 1 件も止めていない** — 使っていない人は払わない。
- **代償は書けた件数**。重なり 1.00 では 48 件中 10 件しか書けていない。

### 3.3 同時実行数を上げた場合 (重なり 0.5 固定・ファイル数 = 書き手 × 6)

| 書き手 | ベースライン: 衝突マージ / ハンク | ガード: 書けた / 計画 | fail-open | busy-deny | ゲート p50 / p95 |
|---:|---:|---:|---:|---:|---|
| 4 | 2 / 4 · 2 ハンク | 14 / 24 | 0 | 0 | 40 / 57 ms |
| 8 | 4 / 8 · 7 ハンク | 27 / 48 | 0 | 0 | 49 / 84 ms |
| 16 | 11 / 16 · 19 ハンク | 55 / 96 | 0 | 0 | 64 / 104 ms |
| 32 | 27 / 32 · 56 ハンク | 106 / 192 | 0 | **4** | 113 / 236 ms |
| 64 | 57 / 64 · 132 ハンク | 202 / 384 | 0 | **14** | 160 / 320 ms |

ガード側の衝突ハンクは**全ての行で 0**。

- **`fail-open` (判定せずに通した回数) は全ての規模で 0。**
  `docs/conflict-bench.md` がかつて「16 体で毎回漏れる」と書いていた問題は
  `ec9a479` の 2 つの修正で解消しており、再測で再現しない。
- **代わりに 32 体以上で `busy-deny` が出る。**混雑して判定できないときに
  **止める**方へ倒した結果で (fail-closed)、再試行すれば通る。
  安全側だが、ユーザーからは「たまに拒否される」として見える。
  **32 体以上を常用するならここが次の課題。**

### 3.4 CHANGELOG 0.12.0 の「64 体・1500 書込」

`tools/conflict-bench.sh --agents 64 --files 1000` で**再現した**。

| | A: ガード無し | B: ガード有り |
|---|---:|---:|
| 計画した編集 | 1536 件 | 1536 件 |
| 実際に書けた編集 | 1536 件 | **565 件** |
| 2 人以上が書いたファイル | 464 件 | **0 件** |
| 衝突したマージ | 54 / 64 回 | **0 / 64 回** |
| 衝突ハンク | **167 個** | **0 個** |
| 壁時計: 編集フェーズ | 993 ms | 9.8 秒 |

「1500 書込」の正体は **1536 件**、「167 箇所」の正体は **167 ハンク**。
**ただし B が書けたのは 37% (565/1536)。**この代償は CHANGELOG には
書かれていなかったので、ここに書く。

### 3.5 マージドライバの配管 — 参照ドライバでの上限

段④ が「どこまでなら吸収できるか」の上限を先に見る。git のマージドライバ
契約に沿った**参照ドライバ** (`git merge-file --union %A %O %B`) は
両側を機械的に残すので、**テキスト衝突を全部飲む**。
`--writers 8 --files 48 --overlap 1.0`:

| 段 | 2 人以上が書いたファイル | 衝突マージ | 衝突ハンク |
|---|---:|---:|---:|
| baseline | 6 | 7 / 8 | 18 |
| guard (②) | 0 | 0 / 8 | 0 |
| union (④, 参照ドライバ) | **6 のまま** | 0 / 8 | **0** |

**union は「起こった衝突をマージ時に吸収する」ので、`dup_files` は減らない。**
テキストとして綺麗にマージできたことと、結果がコンパイルできることは別 —
両側を残した `let value` が 2 行並んだコードはコンパイルが通らない。
**この行が示すのは「ドライバを挿す配管が動く」ことと、吸収の理論上限だけ。**
出荷される `zai merge-driver` の実測は 3.7。

### 3.6 統合の順序付け (③) — 総量は減らない。減るのは「止まる回数」

`tools/conflict-zero-bench.sh` は同じ N 本のブランチを **`zai train plan` が
出した順序**と**作成順 (素朴)** の両方でマージし、並べて出す。
片方だけ出しても「順序付けが効いた」とは言えないため。

| 書き手 | train 順: 衝突マージ / ハンク | 素朴順: 衝突マージ / ハンク | 最初の衝突までに自動で入った本数 (train / 素朴) |
|---:|---:|---:|---:|
| 4 | 2 / 4 回 · **2** | 2 / 4 回 · **2** | 2 / 2 |
| 8 | 4 / 8 回 · **7** | 4 / 8 回 · **7** | **4** / 2 |
| 16 | **9** / 16 回 · **19** | 11 / 16 回 · **19** | **7** / 2 |
| 24 | **16** / 24 回 · **40** | 19 / 24 回 · **40** | 1 / **2** |
| 32 | **23** / 32 回 · **56** | 27 / 32 回 · **56** | 1 / **2** |

- **衝突ハンクの総量は全ての規模で完全に一致した (2 / 7 / 19 / 40 / 56)。**
  順序付けは衝突を消す仕組みではない。同じ行域が重なった組は
  どう並べても人手が要る (`train` 自身が `line_pairs` として申告する)。
- **減るのは「衝突で止まったマージの回数」** — 16 人で 11 → 9、
  24 人で 19 → 16、32 人で 27 → 23。**人が割り込まれる回数**がここ。
- **「最初の衝突までに自動で入る本数」は規模によって逆転する。**
  8〜16 人では 2 → 4 / 2 → 7 と伸びるが、**24 人以上では 2 → 1 と縮む**。
  貪欲な並べ方が高並列で裏目に出ている。**良くなる方だけ書かない。**

#### 乾式検査 (`plan --json` の `dry` / `run --dry-run`) はよく当たる

| 書き手 | 予想が触れた段 / 当たり | 最初に衝突する枝 | 衝突ファイルまで |
|---:|---:|---|---|
| 4 | 3 / 3 | 一致 | 一致 |
| 8 | 5 / 5 | 一致 | 一致 |
| 16 | 8 / 8 | 一致 | 一致 |
| 24 | 2 / 2 | 一致 | 一致 |
| 32 | 2 / 2 | 一致 | 一致 |

`train run --dry-run` の終了コードは全ての規模で 1 (= 衝突で停止する見込み)
で、実際の結果と一致した。**予想は「最初に衝突した段で打ち切る」仕様**なので、
分母は予想が触れた段だけ。そこは 5 規模すべてで 100% 当たっている。

#### 使えない条件が 2 つある (どちらも仕様だが、数字として残す)

1. **書き手が worktree を持っている間は 1 本も計画に載らない。**
   実測で計画 0 本 / 他の worktree が握って外された枝が書き手と同数
   (8 人なら 8 本、32 人なら 32 本)。統合順を出せるのは
   **エージェントが worktree を手放した後**。
2. **24 本 (`train::MAX_BRANCHES`) を超えると、超えたぶんは計画に載らない。**
   32 本を投げると計画は 24 本になる。**当時は `plan.dropped` が 0 と嘘をついていた**
   (`train::touches_from_repo` が数える前に `take(MAX_BRANCHES)` していた)。
   いまは数えてから切り、`Touched::skipped` を `plan.dropped` へ足すので
   申告値は正しい。ハーネスは当時の名残で自分でも引き算して警告し、
   比較の公平のため落ちた枝を末尾へ足している。

### 3.7 共有面の自動解決 (④) — この合成リポジトリでは効果ゼロ

| 書き手 | baseline: 衝突マージ / ハンク | `zai merge-driver`: 衝突マージ / ハンク |
|---:|---:|---:|
| 8 | 4 / 8 · 7 | 4 / 8 · **7** |
| 16 | 11 / 16 · 19 | 11 / 16 · **19** |
| 32 | 27 / 32 · 56 | 27 / 32 · **56** |

**1 件も吸収していない。**ただしこれは配管の失敗ではない —
同じ場所へ参照ドライバ `git merge-file --union %A %O %B` を挿すと
`--overlap 1.0` で 18 ハンクが 0 になる (3.5)。差はドライバの方針で、
`zai merge-driver` は共有面の構文 (一覧・宣言ブロック) だけを吸収し、
それ以外は通常の 3-way へ譲る。**この合成リポジトリの中身は

**このベンチでは測れていない。**

### 3.8 行域オーナーシップ (②') — 拒否は消える。衝突は**もともと 0 だった**

`tools/coedit-bench.sh --agents 1,4,8,16,32,64 --lines 2000`。
計測環境は §3 と同じ機械 (macOS 26.5.2 / git 2.47.1 / `zai` 0.13.0) で
2026-08-10、種は既定の `20260810`。

**土俵が §3.1〜3.7 と逆であることに注意。**ここでは合成リポジトリに
**ファイルを 1 個しか置かない**。ファイル単位の所有だと並列度が構造的に
1 に潰れる状況を作って、行域が何を取り戻すのかだけを見る。

段は 4 つ: **A** 素の git (保護なし) / **B** ファイル単位の所有
(`zai lease claim 'src/wide.rs'`) / **C** 出荷物の行域所有
(`zai lease claim 'src/wide.rs#L10-40'`) / **Cref** 行域所有の**参照ゲート**
(`region::spans_too_close` をハーネス内に写したもの)。
**C は 12 段すべて skip した** — 理由は 3.8.3。

#### 3.8.1 離した行域 (`--layout disjoint`) — 衝突は 3 段とも 0。差は拒否だけ

安全帯以上に離れた行域を配った場合。担当表の「近すぎる組」は全規模で 0。

| 体数 | A 完了 | A 拒否 | A ハンク | B 完了 | B 拒否 | Cref 完了 | Cref 拒否 | Cref ハンク |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 0 | **0** | 1 | 0 | 1 | 0 | **0** |
| 4 | 4 | 0 | **0** | 1 | 3 | 4 | 0 | **0** |
| 8 | 8 | 0 | **0** | 1 | 7 | 8 | 0 | **0** |
| 16 | 16 | 0 | **0** | 1 | 15 | 16 | 0 | **0** |
| 32 | 32 | 0 | **0** | 1 | 31 | 32 | 0 | **0** |
| 64 | 64 | 0 | **0** | 1 | **63** | 64 | **0** | **0** |

統合後に残った担当の数は、A と Cref では**完了数と完全に一致**した
(64 体なら 64 体ぶんの変更が最終ツリーに残る)。B は全規模で **1**。

- **一番大事な数字は「A のハンクが全規模で 0」。**
  離れた行域なら、**保護を 1 つも通さない素の git がもとから衝突しない**。
  行域オーナーシップは git にできないことをしているのではない。
- **効いているのは B との比較だけ。** 1 ファイルに 64 体をぶつけると、
  ファイル単位の所有は **63 件を拒否して 1 件しか通さない**。
  行域なら **拒否 0 件・64 件全部が通る**。
  **拒否 63 → 0、完了 1 → 64。これがこの機能の価値の全部である。**
- **B が規模によらず「完了 1」なのは偶然ではない。**
  対象ファイルが 1 個しか無いのだから、ファイル単位の所有では
  並列度は定義上 1 になる。§3.2 の表 (48 ファイル) で
  「重なり 1.00 でも 10 件書けた」ように見えたのは、
  **ファイルが 48 個あったから**にすぎない。

#### 3.8.2 近づけた行域 (`--layout crowded`) — 保護は効く。ただし総作業量は増えない

わざと重ねて配った場合 (幅 6 行の域を 2 行間隔で並べる)。
**保護が本当に効くかの裏取り**がここ。

| 体数 | 近すぎる組 | A 衝突枝 | A ハンク | A 衝突行 | A 人手 | A 生存 | B 完了=生存 | B 拒否 | Cref 完了=生存 | Cref 拒否 | Cref 人手 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0 | 0 | 0 | 0 | 0 | 1 | 1 | 0 | 1 | 0 | 0 |
| 4 | 6 | 3 | 3 | 60 | 3 | 1 | 1 | 3 | 1 | 3 | **0** |
| 8 | 22 | 6 | 6 | 120 | 6 | 2 | 1 | 7 | 2 | 6 | **0** |
| 16 | 54 | 12 | 12 | 240 | 12 | 4 | 1 | 15 | 4 | 12 | **0** |
| 32 | 118 | 24 | 24 | 480 | 24 | 8 | 1 | 31 | 6 | 26 | **0** |
| 64 | 246 | **48** | **48** | **960** | **48** | 16 | 1 | 63 | **9** | 55 | **0** |

- **保護は効いている。** Cref のハンクは全規模で 0、人手も 0。
  同じ担当表で素の git は 64 体で **48 ブランチが衝突し、960 行を人に読ませ、
  48 回の手作業を要求する**。
- **しかし「行域にすれば得」ではない。**64 体の `crowded` で最終ツリーに
  残った担当は **A が 16、Cref は 9** で、**素の git の方が多い**。
  A はそれを **48 回の衝突解決**と引き換えに得ている。
  Cref は 9 体ぶんを**人手 0 回**で得る。
  **総作業量が増えるのではなく、コストが「統合後の人手」から
  「書き込み前の拒否」へ移動しているだけ**である。§1 の「意味しないこと」2 の実体。
- **安全帯は明確に過剰防衛である。**64 体で「近すぎる」と判定される組は
  **246 組**あるが、素の git が実際に衝突したのは **48 ブランチ**。
  fail-closed として正しいが、**断りすぎている分は数えておく必要がある**
  (§5-9)。
- B は `crowded` でも完了 1 のまま。**近さに関係なく 1**。

**これを検査せずに走らせると、静かな嘘になる。**0.13.0 の `lease claim` は

さらに悪いことに、これは単なる未実装ではなく**後退**である:

#### 3.8.4 効かなかったもの・悪化したものも書く

- **参照ゲートのゲート待ちは、規模とともに露骨に伸びる**
  (64 体で p50 **1002ms** / max **1852ms**)。
  **ただしこれは行域判定の費用ではない。**参照ゲートは awk のプロセス起動と
  `mkdir` のスピンロックで書いてあり、測っているのは**ハーネスの費用**である。
  同じ規模で出荷物のファイル所有 (B) は p50 **153ms**。
  **行域判定そのものの費用**は §3.14 で分けて測った。
- **`disjoint` の統合時間は、行域にしても 1 ミリも減らない。**
  64 体で A が 11.3 秒、Cref が 12.7 秒。マージする枝の数が同じなので当然で、
  **B の 1.3 秒が速いのは 63 本を捨てているからにすぎない**。
  「行域にしたら統合が速くなる」とは言えない。
- **`git merge-tree --write-tree` の予測は 36 段すべてで 100% 一致した**
  (64 体なら 64/64)。予測と実際が食い違った段は 1 つも無い。
  git 2.38 未満では検算そのものを skip する。
- **1 体のときは 3 段とも完全に同じ数字になる** (完了 1 / 拒否 0 / 衝突 0)。
  **並列度 1 では、どの所有方式にも価値は無い。**

なお、掃引の **ms 列は別のベンチが一度重なって走った状態**で取っている。
件数の列は種を固定すれば決定的で、`--agents 8` の清浄な再実行で
`crowded` の 6 枝 / 6 ハンク / 120 衝突行 / 生存 2、Cref の完了 2 / 拒否 6 が
**完全に一致することを確認した**。ms 列は目安として読むこと。

#### 途中で見つかった回帰 — 単体テストでは捕まらなかった

最初の再測定で、ハーネスの能力検査が **「重なった 2 つの行域が両方通った」** を検出して
段 C を skip した。単体テストは 4178 件すべて緑だったので、**実バイナリを回さなければ
気付けなかった**。

再現は 1 行: 1 行しかないファイルへ `a.rs#L1-10` を確保した直後に `a.rs#L5-15` が通る。
原因は錨の解決で、(1) 記録した行数を現在のファイルの行数で頭打ちにしていたこと、
(2) 末尾の錨が空（= 確保時に EOF を超えていた）のとき域を先頭 1 行へ畳んでいたこと。
**EOF を超える確保は「これから書く場所の予約」で正しい状態**なので、縮めると予約が消えて
別人が同じ場所を取れる。`region::tests::eofを超える予約は縮まない` が番人。

**この 1 件は、ハーネスが「行域を理解しているか」を毎回検査してから測る作りだったから
見つかった。** 検査を省いていれば「全員書けて衝突 0」という綺麗な数字がそのまま出ていた。

### 3.10 安全帯の下限 — 実測で 3 → 1（`coedit` のみ）

`SAFE_BAND = 3` の根拠は「git の diff の既定文脈が 3 行だからハンクが畳まれる」と
説明されていたが、**これは誤りだった**。実 git で経路別に測った下限:

| 経路 | 相手=置換 | 相手=削除 | 相手=挿入 | 下限 |
|---|---|---|---|---|
| `git merge-file -p` | 1 | 1 | 1 | **1** |
| `git merge-tree --write-tree` / `git merge` | 1 | 1 | 1 | **1** |
| `git apply`（文脈 3 行） | 3 | 3 | 3 | **3** |

3 行は*表示*の話で、xdl_merge が衝突を出すのは変更ハンクが重なるか隣接するときだけ。
myers / minimal / patience / histogram の 4 アルゴリズムすべてで同じ。
**`SAFE_BAND = 3` は正しいが、由来はパッチ適用（`git apply`）だった。**

> ⚠ **この表は「変更 2 つを 1 組で測った」ものである。** 組の中では反復的な内容でも
> 崩れない（§3.16 で周期 1〜12 を測り直して確認した）が、**「全部の組が帯を満たす」
> から「全部まとめてマージしても綺麗に通る」は導けない**。§3.16 を必ず併せて読むこと。

`coedit`（一撃マージの証明）は `git merge` しか使わないので、`MERGE_ONLY_BAND = 1` を使う:

| | 帯 1（新既定） | 帯 3（旧既定・同一ケース列） |
|---|---:|---:|
| 回したケース | **240** | 240 |
| 証明が立った | **122** | 72 |
| 実 git で綺麗だった | **122（全部）** | 72（全部） |
| **見逃し** | **0** | **0** |
| 過剰報告 | 18 = **15.3%** | 68 = **40.5%** |

帯 3 では止まっていた **50 件**が新たに証明でき、全件が実 git で綺麗だった。
Docker Linux（別 git 版）でも数字が 1 件違わず一致。
残る 15.3% は帯のせいではなく、(a) 挿入点を直前 1 行として持つぶんの厚み 16 件、
(b) 2 本が同じ行を同じように削って git が同一変更として畳んだ 2 件。

**`git apply` / `git am` / `format-patch` / `rebase --apply` を通す経路が 1 つでも
生えたら `SAFE_BAND` へ戻す必要がある。** この条件は `coedit` のモジュール doc に書いてある。

### 3.11 交渉 (`--shift`) と挿入点 — 「入るのに断った」を切り分ける

計測環境: macOS 26.5.2 / git 2.47.1 / 2026-08-11 / 種 `20260810` / 安全帯 3 行。
出荷物は `zai` **0.14.0** (`ZAIVERN_BIN=<repo>/target/debug/zai`)。
`--agents 64 --lines 2000 --mode all`。

#### 3.11.1 供給と需要 — 53 件は容量の問題ではない

§3.9 の「詰めた域 / 完了 11 / 拒否 53」を見ても、**空きが無くて断ったのか、
空いているのに断ったのか**が分からない。ハーネスが担当表から毎回出すようにした:

| layout | 要求行数計 | 要求の幅 | 互いに素に置くのに要る行数 | ファイル | 空き | 判定 |
|---|---:|---:|---:|---:|---:|---|
| 離した域 | 896 | 1962 | 1085 | 2000 | 1104 | 入る |
| 詰めた域 | **384** | **132** | **573** | **2000** | **1616** | **入る** |

64 体が要求しているのは **934〜1065 行の 132 行ぶん**にすぎない。
互いに素に置くのに要るのは `384 + 63x3 = 573 行`で、ファイルは 2000 行ある。

> **断られた 53 件は、空きが無いからではない。誰もずらしていないからである。**
> 段 C の `zai lease claim` は要求どおりの行域を取りに行き、重なっていたら
> 断って終わる。**空いている 1616 行は 1 度も使われていない。**

#### 3.11.2 段 C+ (交渉あり) — 参照ゲートも出荷物も 64/0/0

段 C+ は段 C と**同じ担当表**を使い、`--shift` を付けて確保する。
ずらされたら**実際に取れた行域へ書く**（要求した行ではなく）。

| layout | 段 | 完了 | 拒否 | 衝突ハンク | 人手 | 生存 |
|---|---|---:|---:|---:|---:|---:|

| 詰めた域 | B ファイル所有 | 1 | 63 | 0 | 0 | 1 |
| 詰めた域 | C 行域 (出荷 0.14.0) | **11** | **53** | 0 | 0 | 11 |
| 詰めた域 | **C+ 交渉 (参照)** | **64** | **0** | **0** | **0** | **64** |
| 詰めた域 | **C+ 交渉 (出荷 0.15.0)** | **64** | **0** | **0** | **0** | **64** |

  素の git は同じ担当表で **48 ブランチが衝突し 960 行を人に読ませる**のに、
  最終ツリーに残るのは 16 体ぶんだけである。
- **出荷物の `--shift` は 0.14.0 で配線された** (`src/cli.rs` の
  `--shift` / `--max-shift` → `lease::try_claim_shift_in`)。
  能力検査は `--shift` を付けた確保が rc=0 で返り、かつ
  **標準出力の最後の行が厳密に `granted <spec>`** であることまで見る。

- **0.15.0 で 64 体でも参照ゲートと完全一致 (64/0) になった。**

  **ずらし上限の固定値**で、既定 `negotiate.max_shift = 200 行` に対し
  crowded な計画は 204〜234 行のずらしを要求していた (空きは 1868 行あった)。
  `lease::shift_ceiling` が「他人がいま実際に押しのけているぶん」を足して
  上限を広げるようにした。**測定は macOS のみ** (`tools/coedit-bench.sh
  --agents 64 --lines 2000 --layout crowded` を 6 回、6 回とも 64/0)。
  誤って「実行ごとのブレ」と読んでいた経緯は §6-1。

  ので、rc だけを見ると**段 C と同じ数字が「交渉あり」の顔で出た**。

#### 3.11.3 ずらした距離 — 64/0 の代償

「64/0 になりました」だけでは片手落ちで、**何を払って買ったのか**を並べる。
段 C+ (参照) の詰めた域・64 体:

| | 件数 | 距離 p50 | 距離 p95 | 距離 max | ファイル外へ出た件数 |
|---|---:|---:|---:|---:|---:|
| 要求どおり取れた | **5** | — | — | — | — |
| ずらして取れた | **59** | **129 行** | **253 行** | **281 行** | **0** |

- **64 件のうち 59 件は要求と違う場所を渡されている。**
  中央値で 129 行、最悪 281 行離れる。**「同じファイルの、頼んだのとは別の場所」**
  を受け取ることになるので、`negotiate::Want::max_shift` のような
  **「ここまでなら動かしてよい」の上限は必須**である
  （上限を超えたら `DenyKind::TooFar` で断るほうが、黙って 281 行動かすより正しい）。
  **0.14.0 で入った。** 既定は設定 `negotiate.max_shift` から取り
  (`lease::default_max_shift_in`)、`--max-shift <行>` で
  上書きできる。**無制限を既定にはしない。**
- **配られた行域はすべてファイル (1〜2000 行) の中に収まった** (範囲外 0)。
- 距離は**走るたびに揺れる**。担当表は `--seed` で固定できるが、
  誰が先にロックを取るかで空きの取り合いの結果が変わる（先着順の最近傍あてはめ）。
  同条件の別実行では p50 137 / p95 272 / max 281 も出た。**件数は決定的、距離は分布**。

#### 3.11.4 段 ins (挿入点) — 出荷物 0.14.0 で実測できる

`path#@120` は幅 0 で既存の行を 1 行も占有しない予約。「関数を足す」用途はこれで表せる。
64 体がそれぞれ違う挿入点を取り、自分の点の手前に 3 行ずつ足した:

| layout | 段 | 完了 | 拒否 | 衝突ハンク | 人手 | 生存 |
|---|---|---:|---:|---:|---:|---:|
| 離した域 | **I 挿入点 (出荷 0.14.0)** | **64** | **0** | **0** | **0** | **64** |
| 離した域 | I 挿入点 (参照) | 64 | 0 | 0 | 0 | 64 |
| 詰めた域 | I 挿入点 (出荷 0.14.0) | 29 | 35 | 0 | 0 | 29 |
| 詰めた域 | I 挿入点 (参照) | 29 | 35 | 0 | 0 | 29 |

- **点をばらけさせれば 64 体が全員書けて、衝突も人手も 0。**
  出荷物と参照ゲートが全列で一致した。
- **点にも安全帯は要る。** 詰めた域は点を 2 行間隔で並べるので、
  `Span::probe` が点を `[n, n]` として扱う以上 gap は 1 行しかなく、
  安全帯 3 行を割る。**64 体中 35 体が断られる。**
  幅 0 でも「隣に挿してよい」わけではない、というのが数字で出た形である
  （点だけで 64 体を置くのに要るのは `1 + 63x4 = 253 行`で、これも 2000 行に余裕で入る。
  **ここでも断りの理由は容量ではなく配置**）。
- 能力検査は `#@N` を**点として理解しているか**まで見る。
  同じ文字列の 2 本目を断るだけなら、`#@120` を**ただのパス文字列**として
  扱っていても通ってしまうので、(1) 安全帯より近い**別の**点を断るか
  (2) その点を**覆う行域**とぶつかるか、の 2 つで判定する。
  0.13.0 はどちらも素通りしたので skip になった (0.14.0 は両方で断る)。

#### 3.11.5 ハーネス自身のバグ — 「配ったもの」を検査していなかった

段 C+ の参照ゲートを足した最初の実行で、**ゲートが全員に配ったのに統合で衝突した**。
台帳を見ると `240-245` と `242-247` が同時に配られていた。

原因は awk の**未初期化変数を配列の添字に使ったこと**:

```awk
$1 == p { hs[n] = $2; he[n] = $3; n++ }   # n は未初期化 → 添字は "" (「0」ではない)
...
for (i = 0; i < n; i++) ...               # hs[0] は空。**台帳の 1 件目が判定から消える**
```

`hs[n]` は `hs[""]` に入り、`hs[0]` は最後まで空のまま。
**台帳の 1 件目だけが毎回見えなくなる**ので、重なった域を 2 人に配る。
`BEGIN { n = 0 }` の 1 行で直る。

再発を防ぐために、**実際に配られた域そのものを保存して互いに素かを検査する**列
（「近_配布」）を足した。統合が偶然きれいに通っても、ゲートが重なった域を
配っていればそこで落ちる。`negotiate::Plan::is_disjoint` と同じ自己検査である。
**要求の時点で近すぎる組（近_要求）と、配った結果で近すぎる組（近_配布）は別物**で、
後者は 0 でなければならない。

#### 3.11.6 効かなかったもの・正直に書くこと

- **参照ゲートのゲート待ちは規模とともに露骨に伸びる**
  (64 体・詰めた域で p50 1086ms / max 2047ms)。§3.8.4 と同じで、
  **これは行域判定の費用ではなくハーネスの費用**である
  （1 確保につき awk を 1 プロセス起こし、`mkdir` のスピンロックで直列化している）。
  同条件で出荷物の段 C は p50 596ms / max 739ms、段 ins は p50 314ms / max 521ms。
  **交渉そのものの費用は 1 度も測っていない。**
- **交渉しても統合は速くならない。** 詰めた域・64 体で段 C は統合 7.6 秒、
  段 C+ (参照) は 10.5 秒。マージする枝が 11 本から 64 本へ増えるので**遅くなる**。
  買っているのは並列度であって統合時間ではない。
- **段 C の出荷物と参照が 11 / 12 と 1 件ずれた**（拒否 53 / 52）。
  どちらも先着順なので、64 体の到着順が変われば境界の 1 件は入れ替わる。
  **同じ種でも件数が完全一致するとは限らない**のはここだけで、
  離した域では全段が完全一致した。
- **`--self-check` を足した。**（出荷物に `--shift` が無かった頃の話。
  いまは出荷物で段 C+ を測れるが、**ハーネス自身の健全性検査として残す**。）段 C+ の
  出荷側コード（能力検査の成功側・`granted <spec>` の解釈・**ずらした先**への
  書き込み）は 1 度も走らない。実装が届いた日に初めて動かして壊れているのでは
  計測器として使えないので、**契約だけを満たす代役の `zai`** を作って全段を通す
  経路を用意した。代役での 64 体・詰めた域は
  **完了 64 / 拒否 0 / 衝突 0 / 人手 0、ずらし 57 件・距離 p50 137 / p95 272 / max 281**
  で、参照ゲートと同じところに着く。
  **`--self-check` の数字は製品の測定値ではない**（見出しに毎回そう出す）。

### 3.12 実在のリポジトリでの証明 (`tools/anyrepo-prove.sh`)

ここまでの数字はすべて**合成リポジトリ**のものだった。合成は
「`let value = N;` を書き換える」のような都合のよい形しか作らないので、
**利用者の手元で同じことが起きる保証にはならない**。
`tools/anyrepo-prove.sh` は **実在のリポジトリを複製して**同じ実験を回す。

計測環境: macOS (Darwin 25.5.0) / `zai` 0.14.0 release。

| リポジトリ | 書き手 | 素の git | zaivern あり |
|---|---:|---|---|
| zaivern-code (Rust・追跡 259 ファイル) | 8 | **9 ファイル / 11 ハンク**衝突 | **0 / 0** (48/48 成立・拒否 0) |
| zaivern-code | 16 | **26 / 28** | **0 / 0** (96/96・30 件ずらし・拒否 0) |
| hyperframes (TS/HTML・追跡 1194 ファイル) | 16 | **26 / 28** | **0 / 0** (96/96・32 件ずらし・拒否 0) |
| 合成 `--overlap 1.0` (全員が同じファイル) | 32 | **118 / 147** | **0 / 0** (192/192・171 件ずらし) |

**素の git は言語にもファイル数にも依らずに壊れる** (Rust の 259 ファイルでも
TS/HTML の 1194 ファイルでも同じ 26/28)。書き手を 8 → 16 にすると
衝突ファイルは 9 → 26 と**線形より速く**増える。

#### 3.12.1 種を 12 通り振っての再検証

統合後に**12 種の乱数種**で取り直し、全部で
`dup_lines=0 / conflict_files=0 / granted=48/48 / refused=0`。
同条件のベースライン (保護なし) は**毎回 4〜9 行の二重書き込み**を出した。
つまり 0 は「重なりが起きない担当表をたまたま引いた」からではない。

#### 3.12.2 間欠的な二重配布の真因 — **錨の誤マッチ**

`anyrepo-prove.sh` は最初 8 回中 3 回で二重書き込みを出した。
**間欠に見えたのは乱数種のせい**で、`--seed 20260818` に固定すると
**決定的に再現した**。追ったら、原因は容量でも競合でもなく**錨**だった。

1. w1 が `README.md#L21` を確保する (錨 = そのときの 21 行目の中身)
2. w1 が 21 行目を書く → **自分の編集で自分の錨が合わなくなる**
3. w1 が同じファイルの別の域を確保し直すとき、`absorb` が
   `region::resolve` で自分の域を取り直す。錨は**似た行** (空行 / ` ``` ` /
   `---` — README には山ほどある) に当たり、**L21 が L15 へ「移動」した**
4. 21 行目が空いたことになり、w2 が**正当に**確保する → 2 体が同じ行を書いた

**台帳の最終形に重なりは残らない** (移動しただけ) ので、
台帳をいくら見ても気付けない。いちばん静かな壊れ方だった。

修正は 1 行の判断で、**取り直した結果が記録と違ったら、その読みを採らない**
(`lease::absorb` — `src/lease.rs`)。自分が書いた行を手放すより、留まるほうが必ず安全である。

**撤回した案も残す。** `hull` で「元の域と取り直した域の両方」を持たせる案を
試したが、**伸びた域が他人の既に持っている域を飲み込んで**台帳の不変条件
(どの 2 人の担当も重ならない) を壊した (種 20260818 で `overlaps=1`)。
元の場所に留めるのが、伸びも移動もしない唯一の安全な選択だった。

**追従が消えるわけではない。** 他人から見た判定は `overlaps_live` が判断の
たびに錨で取り直すので、行が本当にずれていても保護は効く。ここで動かさないのは
*自分の帳簿の座標*だけである。

同じ commit で**ロックの相互排除**にも穴が見つかった。置き去りロックの奪取が
`remove_file` + `create_new` の **2 手**だったので、同じ置き去りを見た 2 人目が
**1 人目の張りたてを消して**同時に臨界区間へ入り得た (lost update = 二重配布と
取りこぼしの両方を説明する)。奪取を `rename` の 1 手にして直列化し、
ロックに token を持たせて**自分が張ったものだけ**外すようにした。

詳細は [docs/anyrepo-proof.md](anyrepo-proof.md)。

### 3.14 行域判定そのものの費用 (`tools/region-cost.sh`)

かつて §5 に「参照ゲートの遅延はハーネスの遅延であって実装の遅延ではない
— ただし分けて測っていない」と書いていた穴を埋める。
**ハーネスの費用を測って差し引く**。

| 測る対象 | ハーネス | 判定そのもの | ハーネス率 |
|---|---:|---:|---:|
| 予約一覧 N=800 の重なり判定 | 0.23ms | **3.67ms** | 5.4〜9.1% |
| `text.resolve` 16000 行 | 2.23ms | **8.91ms** | 16.6〜24% |
| `text.anchor` 16000 行 | 2.11ms | **4.19ms** | **最大 42.6%** |

**引かないと 4 割が嘘になる。** 判定回数は入力を 2 倍にするとちょうど **×2.00**
で線形。一方**同じ点の時間は ×1.31〜2.78 に散った** — CLAUDE.md の
「絶対時間で性能テストの線を引かない」の実物である。

#### 測って初めて分かった二次の判定

`region::conflicting_pairs` は総当たりで **O(N²)** だった。
**互いに素な 800 件で 319,600 回 / 9,467ms**。開始行で整列してから掃引する形に
直して **0 回 / 3.67ms (2581 倍)**。さらに `is_disjoint` に**最初の 1 組で
降りる**早期脱出を入れたので、全員が重なる最悪ケースは
**319,600 回 → 1 回**になる (`region::conflicting_pairs` / `region::is_disjoint` — `src/region.rs`)。

**「遅い」と言われたわけではない。**「費用を測る」ためのハーネスを書いたら
出てきた。詳細は [docs/region-cost.md](region-cost.md)。

### 3.15 リポジトリの形ごとに何が保証されるか

### 3.16 帯だけでは足りなかった — 反復的な内容と交錯 (`tools/merge-band-probe.sh`)

計測環境: macOS 26.5.2 (darwin 25.5.0) / **git 2.47.1** / 2026-08-11。
`zaivern` を 1 度も呼ばない。**素の git だけ**で測る。

#### 3.16.1 何が壊れていたのか

§3.10 の下限表は正しい。壊れていたのは**そこから先の推論**である:

> 「全部の組が帯を満たす」⇒「全部まとめてマージしても綺麗に通る」

これは成り立たない。反証 (`--mode bracket`、周期 6 の Markdown 600 行):
A が **17 行目**、B が **5 / 13 / 25 行目** — どの組も 4 行以上離れていて
`SAFE_BAND = 3` を満たすのに、`git merge` は衝突する。

| 形 | unique | fences | blank | generated | repeat |
|---|---|---|---|---|---|
| A={17} B={13,25} | clean | clean | clean | clean | clean |
| **A={17} B={5,13,25}** | clean | **衝突** | clean | **衝突** | **衝突** |
| A={17} B={1,13,25,33} | clean | clean | clean | clean | clean |
| A={100} B={88,96,108} | clean | clean | clean | clean | clean |

#### 3.16.2 原因 — ort は diff アルゴリズムを histogram に固定している

`man git-merge` の `diff-algorithm` の項に**そのまま書いてある**:

> Note that **ort specifically uses diff-algorithm=histogram**,
> while recursive defaults to the diff.algorithm config setting.

`git merge` の既定戦略は 2.34 以降 ort なので、**`-X diff-algorithm=myers` を
渡しても内容マージは histogram のまま**である (実測でも 4 つ全部で同じ結果)。
histogram は本文が反復的だと同じ側の複数の変更を 1 つの巨大なハンクへ畳む。

**§3.10 の測定が myers 相当の経路も混ぜていたのは、ハーネスの欠陥だった。**
`git merge-file` は `XDL_MERGE_ZEALOUS_ALNUM` + myers を使うので `git merge` より
**寛容**で、上の失敗ケースを 3 つとも clean と答える。実 git の答えを取るときは
`git merge` / `git merge-tree --write-tree` を使うこと (`region::tests::Lab::merge_tree`)。

#### 3.16.3 帯を広げても直らない (ここが肝)

周期 6・16 体・1 行ずつ・**ランダム順**で間隔を振ったときの衝突マージ数:

| 本文 | gap=1 | gap=3 | gap=8 | gap=16 | gap=32 | gap=64 |
|---|---:|---:|---:|---:|---:|---:|
| 周期 1 (全行同一) | 9 | 5 | 2 | 0 | 0 | 0 |
| 周期 6 | 7 | 9 | **10** | **9** | 0 | 0 |
| unique | 0 | 0 | 0 | 0 | 0 | 0 |

**間隔 16 行でも 9 件衝突する。** 帯は定数なので、この形には原理的に届かない。

#### 3.16.4 効いたもの (2 つ)

**(a) 混ぜる順を行番号の昇順にする。** 直列マージでは `ours` に「先に入れた全員」が
積み上がるので、名前順で流すと**まだ入れていない枝が既に入った枝に挟まれる**形が
順番のせいで生まれる。`--mode order` (16 本・1 行ずつ):

| 本文 | 間隔 | 昇順 | 降順 | 入れ替え |
|---|---:|---:|---:|---:|
| unique | 2 / 4 / 9 | 0 | 0 | 0 |
| fences | 2 / 4 / 9 | **0** | 0 | 2 / 1 / 2 |
| repeat | 2 / 4 / 9 | **0** | 0 | 3 / 1 / 1 |

`coedit::integrate` は `names.sort()` (**名前の辞書順**) で流していた。
`coedit::merge_order` を入れて行番号の昇順にした。単調な順なら降順でもよいが、
昇順に固定して決定性を取っている。

**(b) 錨 — 隣り合う他人の域の間に「ファイル内で唯一の行」があるか。**
交錯 (片方が相手を挟む) は順番では直らない (両向きで測って両方衝突した)。
一方、その隙間に**ファイル内で 1 回しか出てこない行が 1 本あるだけで**、
上の失敗ケースは周期 1 / 3 / 6 のすべてで綺麗に通った (15/15)。
diff は一意な行を必ず対応させるので、ハンクがそこを越えられない。

無作為な配置 400 通り (周期 1〜12 × 錨の密度 0〜100%、置換のみ) で:

| 判定 | 通した | うち実際に衝突 | 断った | うち実際に衝突 |
|---|---:|---:|---:|---:|
| 錨だけ (順不同) | 127 | **0** | 255 | 79 |
| **昇順 + 交錯時のみ錨** | **173** | **0** | 209 | 76 |
| 昇順 + 交錯を全部断る | 79 | **0** | 303 | 76 |

3 つとも**見逃し 0**。いちばん通すのが「昇順 + 交錯時のみ錨」なのでこれを採った
(`region::interleave_safe` / `coedit::clashes_with`)。

実リポジトリでは錨は潤沢にある。**このリポジトリの `src/**.rs` + `docs/*.md` +
`tools/*.sh` の 157 ファイル 319,004 行で、ファイル内で唯一の行は 60.7%**
(最も低い `src/jsonc.rs` でも 47.1%)。2 行以上の隙間にはまず錨が入る。

#### 3.16.5 それでも残る限界 (伏せない)

1. ~~**削除・挿入が混ざると、昇順でも崩れる組がある。**~~ **潰した (§3.16.7)。**
   当時は「削除・挿入を混ぜた 200 通りで 3 件衝突したが、錨の判定が全部
   断っていた」と書いていた。**その読みは間違っていた** — 標本を 6000 通りへ
   増やしたら、当時の判定 (交錯しているときだけ錨) は **35 件見逃していた**。
   門を「同じファイルの 2 人には必ず壁」へ強めて **0 件**になった。
2. ~~**錨が 1 本も無いファイルでは、交錯した 2 人に行域を配れない。**~~
   **断る以外の答えを入れた (§3.16.8)。** 錨が薄いだけのファイルなら
   `region::anchor_fit` が壁のある空きへずらして配る。錨が
   **1 本も無い**ファイルだけは今も断る (そこには置ける場所が存在しない)。
3. **判定はかなり過剰に断る。** 無作為 6000 通りのうち 2639 通りを断ったが、
   実際に衝突したのはそのうち 272 通りだけ (10.3%)。ただしこの合成本文は
   錨の密度 0% を 1/3 の確率で引く**極端に敵対的な標本**で、実リポジトリの
   60.7% とはかけ離れている。**実ファイル (`--real src/region.rs`) の 800 通り
   では、断ったのは 6 通りだけ (0.75%)。**
4. **`git merge` の答えは局所的な性質では決まらない。** 同じ配置・同じ周期でも、
   **ファイル末尾に一意な行が 1 本あるかどうか**、**ファイルの総行数**で
   答えが反転する (周期 6・A={17}/B={5,13,25} は 200/300 行で衝突、
   400/600 行では通る。末尾に一意な行を足すと 200〜600 行のどこでも衝突する)。
   つまり**「内容の周期を測って帯を決める」方向の対策は原理的に当たらない**。
   これが「配る前に実際にマージしてみる」案を採らなかった理由でもある —
   **配る時点では、その担当が何を書くかまだ決まっていない。**

#### 3.16.6 保証の線引き (これが結論)

| 主張 | 成り立つか | 依存するもの |
|---|---|---|
| `dup_lines = 0` (同じ行を 2 人に配らない) | **常に成り立つ** | 台帳だけ。内容に依存しない |
| `conflict_files = 0` (マージが一撃で通る) | **条件付き** | 帯 + **壁 (錨)** + 昇順。反復的な内容では断ることがある |


**関所も同じ 3 条件で判定する。** `zai lease claim` / `zai guard check` /
`zai negotiate offer` / czero の危険地帯は、帯だけでなく**壁**まで見る
(配線前は `guard check --staged` が交錯を rc=0 で素通りさせていた)。
元テキストが読めないときは**断る** — 帯だけへ落とすと、いちばん効いてほしい場面
(生成物・巨大データ・反復的な大ファイル = ちょうど読み取り上限を超えるもの) で
だけ静かに緩むため。
`Proof::disjoint` が主張しているのは**下の段**である。`coedit::integrate` は
証明が立った後も `merge-tree` の乾式検査を全枝に通してから初めて参照を動かすので、
**判定が外れても壊れるのは「一撃だった」という主張だけで、履歴は 1 バイトも動かない**。

#### 3.16.7 交錯していなくても壁が要る (穴 1 を潰した)

計測環境: macOS 26.5.2 (darwin 25.5.0) / git 2.47.1 / 2026-08-12。
`tools/merge-band-probe.sh --mode random --trials 2000 --seed <種>`。
**zaivern を 1 度も呼ばない。素の git だけで測る。**

§3.16.5 の 1 は「削除・挿入を混ぜた 200 通りで 3 件衝突したが、錨の判定は
全部断っていた」と書いていた。**標本が小さすぎた。** 削除・挿入・置換を混ぜた
無作為配置を **6000 通り** (3 種 × 2000) 回すと:

| 判定 | 通した | 見逃し (通したのに衝突) | 断った | 断ったうち実際に衝突 |
|---|---:|---:|---:|---:|
| 帯だけ | 5492 | **272** | 306 | 0 |
| 交錯のときだけ壁 (0.16.0 まで) | 4136 | **35** | 1662 | 237 |
| **常に壁 (いま)** | **3159** | **0** | 2639 | 272 |

**当時の判定は 35 件見逃していた。** 原因は「交錯していなければ帯で足りる」と
いう門で、その理屈は*置換だけ*なら正しい。削除と挿入は行数を変えるので
histogram は「同じ側の変更をどこへ置くか」を選び直せ、周期的な本文では
その自由度がファイル全体に及ぶ。

いちばん短い反証 (周期 6 の本文 300 行・**末尾に一意な行を置かない**):

> A が 126〜127 行目を置換 / B が 32 行目の手前へ 1 行挿入
> — **94 行離れていて交錯もしていない**のに `git merge` は衝突する。

`region::tests::実gitで交錯していなくても壁が要ることを固定する` が実 git で
固定している。壁 (= その間にある「ファイル内で唯一の行」) を **1 本**植えると
同じ組が綺麗に通る (`実gitで壁を一本置けば交錯していない組も通る`)。

**何を失ったか。** 同じ 6000 通りで通す数は **4136 → 3159 (−23.6%)**。
ただしこの合成本文は錨の密度 0% を 1/3 の確率で引く極端に敵対的な標本である。
**実ファイルでは 1 件も減らない**:

| 素材 | 試行 | 旧門が通した | 新門が通した | 見逃し |
|---|---:|---:|---:|---:|
| 合成 (周期 1〜12 × 錨密度 0〜100%) | 6000 | 4136 | 3159 | 0 |
| **`src/region.rs` (実ファイル)** | 800 | **792** | **792** | 0 |

門は `region::needs_wall` 1 か所。`coedit` / `lease` / `guard` / `negotiate` /
`czero` の 5 経路が同じ関数を通る。

**同時に塞いだ穴がもう 1 つある。** `lease` には「どちらも 1 本しか持って
いないなら交錯は起こり得ない」と降りる近道があった。交錯は確かに起こり得ない
が**壁は要る**ので、**いちばん普通の形 (2 人が 1 本ずつ) だけが素通り**して
いた。番人は `lease::span_tests::一本ずつでも壁が無ければ断る`。

**断り方が広がったことの副作用**: 本文を読めないファイル (存在しない・
バイナリ・読み取り上限超え) では、**同じファイルの 2 人目を必ず断る**ように
なった。fail-closed の一貫した結果だが、以前は「交錯していなければ通る」で
逃げられていた。`zai czero verify` の実証もこれに引っかかったので、実在する
ファイルを置いてから測るよう直した (`czero_init::trial_regions`)。

**費用も増えた。隠さない。** 錨を数えるのが「交錯している組があるファイル
だけ」から「2 人以上が触ったファイルすべて」へ広がるので、本文を読む回数が
増える。網羅試験 (240 ケース) では `git show` が **0 → 229 回**になった。
**ファイルごとに撃つのをやめ、`git cat-file --batch` の 1 回へまとめた**
(`coedit::base_texts` / `parse_cat_file_batch`) ので、実測は **229 → 1**。

#### 3.16.8 断る代わりにずらす (穴 2 への答え)

錨が薄いファイルで 2 人目を断るのは**安全ではあるが、空いている行が大量に
あるのに誰にも配らない**という形の損である。`region::anchor_fit` は要求を
同じ長さのまま、**帯を満たし、かつ境目に壁がある**いちばん近い位置へずらす。
見つからなければ `None` (= そこには本当に置ける場所が無い)。

* 距離が同じなら下方向を先に採る (**決定的**。64 体が同時に呼んでも同じ答え)
* 挿入点は挿入点のままずらす
* 探す幅は既定でファイル全体 — 固定の上限を置くと、大きいファイルでだけ
  静かに諦める
* `coedit` は断った組の `Clash` にずらし先を載せて画面へ出す
  (`Clash::shift` → 「… → B を L67-69 へずらせば通ります」)

**採らなかった案 (再提案されるので残す)**:

| 案 | 採らなかった理由 |
|---|---|
| 統合順で直列化する | **効かない**。順番は §3.16.4 (a) で既に効かせてあり、その上でなお残っているのがこの穴。§3.16.7 のとおり上下に分かれた組でも衝突する |
| 境目へ一意な行を注入する | 効くことは実測済み (`実gitで錨を一本置けば同じ組が通る`) が、**他人の本文を勝手に書き換える**。錨は元の本文から数える、という `resolve` の前提も壊す。提案に留め、自動では当てない |
| ファイル単位へ粒度を落とす | 「2 人目を断る」と同じことなので、並列度は 1 も増えない |

**効き目 (実測)**。`tools/merge-band-probe.sh --mode random --trials 2000
--seed 777` は、断った組のうち動かせる形 (相手が 1 本) を全部ずらしてみて、
**ずらした先を実 git でマージし直す**:

| 断った組のうち動かせる形 | ずらし先が見つかった | 証明が立った | **実 git でも綺麗** |
|---:|---:|---:|---:|
| 243 | 28 (11.5%) | 28 | **28 (100%)** |

**見つかった 28 件は 28 件とも実 git で綺麗に通った。** 残り 215 件は
「ずらす先が無い」= 錨が 1 本も無い本文で、そこは断るのが正しい。
11.5% という数字が低く見えるのは、この合成本文が錨の密度 0% を 1/3 の確率で
引く**極端に敵対的な標本**だからである。

**まだ測っていない**: 64 体のベンチ (`tools/coedit-bench.sh`) で端から端まで
測っていない。いまあるのは上の実測と単体テスト、そして `coedit` の画面に
提案が出るところまでである。

### 6-1. 「`--shift` の取りこぼしは実行ごとのブレで、稀」— 否定

**当時こう書いていた** (2026-08-11 / 0.14.0 / §3.11.2 と
[docs/xplat-bench.md](xplat-bench.md) §「64 体の `c+`」):

> crowded / 64 体を 6 回まわすと 4 回は 64/64 だが、macOS 58/64 (6 件拒否)・
> Linux 47/64 (17 件拒否) が各 1 回出た。片方の OS の問題ではない。
> 32 体以下では 1 度も出ない。

**否定した測定** (`tools/coedit-bench.sh --agents 64 --lines 2000
--layout crowded` を 6 回):

```
51/13 · 54/10 · 53/11 · 55/9 · 54/10 · 54/10
```

**6 回中 6 回で 9〜13 体が締め出されていた。**「4 回は 64/64」は再現しない。

**本当の原因**は競合状態でも実行ごとのブレでもなく、**固定の上限値**だった。
既定 `negotiate.max_shift = 200 行` に対し crowded な計画は 204〜234 行の
ずらしを要求しており、空きは 1868 行あった。断る理由はどこにも無かった。

**直したもの** (0.15.0): `lease::shift_ceiling` が上限を「空いている
ファイルでの上限」へ降格し、他人がいま実際に押しのけているぶんを足す。
`negotiate::allocate` も入口で同じ広げ方を通す。直した後の 6 回は**すべて
64/0** (参照ゲートと完全一致)。

**この誤診が起きた理由も残す。** `lease` 側の 64 体試験は `max_shift = None`
(上限なし) で 64/64 を主張していたが、出荷経路は `Some(200)` を渡す。
**上限を外した経路しか測っていなかった**ので、単体テストは緑のまま
出荷物だけが落ちていた。

### 6-2. 「昔の `--shift` は未知のフラグとしてファイル名になる」— 解消済み

0.13.0 は `--shift` を知らず、確保パターンとして黙って飲んでいた。
`reject_unknown_flags` (`src/cli.rs`) が `--` より前の未知の旗を断るように
なったので、もう起きない。当時は **rc だけを見て「交渉できた」と数えると、
段 C と同じ数字が「交渉あり」の顔で出る**という形の嘘が起き得た。
能力検査 (§3.11.2) を省いてはいけない理由はこれである。

### 6-3. 「互いに素な行域なら綺麗にマージできる」— 否定

**当時こう書いていた**: 「どのリポジトリでも競合ゼロ」。
**否定した測定**: 反証役の独立検証で **126 回中 42 回は衝突が残った**。

**所有の主張のほうは崩れていない** — 「同じ行を 2 人に配らない」は
**126 回中 126 回で `dup_lines = 0`** (§3.12 / §3.16.6)。
つまり否定されたのは**そこから先の推論**で、内容が周期的なファイル
(` ``` ` の連続 / 生成コード / 同じ行の反復) では、行距離が安全帯を満たしていても
git がハンクを別の位置へ合わせて衝突する (§3.16 / `tools/merge-band-probe.sh`)。
**この 2 つを混ぜないこと。**
