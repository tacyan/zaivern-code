# 並列エージェントの「衝突ゼロ」を数字で出す — `tools/conflict-bench.sh`

「衝突が減ります」は印象であって主張ではない。同じ作業量を 2 つの条件で流して、
差を実測するためのハーネス。

- **A 群 (ガード無し)** — N 個の worktree で、わざと重なるファイル集合を編集 →
  各ブランチでコミット → 直列マージ。**競合 (orca / swarm 系) と同じ条件**。
- **B 群 (ガード有り)** — **同じ担当表**を流すが、各書き込みの前に `zai hook`
  (= `crate::lease::gate`) を通す。拒否されたエージェントはそのファイルを諦めて
  次の担当へ移る (実運用と同じ挙動)。

担当表は `--seed` から決まるので、両群へ流れる作業内容は 1 バイト同じ。
差が作業内容の違いから出たら計測になっていない。

```
tools/conflict-bench.sh                        # 既定 (4 体 / 12 ファイル)
tools/conflict-bench.sh --agents 8 --files 40  # 規模を変える
tools/conflict-bench.sh --seed 12345           # 別の担当表で再現する
tools/conflict-bench.sh --hunk-cost 90         # モデルの仮定を変える
tools/conflict-bench.sh --json                 # JSON は stdout、表は stderr
tools/conflict-bench.sh --keep                 # 一時リポジトリを残す
```

一時リポジトリは `mktemp -d` (= `$TMPDIR` 由来)。`HOME` も一時ディレクトリへ
差し替えるので、**本物の `~/.zaivern` と `~/.gitconfig` には一切触らない**。
後始末は trap。ホストの `target/` も汚さない (既にある `zai` を再利用するだけ)。

`zai` は `ZAIVERN_BIN` → `CARGO_TARGET_DIR` → `cargo metadata` の順で探し、
**バージョンではなく能力 (`zai help` に `zai lease` が載るか) で選ぶ**。
古い `zai` は `lease` を知らず `zai lease …` を GUI 起動として扱うので、
パスだけ見て選ぶと計測が固まる (実際に踏んだ)。

> **ベースライン (zaivern を使わなかったら何件衝突するか) は
> `tools/conflict-zero-bench.sh` の担当。**このハーネスは `zai` が無いと
> 1 行も走らないので、「使わなかった場合」の数字はそちらで取る。
> 主張の全体像は `docs/conflict-zero.md`。

## ゲート 1 回の費用 (`zai hook` はユーザーの臨界路に乗る)

止めるのが速くても、止める判断が遅ければ意味が無い。並列実測に加えて、
**直列プローブ 30 回ずつ**で「1 回いくらか」の内訳を取っている。

| 測ったもの | p50 (4 / 8 / 6 体の 3 回) | 上との差 | 意味 |
|---|---|---|---|
| `git --version` | 20.3 / 26.9 / 20.3 ms | — | 計測系の下駄 (Python からの fork + exec) |
| `zai --version` | 25.5 / 30.3 / 26.2 ms | +3〜5 ms | + `zai` 自身のプロセス起動 |
| `zai hook` (台帳なし) | 23.3 / 31.9 / 28.8 ms | **-2.2〜+2.5 ms** | + フック投函と `stat` 1 回 |
| `zai hook` (台帳あり) | 32.9 / 34.0 / 29.6 ms | **+0.8〜+9.6 ms** | + リース判定 = ゲートの全額 |

- **リースを使っていない人の追加負担は計測誤差の範囲 (数 ms)。**
  設計原則 3「アイドル時のコストはゼロ」の検算になっている。
- **リース判定そのものは 1〜10 ms** (3 回の測定で 0.8 / 2.1 / 9.6 ms)。
  0.11.0 の時点では **15〜21 ms** だった。`with_store` が
  **変化が無ければ書き戻さない**ようになり (`src/lease.rs`)、許可されるだけの
  呼び出し (大半) で tmp 書き + rename を払わなくなったぶん。
- 並列時 (実測): 4 体で p50 46.5 / p95 54.1 / max 54.6 ms、
  8 体で p50 51.4 / p95 116.8 / max 141.6 ms、
  6 体 180 回で p50 38.8 / p95 65.3 / max 137.7 ms、
  **64 体 1536 回で p50 298.7 / p95 571.2 / max 1025.2 ms**。

## 解決済み: 同時 16 体のゲート fail-open (2026-08-10 の再測で 0 件)

**この節はかつて「未解決の問題」として書かれていた。実測し直した結果、
現在のコード (`5b2c66f` / 0.12.0) では再現しない。**

かつての記述はこうだった — 「16 体で走らせると 3 回中 3 回 `zai hook` が
判定せずに素通りし、1 回は B 群に本物のマージ衝突まで出た」。
同じ条件 (`--agents 16 --files 80`) を 3 回走らせた**今の実測**:

```
run1 rc=0 dup=0 B ハンク=0 A ハンク=15 gate_p50=49.1 p95=129.3 max=198.2 calls=128 fail-open=0
run2 rc=0 dup=0 B ハンク=0 A ハンク=15 gate_p50=45.9 p95=103.2 max=220.5 calls=128 fail-open=0
run3 rc=0 dup=0 B ハンク=0 A ハンク=15 gate_p50=47.6 p95= 88.8 max=164.7 calls=128 fail-open=0
```

**64 体 1536 回 (上の表) でも fail-open は 0 件。**

### いつ・何で直ったか

**直したのは、この文書を追加したのと同じコミット `ec9a479` である。**
つまり同じコミットの中で、直した後の再測をせずに「未解決」と書いた文章だけが
残っていた。**文書とコードのどちらかが嘘、という状態を 1 コミットの内側で
作っていた。** 直した内容は 2 つ:

1. `src/lease.rs` の `with_store` が **変化が無ければ書き戻さない**ようになった。
   ロックの保持時間が「小さな JSON の読み取り」だけになり、判定だけの呼び出し
   (大半) で tmp 書き + rename を払わなくなった。同じ `LOCK_WAIT_MS = 200`
   の予算でずっと多くの同時実行に耐える。
2. `crate::lease::gate` が **混雑を fail-closed (deny) に変えた**。
   ロックが取れないのは「衝突しやすい時ほど起きる」ので、そこで通すのは
   最悪の壊れ方だった。今は `busy-deny` として止め、再試行すれば通る。

### 代わりに出るようになった数字: `busy-deny`

fail-open (黙って通す) が消えた代わりに、**混雑して止める** `busy-deny` が
高並列で出る。`tools/conflict-zero-bench.sh` はこれを数えて表示する
(このハーネスは fail-open しか数えていない)。実測 (`--overlap 0.5`):

| 書き手 | fail-open | busy-deny | ゲート p50 / p95 |
|---:|---:|---:|---|
| 4 | 0 | 0 | 87 / 119 ms |
| 8 | 0 | 0 | 49 / 84 ms |
| 16 | 0 | 0 | 64 / 104 ms |
| 32 | 0 | **4** | 113 / 236 ms |
| 64 | 0 | **14** | 160 / 320 ms |

**`busy-deny` は「衝突が漏れた」ではなく「今は判定できないので止めた」。**
安全側だが、ユーザーからは「たまに拒否されて再試行が要る」として見える。
32 体以上を常用するならここが次の課題。

このハーネスは fail-open の回数を `gate.log` から自分で数え、
**重複担当が 1 件でも残ったら異常終了する** (緑の嘘を作らないため)。

## この計測で言えること

1. **B 群のマージ衝突は 0 件** — 4 体 / 8 体 / 6 体 180 編集 / 16 体 ×3 /
   64 体 1536 編集のいずれでも、衝突ファイル・衝突ハンク・衝突行数がすべて 0。
   同じ担当表を流した A 群では 1 / 5 / 11 / 15 / 167 ハンク出ている。
2. **「2 人以上が同じファイルを書いた」件数が 6 → 0、20 → 0、58 → 0、464 → 0。**
   これはモデルに依存しない一次データで、ここが 0 なら衝突は起こり得ない。
3. **止めるのは安い (低並列では)** — リース判定 1〜10 ms。
   ただし**同時 64 体では p50 298.7 ms** まで伸びる。ゲートは 1 本のロックを
   取り合うので、**同時実行数に対して線形には効かない**。
4. **使っていない人はほぼ払わない** — 台帳が無いときの `zai hook` は
   `zai --version` と区別できない (差は計測誤差の範囲)。
5. **fail-open は 4 / 8 / 16 / 64 体のいずれでも 0 件になった。**
   代わりに 32 体以上で `busy-deny` (再試行で通る拒否) が出る。

## この計測で言えないこと (正直な話)

1. **意味的な衝突は 1 つも防げない。** 片方が API を変え、もう片方が古い
   呼び方のまま書いた場合、ファイルが違えばリースは通し、git も黙って
   マージする。壊れるのはコンパイル時かテスト時。**このハーネスは
   テキストとしてのマージ衝突しか数えていない。**
2. **`--hunk-cost` (既定 45 秒) は測っていない仮定。** 「45 分の作業で
   待ち 18 分 → 4 分」の形にするにはハンク数へ係数を掛けるしかないので、
   係数は引数として外に出してある。**実測値はハンク数とゲート時間だけ。**
3. **ゲートは git より保守的で、通るはずの編集も止める。**
   同じファイルの別ブロックなら git は自動マージできるが、リースは
   ファイル単位なので 2 人目を拒否する。上の表の「実際に書けた編集
   180 → 101 件」「1536 → 565 件」がその代償で、止められたもののうち
   git なら綺麗に通ったものが相当数ある。**「衝突ゼロ」は「並列度を下げる」
   ことで買っている。**ただし諦めた担当は消えるのではなく別のエージェントへ
   回る想定なので総作業量が減るわけではない — が、**そこはこのハーネスでは
   測っていない。**
4. **編集の中身が合成。** 1 ファイル 6 ブロック、1 ブロック 8 行、
   エージェントは無作為な 1 ブロックの 1 行を書き換えるだけ。実際の
   エージェントはもっと広く触るので、**A 群の衝突数は実運用より少なめに
   出ているはず** (この製品に不利な側へ倒してある)。
5. **壁時計は「機械が直した時間」。** 衝突解消は
   マーカを外して両側を残す機械的な処理で 1 ファイル数 ms。人や AI が
   読んで判断する時間は入っていない (だから 2 の係数モデルが要る)。
6. **1 台の macOS でしか測っていない。** `busy-deny` が出はじめる境目
   (32 体) はファイルシステムの速度に直結するので、Linux / Windows では
   別の数字になる。
7. **ゲートの絶対値には計測系の下駄が乗っている。** `git --version` が
   20〜27 ms かかっているのが Python からの fork + exec の費用で、
   `zai hook` の実測値にも同じだけ含まれる。**差は正しいが、絶対値は
   上振れしている。**

## 再現手順

```sh
# 1. lease を持つ zai を用意する (0.11.0 以降)
cargo build --release --bin zai

# 2. 走らせる
tools/conflict-bench.sh
tools/conflict-bench.sh --agents 8 --files 40
tools/conflict-bench.sh --agents 6 --files 120

# 3. CHANGELOG 0.12.0 の「64 体・1500 書込」を再現する (約 6 分)
tools/conflict-bench.sh --agents 64 --files 1000

# 4. かつて fail-open した条件 (今は 0 件になる)
tools/conflict-bench.sh --agents 16 --files 80 --keep
#    → 残った一時ディレクトリの home/.zaivern/leases/gate.log を見る

# 5. 機械可読
tools/conflict-bench.sh --json | jq '.a.hunks, .b.hunks, .gate.p50, .gate.fail_open'
```

終了コードは 0 = B 群が 0 件、1 = 衝突か重複担当が残った (または A 群が
1 件も衝突せず計測になっていない)、2 = 引数の指定ミス。
