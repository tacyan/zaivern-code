# 並列エージェントの「衝突ゼロ」を数字で出す — `tools/conflict-bench.sh`

「衝突が減ります」は印象であって主張ではない。同じ作業量を 2 つの条件で流して、
差を実測するためのハーネス。

- **A 群 (ガード無し)** — N 個の worktree で、わざと重なるファイル集合を編集 →
  各ブランチでコミット → 直列マージ。**競合 (orca / swarm 系) と同じ条件**。
- **B 群 (ガード有り)** — **同じ担当表**を流すが、各書き込みの前に `zai hook`
  (= `crate::lease::gate`) を通す。拒否されたエージェントはそのファイルを諦めて
  次の担当へ移る (実運用と同じ挙動)。

担当表は `--seed` から決まるので、両群へ流れる作業内容は 1 バイト同じ。
差が作業内容の違いから出たら計測になっていない。

```
tools/conflict-bench.sh                        # 既定 (4 体 / 12 ファイル)
tools/conflict-bench.sh --agents 8 --files 40  # 規模を変える
tools/conflict-bench.sh --seed 12345           # 別の担当表で再現する
tools/conflict-bench.sh --hunk-cost 90         # モデルの仮定を変える
tools/conflict-bench.sh --json                 # JSON は stdout、表は stderr
tools/conflict-bench.sh --keep                 # 一時リポジトリを残す
```

一時リポジトリは `mktemp -d` (= `$TMPDIR` 由来)。`HOME` も一時ディレクトリへ
差し替えるので、**本物の `~/.zaivern` と `~/.gitconfig` には一切触らない**。
後始末は trap。ホストの `target/` も汚さない (既にある `zai` を再利用するだけ)。

`zai` は `ZAIVERN_BIN` → `CARGO_TARGET_DIR` → `cargo metadata` の順で探し、
**バージョンではなく能力 (`zai help` に `zai lease` が載るか) で選ぶ**。
古い `zai` は `lease` を知らず `zai lease …` を GUI 起動として扱うので、
パスだけ見て選ぶと計測が固まる (実際に踏んだ)。

## ゲート 1 回の費用 (`zai hook` はユーザーの臨界路に乗る)

止めるのが速くても、止める判断が遅ければ意味が無い。並列実測に加えて、
**直列プローブ 30 回ずつ**で「1 回いくらか」の内訳を取っている。

| 測ったもの | p50 | 上との差 | 意味 |
|---|---|---|---|
| `git --version` | 22.6〜31.1 ms | — | 計測系の下駄 (Python からの fork + exec) |
| `zai --version` | 29.8〜34.5 ms | +1〜8 ms | + `zai` 自身のプロセス起動 |
| `zai hook` (台帳なし) | 29.0〜35.7 ms | **-0.8〜+3.6 ms** | + フック投函と `stat` 1 回 |
| `zai hook` (台帳あり) | 49.1〜51.1 ms | **+15.4〜21.0 ms** | + リース判定 = ゲートの全額 |

- **リースを使っていない人の追加負担は計測誤差の範囲 (数 ms)。**
  設計原則 3「アイドル時のコストはゼロ」の検算になっている。
- **リース判定そのものは 15〜21 ms。** ロック作成 → 台帳読み → 判定 →
  tmp 書き → rename → ロック削除の 6 回のファイルシステム操作ぶん。
  `with_store` は**変化が無くても必ず書き戻す**ので、許可されるだけの
  呼び出し (大半) でも tmp 書き + rename を払っている。ここは削れる。
- 並列時 (実測): 4 体で p50 47.6 / p95 54.7 / max 56.6 ms、
  8 体で p50 55.2 / p95 98.5 / max 155.1 ms、
  6 体 180 回で p50 55.5 / p95 92.6 / max 136.0 ms。

## 見つかった問題: 同時 16 体でゲートが fail-open する

**16 体で走らせると、3 回中 3 回、`zai hook` が判定せずに素通りした。**
1 回は B 群に本物のマージ衝突 (1 ハンク) まで出た。

```
run1 rc=1 dup=1 bhunk=1 ahunk=15 gate_p95=184 gate_max=250 calls=128 fail-open=1
run2 rc=1 dup=1 bhunk=0 ahunk=10 gate_p95=172 gate_max=239 calls=128 fail-open=1
run3 rc=1 dup=1 bhunk=0 ahunk=12 gate_p95=211 gate_max=352 calls=128 fail-open=1
```

`gate.log` に直接の証拠が残る (推測ではない):

```
1786293012 fail-open src/mod_72.rs: ロックを取れませんでした (先客が握っています)
```

8 体では 10 回中 1 回 (`fail-open=1` / 640 回のゲート呼び出し中 1 回)。
4 体では 0。

**原因**は `src/lease.rs` の設計そのもの:

- `LOCK_WAIT_MS = 200` — ロックが取れなければ 200 ms で諦める
- `gate` は**内部エラーを fail-open (許可)** にする
  (「台帳が読めない・ロックが取れないのはこちらの都合で、それでユーザーの
  エージェントを止めるのは衝突より悪い」)
- 1 回のロック保持がおよそ 15〜21 ms なので、**同時に 10 本以上並ぶと
  待ち行列が 200 ms を超える**

つまり「衝突ゼロ」は**同時実行数が上がると保証でなくなる**。数字で言うと、
この機材では 4 体で保証、8 体で 1/640 回、16 体では毎回 1 回漏れる。

削るべきは待ち時間ではなく**ロックの保持時間**で、いちばん安い一手は
「許可されただけで台帳が変わっていない呼び出しでは書き戻さない」
(`with_store` が無条件に `write_store` を呼ぶのをやめる)。
保持時間が 1/3 になれば、同じ 200 ms の予算で 3 倍の同時実行に耐える。

このハーネスは fail-open の回数を `gate.log` から自分で数え、
**重複担当が 1 件でも残ったら異常終了する** (緑の嘘を作らないため)。

## この計測で言えること

1. **B 群のマージ衝突は 0 件** — 4 体 / 8 体 / 6 体 180 編集のいずれでも、
   衝突ファイル・衝突ハンク・衝突行数がすべて 0。同じ担当表を流した A 群では
   1 / 5 / 11 ハンク出ている。
2. **「2 人以上が同じファイルを書いた」件数が 6 → 0、20 → 0、58 → 0。**
   これはモデルに依存しない一次データで、ここが 0 なら衝突は起こり得ない。
3. **止めるのは安い** — リース判定 15〜21 ms。180 回のゲートで合計 10.5 秒。
   同じ条件で A 群が抱えた 11 ハンクを 1 個 45 秒で直すと 8 分 15 秒なので、
   **8 分 15 秒 → 10.5 秒**。
4. **使っていない人はほぼ払わない** — 台帳が無いときの `zai hook` は
   `zai --version` と区別できない (差は計測誤差の範囲)。
5. **同時実行数の上限が数字で出る** — 4 体は安全、8 体で 1/640、16 体で毎回漏れる。

## この計測で言えないこと (正直な話)

1. **意味的な衝突は 1 つも防げない。** 片方が API を変え、もう片方が古い
   呼び方のまま書いた場合、ファイルが違えばリースは通し、git も黙って
   マージする。壊れるのはコンパイル時かテスト時。**このハーネスは
   テキストとしてのマージ衝突しか数えていない。**
2. **`--hunk-cost` (既定 45 秒) は測っていない仮定。** 「45 分の作業で
   待ち 18 分 → 4 分」の形にするにはハンク数へ係数を掛けるしかないので、
   係数は引数として外に出してある。**実測値はハンク数とゲート時間だけ。**
3. **ゲートは git より保守的で、通るはずの編集も止める。**
   同じファイルの別ブロックなら git は自動マージできるが、リースは
   ファイル単位なので 2 人目を拒否する。上の表の「実際に書けた編集
   180 → 101 件」がその代償で、止められた 79 件のうち git なら綺麗に
   通ったものが相当数ある (この条件だと重複 79 件中 11 件しか実際には
   衝突していない)。**「衝突ゼロ」は「並列度を下げる」ことで買っている。**
   ただし諦めた担当は消えるのではなく別のエージェントへ回る想定なので、
   総作業量が減るわけではない — が、**そこはこのハーネスでは測っていない**。
4. **編集の中身が合成。** 1 ファイル 6 ブロック、1 ブロック 8 行、
   エージェントは無作為な 1 ブロックの 1 行を書き換えるだけ。実際の
   エージェントはもっと広く触るので、**A 群の衝突数は実運用より少なめに
   出ているはず** (この製品に不利な側へ倒してある)。
5. **壁時計は「機械が直した時間」。** 衝突解消は
   マーカを外して両側を残す機械的な処理で 1 ファイル数 ms。人や AI が
   読んで判断する時間は入っていない (だから 3 の係数モデルが要る)。
6. **1 台の macOS でしか測っていない。** fail-open の閾値
   (4 体 / 8 体 / 16 体) はファイルシステムの速度に直結するので、
   Linux / Windows では別の数字になる。
7. **ゲートの絶対値には計測系の下駄が乗っている。** `git --version` が
   22〜31 ms かかっているのが Python からの fork + exec の費用で、
   `zai hook` の実測値にも同じだけ含まれる。**差 (15〜21 ms) は正しいが、
   絶対値は上振れしている。**

## 再現手順

```sh
# 1. lease を持つ zai を用意する (0.11.0 以降)
cargo build --release --bin zai

# 2. 走らせる
tools/conflict-bench.sh
tools/conflict-bench.sh --agents 8 --files 40
tools/conflict-bench.sh --agents 6 --files 120

# 3. fail-open を再現する (同時 16 体)
tools/conflict-bench.sh --agents 16 --files 80 --keep
#    → 残った一時ディレクトリの home/.zaivern/leases/gate.log を見る

# 4. 機械可読
tools/conflict-bench.sh --json | jq '.a.hunks, .b.hunks, .gate.p50, .gate.fail_open'
```

終了コードは 0 = B 群が 0 件、1 = 衝突か重複担当が残った (または A 群が
1 件も衝突せず計測になっていない)、2 = 引数の指定ミス。
