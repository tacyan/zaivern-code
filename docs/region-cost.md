# 行域判定そのものの費用 — ハーネスと分けて測る

**先に結論**: 行域判定は**二次だった**。`region::conflicting_pairs` は `N` 件に
対して `N(N-1)/2` 回の `conflicts` を呼び、その 1 回が `lease::overlaps` の中で
パスを正規化して**セグメントごとに DP の表を確保**していた。そして
**その事実は既存の数字のどこにも現れていなかった** — `tools/coedit-bench.sh` の
所要は git とプロセス起動に埋もれていたからである。

再現はコマンド 1 行:

```sh
tools/region-cost.sh                      # 表
tools/region-cost.sh --json               # JSON は stdout、表は stderr
tools/region-cost.sh --sizes 100,200,400,800 --lines 2000,4000,8000,16000
```

---

## 1. なぜ別のハーネスが要るのか

既存の `tools/coedit-bench.sh` / `tools/conflict-zero-bench.sh` は

* 一時リポジトリを `git init` して
* N 体ぶんのワークツリーを作り
* `zai` を何十回も**プロセスとして**起動する

数字の**大半はこのハーネスの費用**である。行域判定が 1 回 50µs であろうと
5µs であろうと、git の 1 回の呼び出し (0.03〜10 秒) の中に完全に埋もれる。
つまり既存のハーネスでは、

> **行域判定そのものが速いのか遅いのかが分からない。**

実際、判定は二次に伸びていたのに、既存の数字は一度もそれを示さなかった。

## 2. 何を測るのか — `src/region.rs` の API の分類

**`src/region.rs` には I/O が 1 つも無い** (テストを除く)。ファイル読みは
`lease::gate` 側にある。つまり既存ベンチの所要のうち行域判定に帰せられる
部分は **100% CPU** であり、そこだけを取り出せば必ず測れる。

| 分類 | API | 何に比例するか |
|---|---|---|
| **判定 (テキストを見ない)** | `spans_too_close` | O(1) |
| | `conflicts` | O(パス長)。中で `lease::overlaps` を通る |
| | `conflicting_pairs` / `is_disjoint` | **ここが二次だった** |
| | `within` | O(持ち域 × 触れた域)。どちらも 1 桁なので測っていない |
| | `parse` / `render` / `parse_spec` / `render_spec` | O(仕様文字列長) |
| **テキストを走査する** | `capture_anchor` | O(行数) |
| | `resolve` (`best_pair` / `nearest_unique`) | O(行数 + 候補数 × 半径) |
| | `touched_spans` | O(行数) |
| | `symbol_span` / `resolve_spec` | O(行数) |
| **I/O を伴うもの** | **無い** | — |

測る軸は 4 つ: **(a) 予約件数 N**、**(b) 1 ファイルの行数**、**(c) 帯幅**、
**(d) 重なり率** (互いに素 / 2 件ずつ衝突 / 全員が重なる)。

## 3. 分け方 — 「空の判定」を同じ回数回す

`src/region.rs` の `cost` モジュールは外部プロセス・git・ファイル I/O を
1 つも含まない。同じ入力の生成を**判定ありと「空 (0 件) の判定」の両方で**
回して差を取る:

```
total   = 入力を作る + 判定する
harness = 入力を作る + 空を判定する
judge   = total - harness      ← これが知りたかった数字
```

* 予約一覧 → `conflicting_pairs(&input, band)` と `conflicting_pairs(&[], band)`
* 錨の取り直し → 錨のある域と、**錨が空でその場で返る**域
* 錨打ち / 触れた行域 → 実テキストと、空文字列

`har_%` 列が「測った時間のうち何 % が入力作りだったか」である。

## 4. 合否は時間で決めない

表に出す時間は**数字として出すだけ**。赤にするかどうかは**判定の呼び出し
回数**で決める。絶対時間の線は Docker の仮想 FS でも他テストとの同時実行でも
必ず嘘をつく (この repo で実際に 3 件落ちた)。カウンタは**スレッドローカル**
(プロセス共通の `static` にすると同時に走る他テストの呼び出しが混ざる)。

| 番人テスト (`region::cost`) | 何を固定するか |
|---|---|
| `総当たりと同じ答えを返す` | 掃引版と総当たり版の出力が 1 バイト違わない (乱択 400 通り)。`is_disjoint` も別経路として突き合わせる |
| `件数を二倍にしても判定回数は二倍までしか増えない` | 100→200→400→800 で判定回数の伸びが 2.5 倍以内 (総当たりなら 4 倍) |
| `互いに素な一覧では総当たりの一パーセントも判定しない` | 800 件・互いに素で判定 0 回 |
| `全員が重なる最悪ケースでも出力件数までしか判定しない` | 二次な入力でも「出力件数 + 件数」が上限 |
| `錨の取り直しにかかる行の比較は行数に比例する` | 4千→3万2千行で行走査の伸びが 2.5 倍以内 |

`tests::巨大ファイルでも取り直しが速い` も `300ms 未満` という絶対時間の線を
**行の走査回数**の線へ置き換えた (4 万行に対して 4 倍以内)。

### 5.1 ハーネスと判定の分離 — これが今回の主目的

* 予約一覧の側では、測った時間の **5.4〜9.1% が入力作り**。残りが判定そのもの
* テキストの側では **16.6〜42.6% が入力作り**。`text.anchor` は最大で
  **42.6% がハーネス**で、引かずに出した数字は最初から 1.7 倍ずれている
* 800 件の互いに素な一覧なら **ハーネス 0.23ms / 判定そのもの 3.67ms**。
  同じ入力へ総当たりを掛けると **9,467ms** かかる。ハーネスはその 4 万分の 1 で、
  **既存のベンチではこの 9 秒が git の待ちと区別できなかった**
* 総当たりの大きい点は繰り返し 1 回しか回していない (debug で 1 点 10 秒かかる
  ため。`naive_iters` として JSON に出る)。桁は動かないが、倍率は走らせるたびに
  1600〜2600× と揺れる

### 5.2 N を振ったときの伸び — 判定回数は線形、時間は嘘をつく

`judged` 列の伸びは**ちょうど 2.00 倍**なのに、同じ点の時間の伸びは
**1.31〜2.78 倍**にばらついた。**これが「絶対時間で線を引かない」の実物**である。

| 軸 | 100→200 | 200→400 | 400→800 |
|---|---|---|---|
| `pairs.couples` 判定回数 | ×2.00 | ×2.00 | ×2.00 |
| `pairs.couples` 所要 | ×2.31 | **×1.88** | ×2.10 |
| `pairs.disjoint` 所要 | ×2.20 | ×1.96 | ×2.23 |

| 軸 | 2千→4千行 | 4千→8千行 | 8千→1万6千行 |
|---|---|---|---|
| `text.resolve` 走査回数 | ×1.99 | ×2.00 | ×2.00 |
| `text.resolve` 所要 | ×2.33 | ×1.86 | ×2.16 |
| `text.anchor` 走査回数 | ×2.00 | ×2.00 | ×2.00 |
| `text.anchor` 所要 | **×1.31** | **×2.78** | ×1.71 |

`pairs.crowded` だけは判定回数も **×4.01** で二次だが、これは**出力そのものが
`N(N-1)/2` 件ある**からで、下限に張り付いている (ベンチはこれを `output_bound`
として区別し、二次と数えない)。

### 5.3 直す前と後 (同じ入力・同じ述語)

| 入力 (N=800) | 総当たり | バケツ + 掃引 | 比 |
|---|---|---|---|
| 互いに素 | 319,600 回 / 9,467ms | **0 回 / 3.67ms** | 2581× |
| 2 件ずつ衝突 | 319,600 回 / 10,181ms | **400 回 / 4.24ms** | 2400× |
| 全員が重なる | 319,600 回 / 133ms | 319,600 回 / 532ms | **0.3×** (§7 参照) |

`conflicts` 1 回あたりの費用も、同じパスの照合を飛ばすことで
**53µs → 2.1µs** になった (`pairs.crowded` n=200 の判定 19,900 回が
1,067ms → 28ms)。**この 25 倍は「同じファイルの違う行」というこの機能で
一番多い形にそのまま効く。**


## 6. 直したもの

### 6.1 総当たり → バケツ + 掃引 (`conflicting_pairs`)

答えを 1 つも変えずに候補を絞る:

1. パスを**1 回だけ**正規化して、具体パスと「広いパス」(glob / `#` を含む /
   末尾が区切り) に分ける。具体パスどうしは**正規化した文字列が一致する
   ときしか重ならない**ので、一致するものをバケツにまとめる
2. バケツの中は開始行で整列して掃く。「まだ安全帯の内側に届いている」予約
   だけを `active` に残すので、**触る組は実際に衝突する組しか出てこない**
3. 広いパスはパスの照合が要るので従来どおり総当たり (実運用では 0 件)

判定そのものは `conflicts` のまま呼ぶ — **述語の実装を 2 本持たない**。
絞り込みは「衝突し得る組の**上位集合**」を出すだけで、可否は必ず `conflicts`
が決める。計算量は `O(N log N + 出力件数)`。

### 6.2 同じパスなら `overlaps` を丸ごと飛ばす (`conflicts`)

`lease::overlaps` は毎回パスを正規化してセグメントへ割り、セグメントごとに
`vec![false; (n+1)*(m+1)]` と `Vec<char>` を確保する。**「同じファイルの
違う行」というこの機能で一番多い形**が、まるごとそこを通っていた
(debug で 1 回 53µs → 2.1µs)。

同じ文字列は必ず自分自身と重なるので、`a.path == b.path` のときだけ照合を
飛ばす。**照合をやめるのではなく、答えが自明な場合だけ飛ばす**ので実装は
1 本のまま。前提は `tests::同じパスは必ず自分自身と重なる` が固定する。


## 7. 測って「直さなかった」もの

* **錨の取り直し (`resolve`)** は行数に対して**線形**だった。行の走査回数は
  倍々に伸びる。直していない
* **`capture_anchor` / `touched_spans`** も線形。ただし費用の 1/6〜2/5 が
  入力作り (ハーネス) なので、**分けて出さないと過大評価になる**
* **帯幅 (`band`)** を 0→32 に広げても判定回数は変わらない (組の数は並べ方で
  決まる)。所要もほぼ動かない
* **`conflicting_pairs` は「全員が重なる」入力では総当たりより 4 倍遅い。**
  出力そのものが `N(N-1)/2` 件あり、掃引の順に出したものを添字順へ並べ替える
  ぶんだけ負ける。**直さなかった** — 全組を返す仕様そのものの費用なので、
  減らすには仕様を変えるしかない

## 8. 測って分かった宿題 (解決済みのものは経緯を残す)

* ~~**`is_disjoint` の早期脱出は `-D dead_code` に阻まれて撤回した。**~~
  **【解決済み。この節に残っているのは経緯である】**
  当時は早期脱出を入れると `conflicting_pairs` に出荷ビルドからの呼び出し元が
  1 つも無くなり ( `is_disjoint` と `negomesh` / `region` のテストだけだった)、
  CI の clippy が "function conflicting_pairs is never used" で落ちた。
  `allow(dead_code)` は置かない約束なので、いったん撤回した。
  **その後、当時「降ろすならこうする」と書いた道がそのまま実装された** —
  `negotiate::Plan::conflict_report` が `conflicting_pairs` を呼んで
  どの組が衝突したかを出すようになり、呼び出し元が生えた。
  いまの `region::is_disjoint` は掃引に「最初の 1 組で止まる」を渡している
  (`scan(list, band, true, ..)`)。**この節の数字 (§5.3 の表) は早期脱出を
  入れる前のもの**なので、`is_disjoint` の最悪ケースは要再測定。
* **`band = 0` では重なっている行域が「衝突しない」と出る。**
  `spans_too_close` の `gap = hi0.saturating_sub(lo1).saturating_sub(1)` が
  重なりで 0 に飽和し、`0 < 0` が偽になるため。`SAFE_BAND = 3` /
  `MERGE_ONLY_BAND = 1` しか使っていないので出荷物に影響は無いが、
  `band = 0` を「安全帯なし = 重なりだけを見る」の意味で使うと嘘をつく
* **`lease::overlaps` の 1 回はまだ高い** (別ファイル同士で debug 53µs)。
  セグメントごとの DP は `*` を含まないセグメントには要らない。
  `src/lease.rs` は今回の担当外なので触っていない
* **交錯の判定 (`region::anchor_lines`) の費用はここで測っていない。**
  2026-08-11 に足した交錯検査 (`docs/conflict-zero.md` §3.16) は
  **共通祖先側の本文を 1 回読んで、行の出現回数を数える** (`BTreeMap`、
  行数に比例)。ただし呼ばれるのは
  **「2 人の外接域が重なっているファイル」だけ**で、この機能が普段扱う
  「互いに素に配った担当」では**1 度も呼ばれない**
  (`coedit::clashes_with` が `region::interleaved` で先に絞る)。
  `tools/region-cost.sh` は 1 つのテキストに対する `resolve` / `anchor` を
  測るハーネスなので、**「交錯しているファイルの数」を振る区間が要る**。
  この表を足すまでは「互いに素な配り方では費用ゼロ」としか言えない
