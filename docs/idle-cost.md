# アイドル時のコストを測る

設計原則 3 は **「アイドル時のコストはゼロでなければならない。再描画は damage
駆動のみ。アイドル時の CPU/GPU 使用率は印象ではなく数値でリリースゲートにする」**
と言っている。競合 (orca) の最大の不満がまさに「アイドルで CPU 1 コアの約 40%」で、
ここは正面から勝てる領域である。

この文書は、その数値を**誰でも同じ手順で出せる**ようにするためのもの。

## 何を測るのか (と、測らないこと)

| 見るもの | 出所 | なぜ |
| --- | --- | --- |
| **再描画要求の回数と出所** | `perf::snapshot().repaint_ranking()` | 原則は「damage 駆動のみ」。回数がゼロなら守れている。フレーム時間ではこれが見えない |
| **自走している出所** | `perf::snapshot().always_on_sources()` | アイドルフレームと同数以上の要求を出した = 自分で次のフレームを予約し続けている犯人 |
| **プロセスの CPU 時間の増分** | `tools/idle-cpu.sh` | 上の 2 つは「アプリが要求した回数」しか見ない。OS 側で本当に何秒焼いたかは外からしか分からない |

**測らないもの: 絶対時間の合否ライン。** 「アイドル 30 秒で CPU 0.5 秒以下なら合格」
のような線は必ず嘘をつく (このリポジトリでは実測で性能テストが 3 件落ちた:
Docker の仮想 FS、全テストとの同時実行、64 スレッドの負荷)。
`tools/idle-cpu.sh` は数字を出すだけで、判定しない。**同じ機械で版を替えて
2 回走らせ、増分どうしを比べる**のが正しい使い方である。

外形の `%CPU` (`ps` の瞬間値) も使わない。サンプリングの運不運に左右されるうえ、
実エージェントのプロセスが混ざって交絡する。見るのは**そのプロセス自身の
CPU 時間 (user+sys) の累積差分**だけで、子プロセスは数えない。

## 1. CPU 時間の増分 — `tools/idle-cpu.sh`

```sh
tools/idle-cpu.sh                 # 既定 (5s ウォームアップ + 20s 放置)
tools/idle-cpu.sh --seconds 60    # 放置する秒数
tools/idle-cpu.sh --baseline      # 何もしないプロセス (sleep) の増分と並べる
tools/idle-cpu.sh --json          # 機械可読 (版間比較 / CI)
tools/idle-cpu.sh --workspace DIR # 開くワークスペース (既定: 空の一時 dir)
tools/idle-cpu.sh --warmup 10     # 起動直後を測定から外す秒数
tools/idle-cpu.sh --bin PATH      # 測るバイナリを直に指定
```

出力の読み方:

```
CPU 時間の増分 : 0.070s  (= 1 コアの 0.35%)
基準 (sleep)   : 0.000s  (= 1 コアの 0.00%)  ← 同じ機械・同じ区間の下限
```

**この数字は測定条件とセットでないと意味がない。** 窓の長さ・load・ビルド種別を
書かない数字は再現できないし、実際にこのリポジトリで
「アイドルは 1 コアの 0.70%」と書いた直後に、**同じツールで 2.55% / 2.95% /
4.85% / 10.00% が出て覆った**ことがある (窓が短いほど高く出る。理由は
[実測値](#5-実測値-2026-08-11) の節)。実測値は必ず表で残すこと。

* `--baseline` の行が**同じ機械・同じ瞬間の下限**になる。`sleep` の増分は
  ほぼ 0 なので、そこからどれだけ離れているかがそのままアイドルのコスト。
* ワークスペースは既定で**空の一時ディレクトリ**にしてある。git リポジトリを
  開くと `git.rs` / `worktree.rs` のスキャンが回り、それは「アイドル」ではなく
  「リポジトリを見張っている状態」のコストになるため。両方測りたいときは
  `--workspace <リポジトリ>` で明示する。
* バイナリは `$CARGO_TARGET_DIR` → `<リポジトリ>/target/{release,debug}` → `PATH`
  の順で探し、**見つけた版の `--version` を必ず出す**。前の実行の残骸を
  「新しい版」と読み違えないため。
* 起動できない環境 (ヘッドレスの Linux で winit が上がらない等) は
  **skip と理由を出して終了コード 0** で抜ける。黙って飛ばさない。
  Linux の CI で測りたいときは `xvfb-run -a tools/idle-cpu.sh`。
* 測るのは**リリースビルドが望ましい**。debug ビルドの数字は debug の数字と
  しか比べられない。

## 2. 再描画要求の内訳 — `ZAIVERN_PERF=1`

`src/perf.rs` は既定では 1 命令も走らない。`ZAIVERN_PERF=1` のときだけ、
フレーム時間のヒストグラムと**アイドル中の再描画要求**を積む。

```sh
# (A) 手で閉じる — レポートは on_exit で 1 回だけ出る
ZAIVERN_PERF=1 ZAIVERN_PERF_OUT="$(mktemp -d)/perf.txt" zai <ワークスペース>
# → 放置する → ウィンドウを普通に閉じる (⌘Q / ✕) → $ZAIVERN_PERF_OUT を読む

# (B) script から回す — N 秒後に 1 回だけ予約する
ZAIVERN_PERF=1 ZAIVERN_PERF_OUT=… ZAIVERN_PERF_DUMP_AFTER=35 zai <ワークスペース>
```

レポートは**明示的な要求時にまとめて 1 回**だけ書き出す (1 フレームごとに
文字列を吐くと計測自体が観測対象を歪めるため)。既定の書き出し点は `on_exit`
だが、**SIGTERM ではハンドラが無く即終了するので出ない** — script から
「起動 → N 秒放置 → 数字を取る」を回すには `ZAIVERN_PERF_DUMP_AFTER=<秒>`
が要る。`tools/idle-cpu.sh` はこれを自動で渡し、書き終わるのを待ってから
プロセスを終わらせる。

予約のスレッドは**寝て・書いて・終わるだけ**で、再描画を 1 度も要求しない
(計測のために設計原則 3 を破らない)。秒数が数字でなければ予約しない —
黙って 0 扱いにすると起動直後に空のレポートが出て、
「アイドルでは何も起きていない」という嘘になる。

出力は `key=value` の 1 行 1 レコードで、`diff` でも `awk` でも比較できる:

```
ZAIVERN_PERF version=… frames=… p50_ms=… p95_ms=… max_ms=… \
    idle_frames=… idle_fps=… idle_repaints=… idle_repaint_rate=… always_on=-
ZAIVERN_PERF_BUCKET lo_ms=… hi_ms=… count=…
ZAIVERN_PERF_REPAINT source=spinner count=1234
```

読むべき列:

* **`idle_repaints`** — アイドル中に出た再描画要求の総数。damage 駆動が
  守れていれば、放置している間ここは増えない。**この列が主役**で、
  `p50_ms` などのフレーム時間は「1 フレームがどれだけ重いか」しか言わない。
* **`always_on`** — 自走している出所の名前 (無ければ `-`)。
  アイドルフレームと**同数以上**の要求を出した出所だけが載る。
  比で見るので、遅い機械でも速い機械でも同じ結論になる。
* `ZAIVERN_PERF_REPAINT` 行 — 出所ごとの内訳を**多い順**に並べたもの。
  アイドルで CPU が回っているときは、上から数行で犯人が分かる。

`max_ms` と `mean_ms` の乖離は**停止のサイン**である
(p50 10ms・p95 12ms なのに max 4376ms、という形で出た実績がある)。

### 画面から見る

アプリ内では **📊 プラン使用量** ウィンドウに 1 行の要約が出る
(`perf::status_line`)。計測が無効・標本ゼロなら 1px も出ない。

```
1234 frames  p50 8.1ms  p95 12.4ms  max 31.0ms  idle 0.0/s  req 0
```

自走している出所があるときだけ、末尾に `← spinner x1234 常時` が付く。
同じウィンドウのボタンから `perf::dump()` (レポート出力) と
`perf::reset()` (計測のやり直し) ができるので、**区間を切って測れる**:

1. 放置したい状態にする
2. 「計測をやり直す」を押す
3. N 秒放置する
4. 「レポート出力」を押す → `idle_repaints` がその N 秒ぶんの数

### 背面ウィンドウの罠

macOS は背面のウィンドウの描画を止める。**計測中は前面に置くこと。**
止まったまま計ると「軽い」という嘘の数字が出る。

## 3. アイドルの定義はどこにあるか

`perf` は**渡された真偽値を数えるだけ**で、判定は持たない。
判定は `src/app.rs` の `schedule_idle_repaint` にある:

```rust
crate::perf::note_idle(!signals.had_input);
```

`IdleSignals` は `had_input` / `animating` / `awaiting` / `agents_running` /
`watching_files` / `timers_due` / `focused` / `visible` を持つ。
いま数えている「アイドル」は **実入力が無いフレーム**であって、
エージェントが走っている間のフレームも含む。

エージェント実行中を除いた**真のアイドル**を測りたいときは、この 1 行を
`!signals.had_input && !signals.agents_running` にする。
`perf::snapshot()` の側は何も変えなくてよい (数える対象が絞られるだけ)。

この配線が消えると `idle_frames` が永久に 0 になり、
「アイドルでは何も起きていない」という静かな嘘が出る (フレーム時間の数字は
出続けるので気付けない)。`perf::tests::アイドル判定がappから渡されている` が番人。

### 予約の刻み (`app::idle_repaint_ms`)

`always_on=schedule_idle_repaint` が出たときは異常ではなく、**定期フレームの
予約が効いている**という意味である。刻みはこの表で決まる (`src/app.rs`):

| 状況 | 次のフレームまで | fps |
| --- | --- | --- |
| UI スレッドの返事待ち (`awaiting`) | 50ms | 20 |
| 誰かがアニメーション中 (`animating`) | **予約しない** (持ち主に任せる) | — |
| エージェント実行中・前面 | 250ms | 4 |
| エージェント実行中・背面 | 1500ms | 0.67 |
| 家事あり (ファイル監視 / タイマー)・前面 | 2000ms | 0.5 |
| 家事あり・背面 | 6000ms | 0.17 |
| 家事あり・最小化 | 10000ms | 0.1 |
| **何も起きていない** | **予約しない = 1 枚も描かない** | 0 |

つまり `idle_fps` が 0.5 前後なら「ワークスペースを開いて放置」の想定どおり、
0 なら完全に寝ている。**4 や 20 が出たらエージェントか応答待ちが残っている**
ので、その状態は「アイドル」ではない。


## 4. ペットの刻み (`src/pet.rs`)

アイドル中の再描画要求は、**このアプリでは実質ペットしか出していない**。
`pet::repaint_ms` の表がそのままアイドルのコストになる。

| 状態 | 前面 | 背面 | 根拠 |
| --- | --- | --- | --- |
| 熟睡 / **静止** (`is_still`) | **予約しない** | **予約しない** | 絵が時刻に依存しない |
| 待機 / うろうろ | 500ms | 2000ms | 時間の上限が無い。家事 (2000ms) より速くしない |
| うとうと | 1000ms | 2000ms | ゆっくりした上下だけ |
| 作業中 / ノリノリ / 承認待ち | 250ms | 1500ms | `app::IDLE_AGENT_MS` と**同じ**。ペットが駆動源にならない |
| 喜び / 怒り / 失敗 | 80ms | 250ms | 2〜6 秒で必ず終わるので総量が頭打ち |

守っている性質は 2 つ:

* **ペットはアプリで一番速いスケジューラであってはならない。**
  `app::idle_repaint_ms` より短い刻みを出した瞬間、ペットが
  フレームレートの決定者になる = 常時アニメーションになる。
* **`pet_sleep = false` でも止まる。** `is_still` は `SLEEP_AFTER` を超えた
  放置を、**睡眠設定に関係なく**静止画にする。設定で設計原則 3 を
  外せてはいけない — 「眠らない」は*目を閉じない*であって
  *永久に描き続ける*ではない。時計 (`anim_t`) ごと止めるので、
  後から足したバリアントも自動的に静止する。

出所タグは `pet_anim.idle` / `.doze` / `.work` / `.attention` / `.react` と
**状態ごとに割ってある**。`perf::dump()` の 1 行で「どの状態で自走しているか」
まで分かる (割る前は `pet_anim` の 1 本しか無く、刻みの表と突き合わせて
状態を逆算する必要があった)。

## 5. 実測値 (2026-08-11)

macOS (Darwin 25.5.0) / **release ビルド** / 空の一時ワークスペース /
ウォームアップ 5 秒 / `--baseline` 併記。`before` = この修正の前、
`after` = 後。**同じ機械で交互に**走らせ、各回の load を記録してある
(負荷の谷と山を引くと嘘が出るため)。基準 (`sleep`) の増分は**全 16 回とも
0.000s** だったので、下の数字はマシンの負荷では説明できない。
測定時の版表示は 0.14.0 だが、`after` の実装が出荷されたのは **0.15.0** である
(CHANGELOG 0.15.0 の「アイドル時の CPU を 1 コアの 1.95% → 0.35%」)。

| 窓 | load | before | after | 比 |
| --- | --- | --- | --- | --- |
| 20s | 30.8 / 21.0 | 0.390s (1.95%) | 0.070s (0.35%) | 5.6x |
| 20s | 19.2 / 19.0 | 0.410s (2.05%) | 0.060s (0.30%) | 6.8x |
| 20s | 15.3 / 12.3 | 0.370s (1.85%) | 0.070s (0.35%) | 5.3x |
| 60s | 10.5 / 8.7 | 0.700s (1.17%) | 0.170s (0.28%) | 4.1x |
| 60s | 10.3 / 10.5 | 0.390s (0.65%) | 0.100s (0.17%) | 3.9x |
| 60s | 11.0 / 9.6 | 0.380s (0.63%) | 0.100s (0.17%) | 3.8x |
| 120s | 10.8 / 7.9 | 0.450s (0.38%) | 0.180s (0.15%) | 2.5x |
| 120s | 9.1 / 9.2 | 0.460s (0.38%) | 0.230s (0.19%) | 2.0x |

**窓が短いほど高く出るのは仕様ではなく構造**である。ペットが静止するのは
最後にポインタが動いてから `SLEEP_AFTER` = 60 秒後なので、
**60 秒より短い窓は「起きている間」しか測っていない**。
20 秒窓の数字が 120 秒窓の 5 倍あるのはそのため。
「アイドルのコスト」を名乗るなら**窓を必ず書く**こと。

同じ区間の再描画要求 (`ZAIVERN_PERF_REPAINT`):

```
before (20s):  pet_anim          x357
after  (20s):  pet_anim.idle x44  pet_anim.doze x8      (合計 52 = 6.9 分の 1)
before (60s):  pet_anim          x582  schedule_idle_repaint x4
after  (60s):  pet_anim.idle x46  pet_anim.doze x20  schedule_idle_repaint x1
```

**要求の総量**は実時間に依らず数えられるので、番人テストはこちらで線を引く
(`pet::sleep_tests::一度の入力で出る要求の総量に上限がある`):
ポインタが 1 回動いてから静止するまでに出る要求は **600 件 → 89 件**。
眠るまでの秒数は変えていないので、**見た目の挙動はそのまま**である。

### 覆った主張 (残しておく)

最初にこの文書へ書いた **「アイドルは 1 コアの 0.70% / 0.32%」は嘘だった。**
懐疑的な検証で同じツールから 2.55% / 2.95% / 4.85% / 10.00% が出た。
原因は 2 つあり、どちらも**測り方ではなく書き方**の問題だった:

1. **窓の長さを書いていなかった。** 上の表のとおり 20 秒窓と 120 秒窓では
   5 倍違う。同じアプリの同じ状態でも、窓が違えば別の数字になる。
2. **「アイドル = 静止」だと思い込んでいた。** 実際には最後の入力から
   60 秒間はずっとアニメーションしており、短い窓はその 60 秒の中しか
   見ていない。時計を注入して進める試験 (`pet::sleep_tests`) で
   **活動なしのまま `SLEEP_AFTER` を過ぎて静止する**ことを確認して初めて
   「到達していない」のではなく「窓が届いていない」と分かった。

## 6. 回帰を防ぐ

* `perf::tests::アイドルを続けても再描画要求は増えない` — アイドルを 600 フレーム
  模擬して、内訳が空のままであることを見る (damage 駆動の性質そのもの)。
* `perf::tests::自走している出所だけが名指しされる` — 毎フレーム要求する出所は
  名指しされ、たまに起こすだけの出所は名指しされない。
* `perf::tests::記録のメモリは標本数に依らない` / `出所の種類は上限で頭打ちになる`
  — 標本や出所の種類を **2 倍にしても表の大きさが増えない** (O(1))。
  計測自体が重くなって観測対象を歪めないため。
* `pet::sleep_tests::放置がsleep_afterを過ぎたら要求が止まる` — 時計を
  注入して (`RawInput::time`) 活動なしで進め、`SLEEP_AFTER` を過ぎたら
  **要求が 1 件も出ず、フレームも予約されない** (`Duration::MAX`)。
  実時間は 1 秒も待たない。
* `pet::sleep_tests::入力があれば即座に起きる` — 止まったあとポインタを
  動かす / ホイールを回すと、その場で要求が復活する。
* `pet::sleep_tests::静止後はperfの内訳が空になる` — アイドル 600 フレームを
  流して `repaint_ranking()` が空・`idle_repaints() == 0` であること。
  要求は `perf::test_sink` (**スレッドローカル**。プロセス共通の static に
  すると同時に走る他のテストの呼び出しが混ざる) で実際に観測する。
* `pet::sleep_tests::睡眠を切っていても放置すれば止まる` — 設定で
  設計原則 3 を外せないこと。
* `pet::sleep_tests::一度の入力で出る要求の総量に上限がある` — **絶対時間では
  なく件数**で線を引く番人。予約した刻みどおりに次のフレームを起こして数える。
* `pet::tests::終わりの無い状態はアプリの刻みを超えない` — ペットが
  `app::idle_repaint_ms` より速い刻みを出していないこと。
* `app::tests::再描画の要求は必ず出所つきで行う` — app.rs の素の
  `ctx.request_repaint()` を禁じ、`perf::repaint` / `repaint_after` を通させる。
  出所が分からない要求は、アイドルで CPU が回っていても犯人を特定できない。

**新しい機能で再描画を要求するときは、必ず `perf::repaint(ctx, "<タグ>")` を
通すこと。** 素の `ctx.request_repaint()` はアイドルで誰が描かせているのかを
永久に分からなくする。
