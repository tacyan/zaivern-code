# 並列開発仕様

GUI の直接依頼は、実装に必要な分担を一度だけ仕様化してから各担当を起動する。
仕様の目的は、誰が何を作り、どこで接続するかを決めること。
仕様作成そのものを長い計画・承認の工程にしない。

## 品質を保つルール

- 原依頼の全文を仕様とともに保持し、各担当へ渡す。仕様と矛盾するときは
  原依頼を優先する。要約で名称・数値・形式・禁止事項・添付参照を落とさない。
- 各要件を担当と完了条件に対応させる。曖昧な点は仮定として明記し、
  実装済み・確認済みの事実として書かない。
- 担当ごとに成果物と変更ファイルを決め、共有ファイルの編集は一担当に寄せる。
  接続契約には名前・入出力・エラー時の扱いを、必要な範囲だけ書く。
- 各担当は原依頼と接続契約を守り、独立した実装をすぐ始める。
  必要な実装上の検証は行うが、形式だけの計画・仕様・レビュー工程を追加しない。
- 統合担当は差分を統合し、原依頼の要件・接続・最終成果物を照合する。
  成果物の省略、担当の自己申告だけでの完了、確認していない性能の断言はしない。

## 仕様の書式

`## タスク` の各箇条書きが一担当・一実装タスクになる。
ID は `T01` から順に付け、担当ファイルはワークスペース相対パスを列挙する。
依存があるときは `(deps: T01,T02)` を `(files: ...)` より前に置く。
下記は記入例。パスと契約は実際の依頼・コードに合わせて置き換える。

```markdown
# 商品一覧の検索を追加

## 目的
原依頼の表示・操作・互換性を維持して検索を実装する。

## タスク
- implementer: T01 検索処理を実装する (files: src/search.rs)
- implementer: T02 検索画面を実装する (files: src/search_view.rs)
- implementer: T03 既存の画面へ接続する (deps: T01,T02) (files: src/features/search.rs)

## 接続契約
T01 は search(query: &str) -> Result<Vec<SearchItem>, SearchError> を提供する。
SearchItem は id と title を持つ。空文字は全件、失敗は SearchError で返す。
T02 はこの契約に合わせて画面を実装し、空結果とエラーを区別する。
T03 が登録・呼び出しを接続する。共有ファイルの変更は T03 に集約する。

## 完了条件
- T01: 通常検索・空文字・失敗の結果が契約どおりである。
- T02: 入力・結果・空結果・エラーが表示され、既存操作を壊さない。
- T03: 既存画面から検索へ到達でき、処理と画面が接続されている。
- 原依頼の全要件を満たし、担当差分を統合した成果物が利用できる。

## 原依頼（最優先・省略禁止）
ここにユーザーの依頼全文を省略せず保持する。
```

T01 と T02 は契約だけを共有して並列実装し、T03 は両担当の完了後に動く。
コードそのものが先に必要な場合だけ依存を指定する。
依存を生成する際は、後続が消費する必須入力と待機理由を担当本文に記載する。
名称・配色・概念・API契約を揃えるだけなら共有契約に移し、独立実装する。
例えば独立した3スキルは3担当とも `deps: none` とし、整合確認は統合担当が行う。
先行の実データや確定判断が必要なら、編集ファイルが別でも依存を残す。
生成内の最終見直しで「独立なのに待つ」矛盾を取り除く。既存仕様の明示依存を
実行時に推測で削除することはしない。
人数の既定は「おまかせ」。生成済みの計画の並列幅で人数を決定するため、
独立3担当なら3体、直列作業なら1体になる。レビューのない計画に予備担当は足さない。
人数を手動指定した場合はその上限を守る。上限2体で3担当なら空き次第3担当目を配る。
人数に合わせて担当や成果物を増やさない。
ファイルが重なる担当は先行順に直列化されるため、独立させたい担当同士で
同じファイルを申告しない。担当範囲を空にして並列化したことにしない。
単一ファイルなど分割に利点がない成果物は一実装担当と統合担当で扱う。
統合担当は実行側が追加するため、仕様に同じ全体統合を重複して書かない。

## 今回の実装分担

実行指示は担当に応じて切り替える。実装担当は所有成果物の作成、共有契約の
遵守、担当内検証を行い、提供した入出力・変更ファイル・検証結果・接続時の
注意を引き継ぐ。`assemble` の統合担当は各差分を隔離先に取り込み、完成した
本体を作り直さず、接続と利用経路、原依頼の全要件を確認する。

完了報告は Run 専用 outbox に一度提出し、成功時に同じ JSON を端末へ再出力
しない。書込み失敗時だけ端末のマーカー付き JSON へ切り替える。変更パスは
一要素一パスとし、表示用の改行を混ぜない。検証結果は実行したものだけ記録する。
古いタスクへの再提出要求で成果物を作り直さず、報告形式の訂正は報告だけを直す。

| 担当 | 変更範囲 | 接続・完了条件 |
| --- | --- | --- |
| 計画変換 | `src/team/planner.rs` | 仕様の担当を欠落なく実装タスク化し、ファイル重複と明示依存を反映する |
| GUI・仕様生成 | Team の GUI 起動経路と仕様生成処理 | 非同期で一度だけ生成し、原依頼を保持して計画変換へ渡す |
| 文書 | `docs/team.md`, `docs/team-parallel-spec.md` | 書式・担当・品質保持・受入条件を説明する |
| 統合 | 各担当の変更差分 | 呼び出し経路と回帰テストを確認し、要件全体を照合する |

## 受入条件

1. GUI の直接依頼から並列仕様が生成され、成功後に実装へ進む。
   生成待ちで描画を止めず、失敗を黙って担当不明の並列実装に変えない。
2. 原依頼の先頭から末尾まで各担当へ届く。仕様の要約だけに置き換えない。
3. 仕様の各担当が一実装タスクになる。例えば 6 担当・同時実行数 2 でも
   6 担当すべてを保持し、空きができた順に実行する。
4. 独立ファイルの担当は同時に実行可能で、明示した依存とファイル重複がある
   担当だけを待たせる。存在しない依存・循環依存を正常な計画として実行しない。
5. 仕様生成の後に計画専任・設計専任のタスクを追加せず、全体統合は一担当にする。
6. 既存の単一成果物の扱い、隔離先、差分統合、失敗・再試行の制御を維持する。

## 速度の確認方法

同じ依頼・モデル・エージェント数・開始状態で比較し、仕様生成時間、最初の
実装開始までの時間、同時実行数、依存待ち時間、統合完了までの時間を記録する。
速度のために要件を減らしていないことも、原依頼との照合で確認する。
構造上の並列化と実際の所要時間短縮は別に評価し、実測前に速度倍率を保証しない。
