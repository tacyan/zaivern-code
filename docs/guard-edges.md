# ガードの縁 (guard edges) — 取りこぼしを起こす形と、その塞ぎ方

`src/guard.rs` は**書き込みの最後の関所**である。ここが漏れると「競合ゼロ」は
成立しない。この文書は「どんな綴り・どんなファイルなら関所を素通りできるか」を
洗い出した結果と、採った方針を残す。

## 0. 二段構えであること

| 段 | 何を見る | 見えないもの |
|---|---|---|
| 書き込み時 (`lease::gate` / `zai guard check --path`) | これから書くパス 1 本 | まだ書かれていない変更 |
| コミット時 (`guard::check_staged`) | index が確定した変更 | **git が index に入れない経路** |

**git は「シンボリックリンクを越えるパス」を index に入れない**
(`fatal: pathspec 'lib/app.rs' is beyond a symbolic link`)。
つまりコミット時の関所には*構造的に*見えない書き込みがある。
だから書き込み時の入口 (`zai guard check --path <ファイル>`) が要る。

## 1. 正規化の方針 — **字句 ∪ 実体**

`lease::normalize_path` は **字句だけ**の正規化である
(`.` を捨て `..` を畳み、`\` を `/` へ寄せ、macOS / Windows では大小を畳む)。

* **字句だけでは足りない。** `lib -> src` のとき `lib/app.rs` と `src/app.rs` は
  同じ実体なのに字句では別物で、担当表を別々の綴りで書いた 2 人が
  **同じ行を同時に持てる**。
* **実体だけでも足りない。** `canonicalize` は*その瞬間*しか答えない。
  リンクは判定とコミットの間に張り替えられる (TOCTOU) し、
  まだ存在しないファイルは解決できない。
  実体の答えだけを採ると、**リンクを張り替えるだけで担当から外れる**。

採ったのは **どちらかで当たれば当たり (和)** である。実体の綴りを*足す*だけで
字句の綴りを捨てないので、TOCTOU で緩む方向へは動かない。
解決できない (輪 / 読めない) ときも字句の答えが残る。

実体の解決は `pathx::LinkResolver` が行う。`canonicalize` を使わないのは
(1) 途中に実在しない要素があっても答えを返す必要があるため
(2) ディレクトリの解決を憶えて「パス × 担当」で探らないため
(3) `guard::canon_key` の呼び出し回数を固定しているテストを鈍らせないため。

**リンクの行き先は「1 つの葉」ではなく「並んだ要素」として辿る。**
行き先の途中に別のリンクが居ることがある (macOS の `/var` → `private/var`)。
葉だけを見て済ませると、外へ出たまま戻ってこられず「実体は中にあるのに外」と
答える (実際にこれで検査が落ちた)。中か外かは**最後にだけ**決める。

## 2. 塞いだ抜け道

| # | 形 | 塞ぐ前 | 塞いだ後 |
|---|---|---|---|
| 1 | 担当表がリンク越しの綴り (`lib/f.txt`)、コミットは実体の綴り (`src/f.txt`) | 素通り (字句が一致しない) | 止まる (`Pat::alias`) |
| 2 | リポジトリ内のリンクでリポジトリの**外**へ書く | 素通り (git が index に入れない) | `zai guard check --path` が止める |
| 3 | リンクが輪になっている | 解決できず素通り | **判定できないものは通さない** |
| 4 | リンク**自体**の張り替え | 「1 行のテキスト変更」に見える | ファイル全体として扱う (mode 120000) |
| 5 | `.` / `..` / 区切り / 大小の違いで綴りを変える | — (`normalize_path` が既に畳んでいた) | 検査で固定 |
| 6 | Windows の `\\?\` / UNC 接頭辞 | 片側だけ解決できると文字列が食い違う | `canon_key` を `pathx::canonical` 経由に |

* **5 と 6 は「もともと塞がっていた／潜在的だった」ものである。**
  5 は `lease::normalize_path` が既に畳んでいたが、検査が無かった。
  6 は両側とも解決できる限り露見しないが、片側だけ解決できたときに
  **自分の確保を他人のものと誤認して自分のコミットを止める**形で出る。

## 3. 劣化を黙って起こさない

行域が使えないファイルは**ファイル全体の担当**として突き合わせる。これは安全側
だが、**そうなったことが伝わらないと、なぜ止められたのか判らない**
(行をずらせば通るのか、そもそも行域が効かないのかで打つ手が正反対になる)。

`WholeWhy` が理由を持ち、拒否の文面に 1 行足す。

| 理由 | いつ |
|---|---|
| `Shape` | 新規 / 削除 / リネーム / 複製 / 型・モード変更 / シンボリックリンク。**劣化ではなく定義**なので文面に出さない |
| `NoHunks` | 内容の変更なのにハンクが 1 つも出ない = 二値 / `-diff` / `core.bigFileThreshold` 超え |
| `Unaligned` | 記録の数とパッチの節の数が合わない |
| `Lfs` | Git LFS のポインタ (`version https://git-lfs.github.com/spec/…`) |

LFS の判定は `.gitattributes` を引かずに**パッチ本文から**行う。
`-U0` では文脈行が本文に出ないので、`oid` / `size` だけの変更は
ハンク見出しの後ろ (`@@ -2,2 +2,2 @@ version https://…`) からしか判らない。

## 4. `.gitattributes`

`git check-attr -z --stdin diff merge filter` を **1 回だけ**、
しかも**止めると決まった後にだけ**呼ぶ。通す経路の git 呼び出しは
これまでどおり 1 回のままである (未導入者のコストはゼロ、という約束を崩さない)。

* `merge=union` — **両方の行を残す**ドライバなので、同じ行域を 2 人が触っても
  解決はぶつからない。**止めない**。`CHANGELOG` や `.gitignore` で実際に使われる
* `-diff` / `binary` / `filter=lfs` — 行域が使えなかった**理由**として文面に出す

## 5. 残っている限界 (正直に)

* **書き込み時の関所は `lease.rs` が持っている。** `lease::rel_within` は
  実体がルートの外へ出ると `None` (= 関知しない) を返すので、
  リポジトリ内のリンクを通った書き込みは**そちらの経路では**まだ素通りする。
  `guard::check_path` は同じ穴を塞いだ実装を持っているが、
  `lease::gate` からは呼ばれていない (担当ファイルが別のため)。
  必要な変更は `src/lease.rs:777` の `rel_within`:
  リンクを解いた結果がルートの外なら `None` ではなく
  **字句のルート相対を返す** (fail-closed)。`pathx::LinkResolver` を使えば
  `Resolved::Outside` として区別できる。
* **sparse-checkout** — `git diff --cached` は index を見るので、
  作業ツリーに無いファイルの担当も正しく突き合わせられる。
  ただし `--path` の問い合わせは実体を探るので、
  sparse で materialize されていないパスは「まだ無いファイル」として扱われる
  (リンクではあり得ないので字句の答えがそのまま使われる = 安全側)。
  **`.gitattributes` の側も cone の外へ効く** — git は作業ツリーに無い
  `.gitattributes` を index から読むので、`check_attrs` が引く
  `git check-attr` は cone の外のパスにも正しい答えを返す
  (cone / no-cone の両方で実測。[docs/repo-shapes.md](repo-shapes.md) §3)。
* **ファイル名に `*` `?` `[` が入っている**と `region::conflicts` が glob と
  見なして常に衝突扱いになる (`lease::covers` と同じ限界。安全側)。
